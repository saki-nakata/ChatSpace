## フェーズ5 — メンション・通知

**状態: 未着手**

`@メンション`の解決・通知、およびDM/チャンネル/招待/スレッド返信の各通知生成とリアルタイム配信を実装する。**通知のスコープ再チェック(AND結合)がプロトタイプに実在するギャップの修正であり最重要**。詳細は [`docs/機能定義書/メンション機能定義書.md`](../docs/機能定義書/メンション機能定義書.md)・[`docs/機能定義書/通知機能定義書.md`](../docs/機能定義書/通知機能定義書.md) を正とする。

### 実装対象

- [ ] `MentionResolver`: 正規表現でメッセージ本文から`@ハンドル`候補を抽出し、**その時点のライブなチャンネルメンバーシップとのみ突合**して`Mention`レコード・通知を生成(非メンバーへの通知・存在漏洩を防止)
- [ ] メンション自動補完APIも同じ制約(対象チャンネルのメンバーのみを候補として返す)
- [ ] `Notification`エンティティのCRUD、`NotificationService`
- [ ] 通知生成トリガー: `MENTION`(チャンネルメッセージ内の有効なメンション)、`DM`(DM送信)、`THREAD_REPLY`(自分のスレッド親への返信、メンション無しでも届く)、`CHANNEL_INVITE`、`WORKSPACE_INVITE`
- [ ] **通知一覧・`unread-count`・個別既読・全件既読の全4エンドポイントに、channel/dm/workspaceの3条件を`AND`結合したライブスコープ再チェックを適用**(通知機能定義書§6.1のSQL例。`OR`結合すると`dm_id IS NULL`によりDM側の節が常に真になりフィルタが無効化される致命的バグになるため要注意)。N+1回避のため`EXISTS`結合の1本のRepositoryクエリで実装
- [ ] DM側の`EXISTS`は`workspace_members`との`JOIN`を必ず含める(`DmThread`の参加者情報はワークスペースキック後も消えないため)
- [ ] `(createdAt, id)`複合カーソルページネーション、1回最大50件、`nextCursor`をレスポンスに含める
- [ ] 通知パネルのUI仕様に対応するAPI動作: 新しい順、既読化しても並び順・表示位置を変更しない、個別既読・全件既読で存在しない/他人の`notificationId`は404
- [ ] STOMP `/user/queue/events`経由のリアルタイム配信(`NotificationService`から`RealtimeEventPublisher`経由で呼ぶ。フェーズ4で実装済みの宛先解決・Principal一致保証を利用)

### 先に書くテスト

`docs/テスト設計書.md` §6.2 の該当テストID。

- [ ] AUTH-N01: メンション経由のメンバー漏洩防止
- [ ] AUTH-N02: メンション自動補完のメンバー限定
- [ ] AUTH-N03〜N05: 通知のスコープ再チェック(一覧・未読件数・既読化)
- [ ] AUTH-N06: 通知スコープ条件のAND結合検証(OR結合の回帰防止)
- [ ] AUTH-N26: ワークスペースキック後のDM権限失効(5) — 過去のDM通知が一覧・未読件数に含まれなくなること

### 対象外(本フェーズでは扱わない)

- ブラウザ通知(Web Push)・タブタイトル未読件数表示はフェーズ10(UX拡張)

### 確認方法

```bash
docker compose up -d postgres
cd apps/api-java
./gradlew build
```
