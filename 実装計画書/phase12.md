## フェーズ12 — 仕上げ

**状態: 未着手**

プロトタイプから継続する既知のギャップの解消、本番デプロイに向けたセキュリティ設定の最終確認、ログ・監査体制の整備を行う。詳細は [`docs/ログ運用設計書.md`](../docs/ログ運用設計書.md)・[`docs/インフラ構成書.md`](../docs/インフラ構成書.md) を参照。

### 実装対象

- [ ] 認証系のレート制限追加(ログイン試行等のブルートフォース対策。プロトタイプ未実装の既知ギャップ、認証機能定義書§7参照)
- [ ] **本番ドメイン確定後のSameSite/CSRF方針再確認**: フロントエンド・バックエンドが同一registrable domain(eTLD+1)であることを前提に`SameSite=Lax`をCSRF主防御としているため、別ドメイン構成になる場合は`SameSite=None; Secure`+CSRFトークン方式へ切り替える判断が必要(インフラ構成書参照)
- [ ] 構造化ログの導入(認可拒否・認証失敗イベントの記録。パスワード・JWT・メッセージ本文・PIIをログに残さない方針の徹底)
- [ ] 監査ログ対象の実装(オーナー限定操作の実行、キック操作とロールバック時の非切断、通知配信失敗、STOMP接続拒否等。ログ運用設計書の表を参照)
- [ ] Render環境でのログ確認方法の確立(公式ログ機能の利用、保持期間の限界と外部集約要否の判断)
- [ ] **情報漏洩監査**: 実装時点の正しさ(認可クリティカルテストで担保済み)とは別に、運用開始後にログから事後的に検知・確認できるかという観点での確認(ログ運用設計書の観点一覧に沿って実施)

### 先に書くテスト

このフェーズは既存の認可クリティカルテストの追加ではなく、運用・監査観点のレビューが中心。レート制限は新規に単体テスト(規定回数超過で429等)を追加する。

### 対象外(本フェーズでは扱わない)

- 水平スケール対応(フェーズ13)・パフォーマンステスト(フェーズ14)

### 確認方法

```bash
cd apps/api-java
./gradlew build
# レート制限の手動確認(規定回数を超えるログイン試行)
```
