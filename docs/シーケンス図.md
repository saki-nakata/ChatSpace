# ChatSpace シーケンス図

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

> 本ドキュメントは `.plans/java-spring-boot-redesign.md`(承認済み再設計計画書)を一次情報源とする。実装が計画から変更された場合は本ドキュメントも追随して更新すること。

---

## 概要

本ドキュメントでは、Java/Spring Boot + STOMP + PostgreSQL への再設計後の ChatSpace における主要な操作フローを Mermaid シーケンス図で示す。特に認可(誰が何を見られるか・実行できるか)に関わるフローは、CLAUDE.md が最大のリスクと位置づけている領域であるため、正常系だけでなく拒否・失敗系の分岐も明示する。

### 前提知識:認証・リアルタイム通信

| 項目 | 仕様 |
|------|------|
| 認証方式 | ステートレス JWT(HS256、Nimbus JOSE+JWT で発行・検証) + httpOnly Cookie |
| Cookie 名 | `chatspace_token`(`HttpOnly; SameSite=Lax; Secure`〔本番のみ〕、`path=/`) |
| JWT 有効期限 | 7日間(リフレッシュトークンなし。ログアウトはCookie削除のみでサーバー側失効なし) |
| パスワードハッシュ | bcrypt(コストファクタ12)。ユーザー不在時もダミーハッシュ比較でタイミング攻撃を防止 |
| REST 認証エントリポイント | `JwtAuthenticationFilter`(`OncePerRequestFilter`)。Cookie 欠如・不正時は 401 を返さず `SecurityContext` を空のまま後続へ委譲する |
| WebSocket エンドポイント | `/ws`(SockJS フォールバックなし、生 WebSocket のみ) |
| STOMP ブローカー | Spring 標準シンプルブローカー(インメモリ、単一インスタンス前提。フェーズ0-12) |
| WebSocket 認証タイミング | ハンドシェイク時に Cookie の JWT を検証(STOMP CONNECT フレームではない) |
| Origin 検証 | `StompEndpointRegistry.setAllowedOriginPatterns(...)` で `WEB_ORIGIN` 由来の許可オリジンのみ許可 |
| 個人宛通知の宛先 | `/user/queue/events`(実体は `/user/{userId}/queue/events`、`convertAndSendToUser()` で解決) |

## 1. ユーザー登録・ログイン

JWT発行とCookie設定の流れを示す。登録・ログインいずれも成功時は同じ形式(HS256・7日間有効)のJWTを`chatspace_token`Cookieに設定する。

```mermaid
sequenceDiagram
    actor User
    participant Web as React (apps/web)
    participant API as AuthController
    participant Pwd as PasswordService (bcrypt)
    participant Jwt as JwtService
    participant DB as PostgreSQL

    Note over User,DB: 新規登録
    User->>Web: ユーザーID・パスワードを入力して登録ボタン押下
    Web->>Web: バリデーション(ユーザーIDの形式・文字数、パスワード必須)
    alt バリデーションエラー
        Web-->>User: エラーメッセージを表示
    else バリデーション OK
        Web->>API: POST /auth/signup { userId, password }
        API->>DB: ユーザーID重複チェック(SELECT users WHERE user_id)
        alt ユーザーID重複
            DB-->>API: 既存ユーザーあり
            API-->>Web: 409 { error: "このユーザーIDは既に使用されています" }
            Web-->>User: エラーメッセージを表示
        else 重複なし
            API->>Pwd: hash(password, cost=12)
            Pwd-->>API: bcryptハッシュ
            API->>DB: users テーブルに INSERT
            DB-->>API: 作成されたユーザー(内部UUID)
            API->>Jwt: generate(sub=userId, exp=7日, alg=HS256, secret=JWT_SECRET)
            Jwt-->>API: 署名済みJWT
            API-->>Web: 201 + Set-Cookie: chatspace_token(HttpOnly; SameSite=Lax; Secure〔本番のみ〕; path=/; Max-Age=7日)
            Web-->>User: ワークスペース一覧画面へ遷移
        end
    end

    Note over User,DB: ログイン
    User->>Web: ユーザーID・パスワードを入力してログインボタン押下
    Web->>API: POST /auth/login { userId, password }
    API->>DB: ユーザーIDでユーザーを検索
    alt ユーザーが存在しない
        DB-->>API: 該当なし
        API->>Pwd: compare(password, DUMMY_HASH)（タイミング攻撃対策、固定ダミーハッシュに対して必ず比較する）
        Pwd-->>API: false(常に不一致)
        API-->>Web: 401 { error: "ユーザーIDまたはパスワードが正しくありません" }
        Web-->>User: エラーメッセージを表示
    else ユーザーが存在する
        DB-->>API: ユーザー(bcryptハッシュ含む)
        API->>Pwd: compare(password, storedHash)
        alt パスワード不一致
            Pwd-->>API: false
            API-->>Web: 401 { error: "ユーザーIDまたはパスワードが正しくありません" }
            Web-->>User: エラーメッセージを表示
        else パスワード一致
            Pwd-->>API: true
            API->>Jwt: generate(sub=userId, exp=7日)
            Jwt-->>API: 署名済みJWT
            API-->>Web: 200 + Set-Cookie: chatspace_token(同上属性)
            Web-->>User: ワークスペース一覧画面へ遷移
        end
    end
```

## 2. 認証済み API リクエスト

`JwtAuthenticationFilter`は「Cookieがあれば検証してコンテキストにセットするだけ」であり、401を返す判断そのものはSpring Securityの認可フィルタ(`AuthenticationEntryPoint`)が行う点に注意。公開エンドポイント(`/auth/**`・`/health`)は`SecurityContext`が空でもハンドラへ到達できる。

```mermaid
sequenceDiagram
    actor User
    participant Web as React (apps/web)
    participant Filter as JwtAuthenticationFilter
    participant Sec as Spring Security(認可フィルタ / AuthenticationEntryPoint)
    participant Svc as Controller/Service層
    participant DB as PostgreSQL

    User->>Web: 操作(チャンネル一覧表示・メッセージ送信等)
    Web->>Filter: APIリクエスト(Cookie: chatspace_token を自動送信)

    alt Cookie が無い、または JWT が不正・期限切れ
        Filter->>Filter: 検証失敗を無視し SecurityContext を空のまま doFilter() で後続へ委譲
        Filter->>Sec: リクエストを引き渡す
        alt 公開エンドポイント(/auth/**, /health)
            Sec->>Sec: permitAll() のためそのまま通過
            Sec->>Svc: ハンドラへ到達
            Svc-->>Web: 200 レスポンス
        else 保護対象エンドポイント(/workspaces/** 等)
            Sec->>Sec: SecurityContext が空 → 認証エラーと判定
            Sec-->>Web: 401 { error: "Unauthorized" }(AuthenticationEntryPoint)
            Web-->>User: ログイン画面へリダイレクト
        end
    else Cookie の JWT が正当
        Filter->>Filter: JwtService.verify() で署名・有効期限を検証
        Filter->>Filter: SecurityContext に Authentication(userId) をセット
        Filter->>Sec: リクエストを引き渡す
        Sec->>Sec: 認証済みと判定、認可設定に従い通過
        Sec->>Svc: ハンドラへ到達(*AuthorizationService によるリソース単位の認可チェックはここで実施)
        Svc->>DB: 業務データの読み書き
        DB-->>Svc: 結果
        Svc-->>Web: 200 レスポンス
        Web-->>User: UI を更新
    end
```

## 3. STOMP 接続確立

WebSocketハンドシェイク時にOrigin検証とJWT検証を行う。STOMP CONNECTフレームでの検証ではなく、ハンドシェイク(HTTPアップグレード)時点で完結させる設計。

```mermaid
sequenceDiagram
    actor User
    participant Web as React (@stomp/stompjs)
    participant HS as HandshakeInterceptor
    participant Jwt as JwtService
    participant CI as WebSocketAuthInterceptor(ChannelInterceptor)
    participant Reg as SessionRegistry

    Web->>HS: WebSocket ハンドシェイク要求(GET /ws, Cookie: chatspace_token 自動送信)
    HS->>HS: Origin ヘッダを WEB_ORIGIN 許可リストと照合(setAllowedOriginPatterns)
    alt 許可外 Origin
        HS-->>Web: ハンドシェイク拒否(403)
    else 許可された Origin
        HS->>Jwt: Cookie の chatspace_token を verify()
        alt JWT が不正・欠如・期限切れ
            HS-->>Web: ハンドシェイク拒否(401 相当でアップグレード不可)
        else JWT が正当
            HS->>HS: DefaultHandshakeHandler.determineUser() で Principal(name=userId) を設定
            HS-->>Web: 101 Switching Protocols(WebSocket確立)

            Web->>CI: STOMP CONNECT フレーム送信
            CI->>CI: Principal の有無を再確認(ハンドシェイクで設定済みか)
            alt Principal なし
                CI-->>Web: 接続拒否
            else Principal あり
                CI->>Reg: afterConnectionEstablished(session) で userId・sessionId を登録
                Reg-->>CI: 登録完了(Map<sessionId, session>, Map<userId, Set<sessionId>>)
                CI-->>Web: CONNECTED フレーム
            end
        end
    end
```

## 4. メッセージ送信とリアルタイム配信

メッセージ作成はREST経由(STOMP SENDではない)。作成成功後、`RealtimeEventPublisher`が`/topic/channels.{channelId}`へブロードキャストし、購読中の全クライアント(送信者本人を含む)が受信する。

```mermaid
sequenceDiagram
    actor User as 送信者
    participant WebA as React(送信者)
    participant API as MessageController/Service
    participant Guard as ChannelAuthorizationService
    participant DB as PostgreSQL
    participant Broker as STOMPシンプルブローカー
    participant WebB as React(同一チャンネル購読中の他クライアント)

    User->>WebA: メッセージ本文を入力して送信
    WebA->>API: POST /channels/{channelId}/messages { body }
    API->>Guard: requireChannelMember(channelId, userId)
    alt 非メンバー
        Guard-->>API: 例外(404)
        API-->>WebA: 404
    else メンバー
        Guard-->>API: OK
        API->>DB: message テーブルに INSERT(必要なら mention/attachment も同一トランザクションで処理)
        DB-->>API: 作成された Message
        API-->>WebA: 201 { message }
        API->>Broker: SimpMessagingTemplate.convertAndSend("/topic/channels.{channelId}", MESSAGE_CREATED payload)
        Broker-->>WebA: MESSAGE_CREATED(自分自身の購読分としても配信)
        Broker-->>WebB: MESSAGE_CREATED
        WebB-->>WebB: 受信したメッセージをUIへ即時追加
    end
```

## 5. チャンネル SUBSCRIBE 時の認可チェック

`SUBSCRIBE`フレームは平時の認可実施点。非メンバーの購読は拒否する。あわせて、クライアントが`/topic/**`へ直接`SEND`しようとした場合の default-deny も示す。

```mermaid
sequenceDiagram
    actor User
    participant Web as React(@stomp/stompjs)
    participant SI as SubscribeInterceptor(SEND/SUBSCRIBE default-deny)
    participant Guard as ChannelAuthorizationService
    participant DB as PostgreSQL
    participant Broker as STOMPシンプルブローカー

    Note over Web,Broker: 正常な SUBSCRIBE
    Web->>SI: SUBSCRIBE /topic/channels.{channelId}
    SI->>SI: 宛先パターンからチャンネルトピックと判定
    SI->>Guard: requireChannelMember(channelId, userId)
    Guard->>DB: SELECT channel_member WHERE channel_id=? AND user_id=?
    alt 非メンバー
        DB-->>Guard: レコードなし
        Guard-->>SI: 例外
        SI-->>Web: 購読拒否(ERRORフレーム、接続自体は維持)
    else メンバー
        DB-->>Guard: レコードあり
        Guard-->>SI: OK
        SI->>Broker: 購読を登録
        Broker-->>Web: 購読成功、以後のイベントを受信可能
    end

    Note over Web,Broker: 悪意あるクライアントによる直接 SEND(拒否されるべきケース)
    Web->>SI: SEND /topic/channels.{channelId}(偽装 MESSAGE_CREATED を送りつけようとする)
    SI->>SI: SEND 宛先のホワイトリスト(/app/** のみ許可)と照合
    SI-->>Web: 拒否(/topic/**・/queue/**・/user/** へのクライアント発SENDは常に default-deny)
```

## 6. キック時の強制切断

`WorkspaceService`/`ChannelService`はメンバーシップ削除のトランザクション内で`MemberKickedEvent`を発行するだけに留め、実際の`SessionRegistry`参照・`session.close()`は`@TransactionalEventListener(phase = AFTER_COMMIT)`側でのみ実行される。**ロールバック時はイベントリスナー自体が発火しないため、強制切断は発生しない。**

```mermaid
sequenceDiagram
    actor Owner
    participant WebO as React(オーナー)
    participant API as WorkspaceService/ChannelService(@Transactional)
    participant DB as PostgreSQL
    participant Pub as ApplicationEventPublisher
    participant Listener as MemberKickedEventListener(@TransactionalEventListener, AFTER_COMMIT)
    participant Reg as SessionRegistry
    participant WebK as React(キック対象ユーザー)

    Owner->>WebO: メンバーをキック操作
    WebO->>API: POST /workspaces/{id}/members/{userId}/kick
    API->>API: WorkspaceAuthorizationService.requireOwner(workspaceId, callerUserId)
    alt 呼び出し元がオーナーでない
        API-->>WebO: 403
    else オーナーである
        API->>API: @Transactional 開始
        API->>DB: workspace_member(または channel_member) を DELETE
        API->>Pub: publishEvent(MemberKickedEvent) ※コミット前に呼ばれるが、リスナーの実行はコミット完了まで遅延される

        alt トランザクションが正常にコミットされた場合
            API->>DB: COMMIT
            DB-->>API: コミット成功
            Note over Pub,Listener: AFTER_COMMIT フェーズでリスナーが発火
            Pub->>Listener: MemberKickedEvent を配信
            Listener->>Reg: userId に紐づく WebSocketSession を取得
            Reg-->>Listener: セッション(存在すれば)
            opt セッションが存在する
                Listener->>WebK: (ベストエフォート) /user/queue/events へ MEMBER_REMOVED 通知
                Listener->>WebK: session.close(CloseStatus.POLICY_VIOLATION) で強制切断
            end
            WebK->>WebK: STOMP 自動再接続ロジックが発火
            WebK->>API: 新しいハンドシェイクで JWT を再検証(§3参照)
            WebK->>API: 対象チャンネル/ワークスペースへ再度 SUBSCRIBE
            API-->>WebK: 拒否(DB上のメンバーシップは既に削除済みのため §5 の認可チェックで404/拒否)
            API-->>WebO: 200(キック成功)
        else トランザクションがロールバックされた場合(例: 後続のバリデーション例外)
            API->>DB: ROLLBACK
            DB-->>API: ロールバック
            Note over Pub,Listener: コミットが成立しなかったため AFTER_COMMIT リスナーは一切発火しない
            Note over Reg,WebK: SessionRegistry は参照されず、強制切断も発生しない(対象ユーザーは接続・購読を維持したまま)
            API-->>WebO: 5xx/4xx エラー
        end
    end
```

## 7. 個人宛通知の配信

`/user/queue/events`宛のプッシュ配信と、通知取得系エンドポイント(一覧・未読件数・既読化)でのライブスコープ再チェックを分けて示す。後者はCLAUDE.mdが名指しする「通知のスコープ漏洩防止」に対応する新規の受け入れテスト対象。

### 7-1. メンション通知のリアルタイム配信

```mermaid
sequenceDiagram
    actor Sender
    participant WebS as React(送信者)
    participant API as MessageService/MentionResolver
    participant DB as PostgreSQL
    participant Tmpl as SimpMessagingTemplate
    participant WebR as React(メンション対象ユーザー、オンライン)

    Sender->>WebS: 本文に "@bob" を含むメッセージを送信
    WebS->>API: POST /channels/{channelId}/messages
    API->>API: MentionResolver が正規表現でメンション候補を抽出
    API->>DB: 対象チャンネルの現在のライブなメンバーシップと突合(非メンバーは除外)
    DB-->>API: メンバーであるユーザーのみのリスト
    API->>DB: Notification/Mention レコードを INSERT(メンバーのみ)
    API->>Tmpl: convertAndSendToUser(userId="bob", "/queue/events", NotificationPayload)
    Note over Tmpl: UserDestinationMessageHandler が Principal#getName() を使い<br/>宛先を /user/bob/queue/events に解決する。<br/>ハンドシェイク時に設定した Principal.getName() と<br/>ここで渡す userId の一致がプッシュ成立の前提
    alt bob が現在オンラインで /user/queue/events を購読中
        Tmpl-->>WebR: NotificationPayload を配信
        WebR-->>WebR: 通知UI(バッジ・トースト等)を即時更新
    else bob がオフライン
        Note over Tmpl: 配信はスキップされる(DBには保存済みのため、次回一覧取得〔7-2〕で取得可能)
    end
```

### 7-2. 通知取得時のライブスコープ再チェック

```mermaid
sequenceDiagram
    actor User
    participant Web as React
    participant API as NotificationController/Service
    participant DB as PostgreSQL

    User->>Web: 通知一覧を開く / 未読バッジを確認 / 通知を既読にする
    Web->>API: GET /notifications または GET /notifications/unread-count<br/>または POST /notifications/{id}/read または /notifications/read-all
    API->>DB: Notification を channel_member/dm_thread+workspace_member/workspace_member と<br/>EXISTS句(3条件すべて AND 結合)で絞り込む単一クエリを実行
    Note over DB: WHERE (channel_id IS NULL OR EXISTS(channel_member))<br/>  AND (dm_id IS NULL OR EXISTS(dm_thread JOIN workspace_member))<br/>  AND (workspace_id IS NULL OR EXISTS(workspace_member))
    DB-->>API: 現在もライブにスコープ内である通知のみ返却(キック済みチャンネル/DM/ワークスペースの通知は除外)
    API-->>Web: 200 (スコープ済みの一覧・件数・既読結果)
    Web-->>User: 表示を更新
    Note over API,DB: 同一のAND結合クエリ条件を 一覧取得・unread-count・個別既読・全件既読 の<br/>全エンドポイントに適用する(一覧からは消えるのに未読数には残る、といった不整合を防ぐため)
```

## 8. 検索

`pg_trgm` + `ILIKE`による部分一致検索。所属チャンネル/DM集合をまず解決し、その範囲内でのみ検索する。`channelId`指定時に非所属であれば「結果なし」として扱い、403/404とは区別しない(プロトタイプと同じ設計)。

```mermaid
sequenceDiagram
    actor User
    participant Web as React
    participant API as SearchController/Service
    participant DB as PostgreSQL(pg_trgm + GIN index)

    User->>Web: 検索キーワードを入力
    Web->>API: GET /search?q={q}&cursor={cursor}&channelId={任意}
    API->>DB: 呼び出しユーザーの所属チャンネルID一覧・所属DM ID一覧を解決
    DB-->>API: myChannelIds, myDmIds
    alt channelId 指定 かつ myChannelIds に含まれない
        API-->>Web: 200 { results: [] }(403/404を返さず「結果なし」と区別不能にする)
    else 所属範囲内
        API->>DB: ネイティブクエリ実行<br/>WHERE deleted_at IS NULL<br/>  AND (channel_id = ANY(:myChannelIds) OR dm_id = ANY(:myDmIds))<br/>  AND body ILIKE '%'||escape(:q)||'%' ESCAPE '\'<br/>  AND (created_at, id) < (:cursorCreatedAt, :cursorId)<br/>ORDER BY created_at DESC, id DESC LIMIT 50
        Note over DB: 3文字以上のクエリは message_body_trgm_idx(GIN, gin_trgm_ops)が効きやすい。<br/>2文字未満はトライグラムが少なく seq scan にフォールバックし得る<br/>(既知の制約。結果の正しさはILIKEにより保たれる)
        DB-->>API: マッチしたメッセージ一覧(次カーソル込み)
        API-->>Web: 200 { results, nextCursor }
        Web-->>User: 検索結果を表示
    end
```
