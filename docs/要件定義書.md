## 1. プロジェクト概要

### 1.1 プロジェクト名

ChatSpace(Java/Spring Boot 再設計版)

### 1.2 目的

Slack 風のチャットアプリケーションを提供する。ワークスペース単位でチャンネルや DM を管理し、スレッド返信・絵文字リアクション・メンション・メッセージ検索といったコミュニケーション機能を、複数ユーザーが安全に利用できる Web アプリケーションとして実装する。

### 1.3 背景

ChatSpace は Node.js/Hono/Socket.IO/Prisma/SQLite によるプロトタイプ(`apps/api`, `apps/web`)が既に `main` ブランチにマージ済みで、要件を一通り満たしている。今回はこのプロトタイプを土台にした差分改修ではなく、**バックエンドを Java/Spring Boot、フロントエンドも React を再構築するゼロからの再設計**を行う。動機は以下の通り。

- 普段使いのバックエンドスタック(Spring Boot)への統一
- プロトタイプが `CLAUDE.md` に明記していた既知の制約の解消
  - メッセージ検索: SQLite の部分一致(大文字小文字区別あり)→ PostgreSQL `pg_trgm` + `ILIKE` による部分一致検索(大文字小文字区別なし)
  - プレゼンス管理: 単一プロセスのインメモリのみ(水平スケール対応(Redis共有プレゼンス等)は検討したが、Renderが1インスタンス運用でマネージドRabbitMQも無く本番で動かす先が無いため実施しないことが確定している)
- リアルタイム層を Socket.IO から STOMP(`@stomp/stompjs`)へ、API クライアントの型ソースを zod から OpenAPI 生成型へ置き換える2点の変更が全体に染み出すため、フロントエンドも新規プロジェクトとして作り直す(移行期間中は `apps/web-next`、フェーズ11で `apps/web` にリネーム)

この再設計における最大のリスクは、プロトタイプが備えていた認可まわりの不変条件(オーナー限定操作、プライベートチャンネル/DM の非可視性、メッセージスコープの confused-deputy 攻撃対策、メンション経由のメンバー漏洩防止、添付ファイルのライブ権限再チェック、通知のスコープ漏洩防止)を新スタックで機能的に同一に再現することである。詳細な設計判断・レビュー指摘の反映内容は `.plans/java-spring-boot-redesign.md` を一次情報源として参照すること。

### 1.4 対象ユーザー

- チーム・コミュニティ単位でテキストチャットを行いたいユーザー
- ワークスペースを作成し、メンバーやチャンネルを管理したいオーナー
- 学習目的で Java/Spring Boot + STOMP + PostgreSQL によるリアルタイム Web アプリケーション開発を体験したい開発者

## 2. システム概要

### 2.1 システム構成

```
[ユーザー(ブラウザ)]
        ↕ HTTPS / WebSocket(STOMP)
[Render Web Service(単一インスタンス、Spring Boot + React静的配信を同梱)]
  ├── プレゼンテーション層  *Controller.java(REST) / @MessageMapping(STOMP)
  ├── ビジネスロジック層    *Service.java, *AuthorizationService.java, MessageScopeGuard
  └── データアクセス層      *Repository.java(Spring Data JPA) / *Entity.java
        ↕ Spring Data JPA/Hibernate(Flyway管理)
[Render PostgreSQL(pg_trgm拡張)]

[Cloudflare R2(S3互換、添付ファイル保存)]
```

3層アーキテクチャ(プレゼンテーション層/ビジネスロジック層/データアクセス層)を各ドメイン機能パッケージ(`auth/`, `workspace/`, `channel/`, `dm/`, `message/`, `search/`, `notification/`, `upload/`, `realtime/` 等)の内部で厳格に分離する。フォルダ分割はレイヤー別ではなくドメイン機能別とし、認可チェックの取りこぼしを防ぐ。詳細は `docs/インフラ構成書.md` を参照。

水平スケール対応(RabbitMQ外部ブローカーリレー・Redis共有プレゼンス・共有アップロードボリューム)は検討したが、実施しないことが確定している。詳細は `docs/インフラ構成書.md` を参照。

### 2.2 技術スタック

| 役割 | 技術・選択 | 備考 |
|---|---|---|
| バックエンド | Java + Spring Boot | 3層アーキテクチャ(feature-vertical × レイヤー分離) |
| データベース | PostgreSQL + Spring Data JPA/Hibernate | Flyway でマイグレーション管理(`ddl-auto` は不使用) |
| リアルタイム通信 | STOMP over WebSocket(`spring-boot-starter-websocket`) | Spring 標準のシンプルブローカー(単一インスタンス)。RabbitMQ 外部ブローカーリレーへの切替は水平スケール対応そのものを実施しないことが確定しているため行わない |
| スケール対応 | 水平スケール対応(Redis共有プレゼンス + RabbitMQリレー)は検討の結果実施しないことが確定 | 単一インスタンス構成のまま |
| 検索 | PostgreSQL `pg_trgm` 拡張 + `ILIKE` による部分一致検索 | Render が `pg_bigm` を公式サポートしないため採用。短いクエリ(2文字未満)は seq scan にフォールバックし得る既知の制約あり |
| 認証 | ステートレス JWT(HS256, Nimbus JOSE+JWT) + httpOnly Cookie | 有効期限7日。bcrypt(コストファクタ12)でパスワードハッシュ化 |
| 添付ファイル保存 | Cloudflare R2(S3互換オブジェクトストレージ) | Renderの無料インスタンスでは永続ディスクが使えず再デプロイのたびに消えるため、R2へ移行済み(開発/テスト環境は既定でローカルディスク) |
| デプロイ先(想定) | Render(1インスタンス構成、フロントエンド同梱配信) | Web Service 1つ。詳細はインフラ構成書.md参照 |
| フロントエンド | React + Vite + TypeScript(`apps/web`、ゼロから再構築) | Zustand 継続(`authStore`/`workspaceStore`/`notificationStore`/`presenceStore` の4分割)、`@stomp/stompjs`、`marked` + `DOMPurify` |
| API 型共有 | springdoc-openapi 生成 OpenAPI スキーマ → `openapi-typescript` でフロントエンド用型を生成 | `packages/shared`(zod)は廃止 |
| 静的解析(バックエンド) | ArchUnit(3層アーキテクチャ制約テスト)、Spotless + google-java-format(フォーマット統一)、SpotBugs(任意) | `./gradlew build` に内包(spotlessCheck・ArchUnit含む test・ビルド) |
| リポジトリ構成 | モノレポ継続。`apps/api` は Gradle プロジェクト、`apps/web` は pnpm/Vite プロジェクト | 移行期間中は `apps/api-java`/`apps/web-next` として並行開発し、フェーズ11で `apps/api`/`apps/web` にリネームした |
| パッケージマネージャ | pnpm のみ(npm/yarn は使わない) | CLAUDE.md の既存規約を Java 化後も継続 |

### 3.2 対象外機能

| 機能 | 理由 |
|------|------|
| ボイスチャンネル | CLAUDE.md に明記されたスコープ外機能 |
| 添付ファイルのウイルススキャン | マジックバイト検証のみ実施し、ウイルススキャン等は対象外(既知のギャップとして継続) |
| メール認証 | ユーザーID・パスワードのみでの登録とし、メール認証機能は持たない |
| リフレッシュトークン・サーバー側トークン失効 | JWT は発行から7日間、ログアウト後も理論上有効なままとする設計選択をプロトタイプから継続 |
| 認証のレート制限 | プロトタイプ同様未実装。フェーズ12での追加を推奨する既知のギャップ |
| 水平スケール対応(Redis共有プレゼンス・RabbitMQリレー等) | 検討したが実施しないことが確定(Renderが1インスタンス運用でマネージドRabbitMQも無く、本番で動かす先が無いため) |

### 3.4 API 一覧について

TripDiary と同じ方針を踏襲し、**手書きの API 仕様書ファイルは持たない**。springdoc-openapi がコントローラのアノテーションから自動生成する Swagger UI(開発サーバー起動中の `/swagger-ui.html`)を正とする。

- REST API の型・バリデーション制約は Jakarta Bean Validation アノテーションから springdoc-openapi が抽出し、OpenAPI スキーマとして出力する
- CI では起動中サーバーではなく、Gradle タスクが出力する `openapi.json` を用いる(`openapi-typescript` でフロントエンド用 TypeScript 型を生成するパイプラインの入力とする)
- STOMP/WebSocket のメッセージ仕様(宛先・ペイロード)は Swagger の対象外のため、`docs/機能定義書/リアルタイム通信機能定義書.md` に手動で記載する(`StompDestinations.java` を正とし、`apps/web/src/realtime/destinations.ts` と契約テストで同期を検証する)

詳細な宛先一覧・STOMP設計は `docs/機能定義書/リアルタイム通信機能定義書.md`、`docs/シーケンス図.md` を参照。

## 4. 非機能要件

| 分類 | 要件 |
|------|------|
| 認証 | ステートレス JWT(HS256、Nimbus JOSE+JWT)+ httpOnly Cookie(`chatspace_token`、`SameSite=Lax; Secure`は本番のみ)。有効期限7日 |
| パスワード | bcrypt(コストファクタ12)でハッシュ化。存在しないユーザーへのログイン試行でも固定ダミーハッシュと比較し、応答時間差からユーザー存在有無を推測できないようにする |
| 認可 | 宣言的ロールチェックではなく、サービス層のヘルパークラス(`WorkspaceAuthorizationService`/`ChannelAuthorizationService`/`DmAuthorizationService`/`MessageScopeGuard`)によるリソースメンバーシップの動的チェックを行う。存在自体を隠すべきリソースは404、閲覧可能だが操作不可なものは403とする(404-not-403方針) |
| 認可(通知) | 通知一覧・未読件数・個別既読・全件既読の全エンドポイントで、各通知が指すチャンネル/DM/ワークスペースへの現在のライブなメンバーシップを再検証し、非メンバーになったものを除外する(3条件はAND結合) |
| 認可(DM) | DM アクセス判定は「DM参加者か」に加えて「現在有効なワークスペースメンバーか」も必須条件とする(ワークスペースキック後のDM読み書き・添付取得の継続を防ぐ) |
| 認可(メンション) | メンション解決・メンション自動補完候補の取得はいずれも、その時点のライブなチャンネルメンバーシップとのみ突合し、非メンバーへの通知・情報漏洩を防ぐ |
| 認可(添付ファイル) | 添付ファイルの配信は取得の都度、所属メッセージのチャンネル/DM に対するライブな権限チェックを再実行する(アップロード時点のみのチェックにしない) |
| 認可(WebSocket) | SUBSCRIBE 時点で購読先(チャンネル/DM/ワークスペース)への現在のメンバーシップを検証。`SEND` は `/app/**` 宛のみ許可するホワイトリスト方式(default-deny)とし、`/topic/**`・`/queue/**`・`/user/**` へのクライアント直接SENDは拒否する |
| セキュリティ(WebSocket) | ハンドシェイク時に Cookie の JWT を検証。`setAllowedOriginPatterns` により許可オリジンのみ接続可能とする(Cross-Site WebSocket Hijacking 対策) |
| セキュリティ(CSRF) | REST は Cookie 認証 + `SameSite=Lax` を主たる防御としSpring SecurityのCSRF保護は無効化。STOMP CONNECT は Origin 許可リストを主たる防御とする(前提はフロント/バックエンドが同一 registrable domain であること。別ドメイン構成になる場合はフェーズ12で `SameSite=None`+CSRFトークン方式へ再検討) |
| セキュリティ(添付ファイル) | マジックバイト判定によるファイル種別検証(PNG/JPEG/GIF/WEBP/MP4/WEBM)、クライアント指定拡張子・MIMEは信用しない、保存ファイル名はUUID採番、配信時にパス正規化して保存ディレクトリ配下であることを再確認する(パストラバーサル対策) |
| セキュリティ(アップロードサイズ) | `spring.servlet.multipart.max-file-size`/`max-request-size` を25MBに設定し多層防御。サービス層でも `MultipartFile#getSize()` を再確認する |
| セキュリティ(XSS) | Markdown → HTML 変換はフロントエンド(`marked` + `DOMPurify`、`img`タグ除外)側のみで行い、バックエンドは入力値の長さ等のバリデーションのみ担当する |
| セキュリティ(検索) | `ILIKE` 検索語中の `%`・`_`・エスケープ文字自身をエスケープしてから `ESCAPE '\'` 句を付与する(意図しないワイルドカードマッチを防止) |
| データ整合性 | ソフトデリート済みメッセージは検索クエリでのみ `deletedAt IS NULL` を明示して除外する。一覧・スレッド・コンテキスト取得は削除済み行を除外せずtombstone(本文を伏せた行)として返す(DB設計書§1.1・メッセージング機能定義書§3.3参照) |
| ページネーション | メッセージ一覧・スレッド返信一覧・検索結果・通知一覧はいずれも `(createdAt, id)` の複合カーソルでページングする |
| 品質ゲート(バックエンド) | `./gradlew build`(Spotless・ArchUnit含む test・ビルド)で警告0件を必須とする |
| 品質ゲート(フロントエンド) | `pnpm run typecheck`/`lint`/`build` で警告0件を必須とする |
| 可用性 | Render(1インスタンス構成)を想定。永続ディスクと複数インスタンスが排他という Render の制約とフェーズ0-12の単一インスタンス方針は整合する |
| リアルタイム性 | WebSocket は Render 上でアイドルタイムアウトの固定値は無いが、デプロイ・再起動時に強制切断されるため、クライアント側の `heartbeatIncoming`/`heartbeatOutgoing`/`reconnectDelay` による指数バックオフ再接続を実装する |

## 5. 制約・前提条件

| 分類 | 内容 |
|------|------|
| デプロイ先 | Render(1インスタンス構成、フロントエンド同梱配信)を想定。単一インスタンス構成を前提とする |
| パッケージマネージャ | フロントエンド・ルートのオーケストレーションスクリプトとも **pnpm のみ**を使用する(npm/yarnは使わない) |
| バックエンドアーキテクチャ | ドメイン機能別のパッケージ分割と、3層アーキテクチャ(プレゼンテーション層/ビジネスロジック層/データアクセス層)のクラス責務分離を両立させる。ArchUnit により自動テストとして強制する |
| マイグレーション | Flyway によるマイグレーション管理とし、`ddl-auto: update` は使用しない |
| 水平スケール対応 | 検討したが実施しないことが確定(Renderが1インスタンス運用でマネージドRabbitMQも無く、本番で動かす先が無いため) |
| 検索エンジン | `pg_trgm` + `ILIKE` による部分一致検索を採用(`pg_bigm` は Render が公式サポートしないため不採用)。3文字未満のクエリはインデックスが効かず全表スキャンにフォールバックし得る既知の制約がある |
| フロントエンド再構築 | プロトタイプへの差分パッチではなく、`apps/web` として新規プロジェクト化する。ルーティング・Zustand4ストア構成・Markdownレンダリングの設計はプロトタイプを踏襲する |
| 旧実装の扱い | データ移行は行わない(新規シードのみ)。旧実装(Node/Hono の `apps/api`、旧 React 実装の `apps/web`、`packages/shared`)は機能同等性チェックリストを満たすまで残し、フェーズ11で削除した |
| CI | 既存の `.github/workflows/claude-code-review.yml` は引き続き稼働。新スタック用にバックエンド(`./gradlew build`)・フロントエンド(`typecheck`/`lint`/`build`)のワークフローを追加し、両方とも警告0件必須とする。新規ワークフロー自身も `quality-check` スキルの観点(最小権限の `permissions`、`timeout-minutes`、`concurrency`、スクリプトインジェクション対策)を満たす |
| ドキュメント・コミュニケーション | コミットメッセージ・PR・コードレビューはすべて日本語で記述する |

## 7. 用語定義

| 用語 | 説明 |
|------|------|
| ワークスペース | チームやコミュニティ単位で作成される最上位の管理単位。作成者が自動的にオーナーになる |
| オーナー | ワークスペースを作成したユーザー。ユーザーの招待・キック、チャンネルの追加・削除を行える唯一のロール |
| メンバー | ワークスペースに参加している一般ユーザー(オーナー以外) |
| チャンネル | ワークスペース内のテキストチャットの単位。パブリック(誰でも参加可能)とプライベート(招待制)の2種別を持つ |
| パブリックチャンネル | ワークスペースメンバー全員の一覧に表示され、誰でも自主参加できるチャンネル |
| プライベートチャンネル | 非メンバーの一覧には表示されず、存在も伏せられる、オーナーによる招待でのみ参加できるチャンネル |
| DM(ダイレクトメッセージ) | ワークスペースメンバー間の1対1のメッセージスレッド |
| スレッド | あるメッセージ(親メッセージ)に対する返信をまとめた構造。`Message` エンティティの自己参照リレーションで表現する |
| リアクション | メッセージに対して絵文字で行う簡易的な反応 |
| メンション | メッセージ内で `@ユーザー名` により特定ユーザーへ通知を送る仕組み。対象チャンネルのライブなメンバーシップとのみ突合する |
| プレゼンス | ユーザーのオンライン/オフライン状態。単一インスタンスのメモリ上で管理する(水平スケール対応は実施しないことが確定しており、Redis共有プレゼンスへの置き換えは行わない) |
| confused-deputy 対策 | URL上のスコープ(workspaceId/channelId等)と、リソースが実際に所属するスコープの一致確認を指す。`MessageScopeGuard` が担う |
| 404-not-403 方針 | 存在自体を隠すべきリソース(非参加のプライベートチャンネル/DM)へのアクセスは404を返し、閲覧可能だが操作不可能な場合のみ403を返す設計方針 |
| 機能同等性チェックリスト | 旧実装(Node/Hono/Socket.IO)を削除し新実装へ正式に置き換えるための達成条件一覧。`.plans/java-spring-boot-redesign.md` に定義。水平スケール対応は前提条件に含まれない(実施しないことが確定) |
| シンプルブローカー | Spring 標準のインメモリ STOMP メッセージブローカー。単一インスタンス内で完結する |
| outbox パターン | DBトランザクションと同一のトランザクションでイベントを永続化し、後続の非同期ディスパッチャが確実に配送する設計パターン。水平スケール対応時に必要となる想定だったが、水平スケール対応自体を実施しないことが確定したため未使用 |
