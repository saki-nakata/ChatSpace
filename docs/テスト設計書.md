**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki（Claude Code支援）
**対象:** Java/Spring Boot 再設計版（`apps/api`）

## 1. テスト方針・目的

ChatSpace はワークスペース／チャンネル単位で閲覧範囲が分かれるマルチテナント構成であり、CLAUDE.md が明記する通り「認可の実装ミスが最大のリスク」である。本テスト設計書は、この前提に立って以下の3点を核とする。

- **JUnit 5 + Testcontainers** を用い、モックではなく実際の PostgreSQL に対して統合テストを実行する（フェーズ13〈任意〉では Redis/RabbitMQ の Testcontainers も追加する）
- **認可テストは最後にまとめて書かず、各実装フェーズで対応する機能を実装する際に先に（失敗する状態で）書き、実装と同時に通す**。「テストを後回しにしない」方針そのものが、認可漏れの作り込みを防ぐ主たる手段である
- **3層アーキテクチャ（プレゼンテーション層／ビジネスロジック層／データアクセス層）の責務分離を、目視レビューだけに頼らず ArchUnit による自動テストとして強制する**

移植元は `apps/api/test/authorization.test.ts`（Node/Hono プロトタイプの認可テスト）であり、`.plans/java-spring-boot-redesign.md` §10 が定義するテスト計画を正式文書化したものが本書である。

## 2. テストレベルと範囲

| レベル | 対象 | 実施フェーズ | ツール |
|---|---|---|---|
| 単体テスト | Service層（`*AuthorizationService`、`MessageScopeGuard`、`JwtService`、`PasswordService`、`MentionResolver` 等）のホワイトボックステスト | 各機能フェーズ | JUnit 5 + Mockito |
| 統合テスト（実DB） | Controller〜Repository を通した HTTP エンドポイント経由のブラックボックステスト | 各機能フェーズ | JUnit 5 + Testcontainers（PostgreSQL）+ `MockMvc`/`WebTestClient` |
| STOMP 統合テスト | WebSocket ハンドシェイク・SUBSCRIBE/SEND 認可・強制切断 | フェーズ4 | JUnit 5 + Testcontainers + `@stomp/stompjs` 相当のテストクライアント（Spring `WebSocketStompClient`） |
| ArchUnit アーキテクチャテスト | 3層アーキテクチャの層依存制約 | フェーズ0でセットアップし、以降全フェーズで green を維持 | ArchUnit |
| 2インスタンス smoke test | 水平スケール対応（RabbitMQリレー・Redis共有プレゼンス・キック通知配送）の動作確認 | フェーズ13（任意） | docker-compose 2インスタンス構成 + 手動/スクリプト検証 |
| パフォーマンステスト | メッセージ送信API・検索API・STOMP同時接続のスループット/レイテンシ | フェーズ14（任意） | k6 |

単体テストと統合テストの比率は、認可判定ロジック自体（境界値・組み合わせ）は単体テストで網羅し、「実際のHTTPリクエスト経由で意図した通りに拒否/許可されるか」は統合テストで確認する、という役割分担を取る。プロトタイプの `authorization.test.ts` が HTTP レベルの統合テストのみだったのに対し、新スタックでは `*AuthorizationService` 単体テストを追加することで、ロジックの境界値検証と結合確認を分離する。

## 3. テスト観点

- **正常系**: 期待するステータスコード・レスポンス形状、過剰にブロックしていないこと（メンバーであれば操作が成功すること）の確認を含む
- **異常系**: 401（未認証）・403（オーナー限定操作を一般メンバーが実行）・404（非参加リソースへのアクセス、confused-deputy）・400（Bean Validation、STOMPペイロード不正値）
- **404-not-403 の使い分け**: 存在自体を隠すべきリソース（非参加のプライベートチャンネル/DM）は404、閲覧可能だが操作不可なものは403。この使い分け自体をテストケースとして明示する（例: オーナー限定操作は「メンバーだが403」、プライベートチャンネルは「非メンバーで404」）
- **スコープ漏洩防止**: 権限外のチャンネル/DM/ワークスペースの内容・存在が、実行結果（一覧・検索・通知・メンション候補）に一切含まれないこと
- **ライブ権限再チェック**: アップロード時・購読開始時点だけでなく、取得・購読の都度、現在のメンバーシップを再検証していること（過去に権限があった、では不十分）
- **AND結合の検証**: 通知のスコープ再チェックのように複数条件（channel/dm/workspace）を組み合わせる箇所は、OR結合による無効化バグ（本計画書 §3 で指摘された既知のリスク）を検知できるテストケースを含める
- **境界値・副作用非発生**: 403/404 で拒否される場合、対応する Repository の更新系メソッドが呼ばれていないことをモックで確認する（単体テストレベル）

## 4. 層別戦略と命名規則

| 層 | 手法 | モック対象 |
|---|---|---|
| Controller | ブラックボックス・統合テスト（`MockMvc`/`WebTestClient` + Testcontainers） | モックしない（実DBに対して実行） |
| Service（`*AuthorizationService`、`MessageScopeGuard` 等） | ホワイトボックス・単体テスト | Repository（Mockito） |
| Repository | 実DB検証（カーソルページング、`deletedAt IS NULL`、EXISTS/JOINによるスコープ絞り込み） | モックしない |
| STOMP（`@MessageMapping`、SUBSCRIBE/SENDインターセプタ） | 統合テスト | Testcontainers + テスト用STOMPクライアント |
| ArchUnit | アーキテクチャ制約の静的検証 | 対象外（コンパイル済みクラスを解析） |

**命名規則**: `対象_条件_期待結果`（例: `requireDmAccess_ワークスペースキック後_404`、`getChannels_非メンバー_プライベートチャンネル非表示`）。認可クリティカルテストは原則クラス単位で `authorization` パッケージ配下（`src/test/java/.../authorization/`）にまとめ、機能横断の探索性を優先する。

## 5. テスト環境

- **PostgreSQL**: フェーズ0以降、全フェーズで Testcontainers により起動（Render で確認したバージョンに揃え、dev/prod パリティを維持する。フェーズ-2 の技術検証スパイクで確定したバージョンをここに反映する）
- **Redis/RabbitMQ**: フェーズ13（任意、水平スケール対応）でのみ Testcontainers に追加する。フェーズ0-12 のテストスイートはこれらに依存しない
- **テストDB分離**: 開発用DBとは完全に分離し、Testcontainers が都度使い捨てコンテナを起動するため、本番・開発データへの誤影響は構造的に排除される
- **シードデータ**: `CommandLineRunner`（`dev,seed` プロファイル）で `alice`/`bob`/`carol`（`password123`）を再現するが、認可テストは原則としてこの共有シードに依存せず、各テストケース内で必要なユーザー・ワークスペース・チャンネルをその場で作成する（プロトタイプの `test/helpers.ts` の `createTestUser`/`createWorkspaceWithOwner`/`createChannel` パターンを踏襲し、Java側でも `AuthorizationTestFixtures`（仮称）としてテストヘルパーを用意する）

## 9. CI連携

- バックエンドの品質ゲートは **`./gradlew build`** に一本化する。Gradle は `build` → `check` → `test` の依存関係を持ち、Spotless プラグイン適用により `spotlessCheck` も `check` の依存に自動で含まれるため、`./gradlew build` 単体で以下がすべて実行される。
  - Spotless（google-java-format）によるフォーマット検証
  - ArchUnit による3層アーキテクチャ制約テスト（§6.2 AUTH-N19〜N21）
  - 単体テスト・統合テスト一式（Testcontainers込み、§6の認可クリティカルテストを含む）
  - ビルド（コンパイル、パッケージング）
- 検証のみ行いたい場合は `./gradlew check` を使う（ビルド成果物の生成を省略）
- GitHub Actions ワークフローで PR・main への push 時に `./gradlew build` を実行する。Testcontainers を回すため実行時間が読みにくく、`timeout-minutes` を必須で設定する
- フロントエンド（`apps/web`）は別ワークフローで `typecheck`・`lint`・`build`（STOMP宛先契約テストを含む `test`）を実行する
- 両ワークフローとも「警告0件必須」の既存規約（CLAUDE.md）を踏襲する
- 既存の `.github/workflows/claude-code-review.yml`（PR時のClaude Code自動レビュー）は引き続き稼働し、認可チェック項目（DM/チャンネルアクセス判定での現在のワークスペースメンバーシップ再確認、通知の全エンドポイントへの同一スコープ条件適用、AND結合、confused-deputy、ソフトデリート漏れ）をレビュー観点として持つ
