# ChatSpace ログ運用設計書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki（Claude Code支援）
**対象:** Java/Spring Boot 再設計版（`apps/api`）

---

## 0. 位置づけ

ChatSpace はワークスペース／チャンネル単位で閲覧範囲が分かれるマルチテナント構成であり、CLAUDE.md が「認可の実装ミスが最大のリスク」「特にメッセージ検索と通知は、権限外のチャンネル/DMの内容を含めやすい」と明記している。本書はこのリスクを運用面から補完するため、認可拒否・認証失敗といったセキュリティ関連イベントを構造化ログとして記録し、フェーズ12の「情報漏洩監査」で確認すべき観点を整理するものである。

**対象範囲**: バックエンド（`apps/api`、Controller/Service/Repository/STOMPハンドラ）のログ。フロントエンド（ブラウザコンソール）は対象外。
**対象外**: 実際のアラート発報設定（閾値監視ツールの具体的な設定作業）。本書は設計であり、実装フェーズの進行に応じて随時更新する前提。

## 1. ログ方針

### 1.1 構造化ログの採用（フェーズ12にて実装方式を確定）

**確定した方式**: Spring Boot 標準の構造化ログ機能（`logging.structured.format.console`）を使う。追加ライブラリ（`logstash-logback-encoder`）は導入しない。

| 項目 | 内容 |
|---|---|
| 有効化 | 環境変数 `LOG_STRUCTURED_FORMAT` に `logstash` または `ecs` を設定するとJSON出力になる。未設定なら人間可読な行形式（開発時の既定） |
| 行形式でのフィールド出力 | Logback の既定パターンは `%kvp` を含まないため、**行形式ではキー・バリューが一切表示されず監査情報が失われる**問題があった（レビュー指摘）。`logging.pattern.console` を上書きし、行形式でも `auditEvent="..."` 等と `requestId` が必ず出力されるようにしている |
| フィールド付与 | SLF4J 2系の fluent API（`log.atInfo().addKeyValue(...)`）を使う。JSON出力時はフィールドとして、行形式時はキー=値として出力される |
| リクエスト横断のコンテキスト | `MDC` に `requestId`（リクエスト単位のUUID）を入れる。`RequestLoggingFilter` が設定・除去する（スレッドプール再利用による値の漏れを防ぐため `finally` で必ず `remove` する） |
| ロガー名 | アクセスログは `ACCESS`、監査ログは `AUDIT` に固定し、アプリケーションログと分離して検索できるようにする |

`logstash-logback-encoder` を採用しなかった理由: Spring Boot 4系が同等の機能を標準で持っており、依存を1つ増やす必要がないため。

### 1.2 ログレベル方針

| レベル | 用途 |
|---|---|
| `ERROR` | 未捕捉の例外（500系）。スタックトレースを含む |
| `WARN` | 想定内のエラー（4xx系: 401 未認証 / 403 Forbidden / 404 NotFound / 400 Validation）。特に**認可拒否（403/404の一部）・認証失敗（401、ログイン失敗）はセキュリティ関連イベントとして`WARN`以上で必ず記録する**（詳細は2節） |
| `INFO` | 正常系を含む全リクエストのアクセスログ、オーナー限定操作の実行結果、STOMP接続確立/切断、キック確定イベント |
| `DEBUG` | 開発環境のデフォルトレベル。詳細なデバッグ情報（SQLクエリ等） |

環境変数（例: `LOG_LEVEL`）で上書き可能とし、未設定時は本番 `INFO` ／開発 `DEBUG` とする。

### 1.3 認可拒否・認証失敗イベントのログ記録

以下のイベントは、通常のエラーハンドリング（4xxレスポンス）と独立して、**セキュリティ関連イベントとして識別可能な形で記録する**方針を取る（後述「2. 監査ログ対象」の実装方針）。

- 401（未認証アクセス）: `AuthenticationEntryPoint` 到達時
- 403（オーナー限定操作の拒否、`WorkspaceAuthorizationService.requireOwner()` 等の失敗）
- 404（confused-deputy対策による拒否、プライベートチャンネル/DM非可視性、`MessageScopeGuard.assertInScope()` の失敗、キック後のDMアクセス拒否）
- ログイン失敗（`PasswordService` によるハッシュ照合失敗。ユーザー不存在の場合もダミーハッシュ照合により同一の失敗ログとする）
- STOMP接続拒否（許可外Origin、JWT検証失敗、SUBSCRIBE/SEND default-denyによる拒否）

これらは単発では正常な運用の一部（誤操作・URL直叩き等）だが、**同一ユーザー/IPからの短時間の頻発は、権限探索やブルートフォース攻撃の兆候になり得る**ため、後述の監視項目（4節）で頻度ベースの異常検知観点を定義する。

### 1.4 ログに残さない情報（個人情報・機密情報の除外方針）

以下は**いかなるログレベルでも出力しない**。

| 送らない | 理由 |
|---|---|
| パスワード（平文・ハッシュ問わず） | 認証情報の漏洩防止 |
| JWT本体（`chatspace_token` Cookieの値） | トークン漏洩によるなりすまし防止 |
| メッセージ本文・添付ファイルの内容 | チャンネル/DMの内容がログ経由で権限外の閲覧者（ログ閲覧権限を持つ運用者を含む）に渡ることを避ける。特に通知本文プレビューは§3の「通知のスコープ漏洩防止」と同じ配慮が必要 |
| メールアドレス等の個人を特定しうる情報（ChatSpaceはメール認証を持たないため該当は限定的だが、表示名等のPIIに準ずる情報も同様に扱う） | 個人情報保護 |

ログに残してよい最小限の識別子は、**内部ユーザーID（UUID）・workspaceId・channelId・dmId・messageId** 等のリソース識別子に限定する。これらは本文を含まないため、ログ閲覧者に内容そのものを漏らさない。

**この方針を型レベルで担保している（フェーズ12）**: `AuditLogger` の各メソッドは識別子（UUID）・種別・理由コードのみを引数に取り、本文や認証情報を渡せる引数を持たない。`AuditLoggerRedactionTest` がリフレクションで引数名を検査し、`password`・`token`・`body`・`query` 等を含む引数が追加された時点でテストが失敗する。

ただし**引数名の検査だけでは、許可された引数に危険な値が入る経路は防げない**（レビュー指摘）。唯一の例外である `attemptedUserId`（§2で明示的に許可されている、攻撃者が制御できる入力）については、`AuditLogger#sanitizeAttemptedUserId` で制御文字の除去と長さの切り詰めを行い、`AccessLogFieldsIntegrationTest` が実際の値で検証している。

アクセスログでも同様に、`getRequestURI()` のみを記録し**クエリ文字列は記録しない**（検索クエリがユーザーの入力内容そのものであり、PIIに準ずるため）。

### 1.5 出力項目（アクセスログ共通）

| フィールド | 内容 |
|---|---|
| `requestId` | リクエスト単位のUUID。同一リクエストのアクセスログ・エラーログ・監査ログを突き合わせるキー |
| `method` | HTTPメソッド（STOMPの場合はフレームタイプ: CONNECT/SUBSCRIBE/SEND等） |
| `path` | リクエストパスまたはSTOMP宛先（クエリ文字列は除く） |
| `status` | レスポンスのHTTPステータス（STOMPの場合は許可/拒否の別） |
| `duration_ms` | 処理時間（ミリ秒） |
| `userId` | 認証済みユーザーの内部ID（未認証時は`null`） |
| `errorType` | エラークラス名（`UnauthorizedException`/`ForbiddenException`/`NotFoundException`/`ValidationException` 等） |

## 2. 監査ログ対象

以下は「オーナー限定操作の実行」「キック操作」「通知配信失敗」「STOMP接続拒否」等のセキュリティ関連イベントであり、通常のアクセスログとは別に、監査目的での参照・検索がしやすい形（専用のログフィールド・ログカテゴリ、または将来的な専用監査テーブルの検討対象）で記録する。

**実装状況（フェーズ12）**: 下表の全項目を `AuditLogger`（`com.chatspace.api.audit`）に実装済み。イベント種別は `auditEvent` フィールド（例: `MEMBER_KICKED`）で識別する。

> **下表の「記録項目」は実装のログフィールド名と一対一で対応させている。**運用時にこの表を見てログを検索するため、名前がずれていると「あるはずのフィールドで検索して見つからない」という形で調査を妨げる（レビュー指摘により、`attachmentId`→`storageKey` など計6箇所を実装に合わせて修正）。`AuditLogger` のフィールド名を変更する際は本表も必ず同時に更新すること。

> **「オーナー限定操作の拒否」だけは専用イベントを設けていない。** `requireOwner()` の失敗は `ForbiddenException` として `GlobalExceptionHandler` に到達し、`AUTHORIZATION_DENIED`（HTTPメソッド・パス・例外型・userId を含む）として一元的に記録される。パスから操作種別が判別できるため、専用イベントを別に出してもログ量が増えるだけで得られる情報が変わらないと判断した。

| 監査対象 | 記録タイミング | 記録項目（本文・PIIは含めない） |
|---|---|---|
| オーナー限定操作の実行 | チャンネル作成/削除、招待、キックが**成功**しコミットされた時点 | `auditEvent: OWNER_ACTION_SUCCEEDED`、`actorUserId`（実行者）、`workspaceId`、`action`（`CHANNEL_CREATE`/`CHANNEL_INVITE`/`CHANNEL_KICK`/`CHANNEL_DELETE`/`WORKSPACE_INVITE`/`WORKSPACE_KICK`）、`targetResourceId`（対象のチャンネルID・ユーザーID） |
| オーナー限定操作の拒否 | 一般メンバーが上記操作を試みて403になった時点 | **専用イベントは設けず**、`auditEvent: AUTHORIZATION_DENIED`（`userId`・`method`・`path`・`errorType`）として一元記録する（下の注記参照） |
| メンバー操作の実行 | チャンネルからの自主退出が成功しコミットされた時点。オーナーによる強制退出と区別するため別イベントにする | `auditEvent: MEMBER_ACTION_SUCCEEDED`、`actorUserId`、`workspaceId`、`action`（`CHANNEL_LEAVE`）、`targetResourceId`（チャンネルID） |
| キック操作（強制切断） | `WorkspaceMember`/`ChannelMember` 削除が**AFTER_COMMIT**で確定した時点 | `auditEvent: MEMBER_KICKED`、`targetUserId`（対象）、`closedSessionCount`（切断したWebSocketセッション数）。**実行者・ワークスペースは上記 `OWNER_ACTION_SUCCEEDED` 側に記録される**（強制切断はキック操作から非同期に走るイベントリスナーで行われ、実行者の文脈を持たないため）。`requestId` では紐付かないため、突き合わせは `targetUserId` と時刻で行う |
| キック処理のロールバック | トランザクションがコミットに至らず終わった場合（`AFTER_ROLLBACK`） | `auditEvent: MEMBER_KICK_ROLLED_BACK`、`targetUserId`。**強制切断が実施されなかったことを確認できるよう、通常のキック成功ログと別イベントにしている**（ロールバック時は `OWNER_ACTION_SUCCEEDED` も出ないため、実行者はアクセスログの `requestId` から辿る） |
| 通知配信失敗 | `RealtimeEventPublisher`経由の配信、または`/user/queue/events`へのプッシュが失敗した時点 | `auditEvent: NOTIFICATION_DELIVERY_FAILED`、`targetUserId`、`notificationType`、`reason`（例外クラス名。本文は含めない） |
| STOMP接続拒否 | 許可外Origin、JWT検証失敗によるハンドシェイク拒否 | `auditEvent: STOMP_HANDSHAKE_REJECTED`、`remoteAddress`、`origin`、`reason`（`missing_cookie`/`invalid_token`） |
| STOMP SUBSCRIBE/SEND拒否 | 非メンバーによるSUBSCRIBE拒否、`/topic/**`等への直接SEND拒否 | `auditEvent: STOMP_DESTINATION_DENIED`、`userId`、`command`（`SUBSCRIBE`/`SEND`）、`destination`、`reason`（例外クラス名） |
| 認証失敗 | ログイン失敗（ユーザー不存在・パスワード不一致いずれも同一扱い）。レート制限による拒否は `auditEvent: LOGIN_RATE_LIMITED` として別に記録する | `auditEvent: LOGIN_FAILED`、`attemptedUserId`（**未認証の攻撃者が完全に制御できる入力**のため、制御文字を除去し64文字で切り詰めて出力する。無加工だと改行によるログ行の偽装・巨大文字列によるログ肥大・ユーザーID欄への第三者PII混入が起こりうる。パスワードは含めない）、`remoteAddress` |
| 添付ファイルのライブ権限再チェック拒否 | アップロード済みファイルへのアクセスが403/404で拒否された時点 | `auditEvent: ATTACHMENT_ACCESS_DENIED`、`userId`、`storageKey`（URLに現れる保存名。`attachmentId` は記録していない）、`reason`（例外クラス名） |
| 検索リクエスト | **専用の監査イベントは未実装**（フェーズ12時点）。クエリ文字列はPIIに準ずるため記録しない方針は維持し、アクセスログの `path`・`status`・`durationMs` で代替する。専用イベントを追加する場合も、記録するのは `userId`・ヒット件数・`durationMs` に限ること | （未実装） |

## 4. Render環境でのログ確認方法（フェーズ12にて手順を確定）

**設定手順（本番デプロイ時に実施すること）**

1. Render の Web Service の環境変数に `LOG_STRUCTURED_FORMAT=logstash` を設定する（未設定だとJSONにならず、フィールド単位の検索ができない）
2. 必要に応じて `LOG_LEVEL` / `LOG_LEVEL_APP` を調整する（既定はいずれも `INFO`）
3. ダッシュボードの「Logs」タブで、`auditEvent` / `requestId` / `userId` / `errorType` を使って絞り込む

**検索例（監査観点ごとの入口）**

| 調べたいこと | 絞り込みキー |
|---|---|
| ログイン総当たりの兆候 | `auditEvent=LOGIN_FAILED`・`auditEvent=LOGIN_RATE_LIMITED` |
| 権限探索の兆候 | `auditEvent=AUTHORIZATION_DENIED`・`auditEvent=STOMP_DESTINATION_DENIED` を `userId` または `remoteAddress` で集計 |
| オーナー操作の追跡 | `auditEvent=OWNER_ACTION_SUCCEEDED` を `workspaceId` で絞る（自主退出は `MEMBER_ACTION_SUCCEEDED`） |
| 添付ファイルへのアクセス拒否 | `auditEvent=ATTACHMENT_ACCESS_DENIED` を `storageKey` または `userId` で絞る |
| キックと強制切断の対応確認 | `auditEvent=MEMBER_KICKED`（`closedSessionCount` を含む）と `auditEvent=MEMBER_KICK_ROLLED_BACK` |
| 特定リクエストの全ログ | `requestId` |

**実機での検証結果（2026-08-26、実際にデプロイ済みの`chatspace`サービスで確認）**

- `LOG_STRUCTURED_FORMAT=logstash` は Render Web Service の Environment に設定済み。Logs タブの実際の出力は想定通りJSON形式になっている。例:
  ```json
  {"@timestamp":"2026-08-25T22:01:18.593930497Z","@version":"1","message":"リクエストを処理しました。","logger_name":"ACCESS","thread_name":"http-nio-10000-exec-1","level":"INFO","level_value":20000,"requestId":"13449c82-1af2-4968-a642-6e59f5b4aa9a","method":"GET","path":"/health","status":200,"durationMs":3,"userId":null}
  ```
- Render ダッシュボードの Logs タブ検索で `requestId`・`auditEvent`（`LOGIN_FAILED`を実際に発生させて確認）とも絞り込みできることを確認した
- Render の Web Service は標準出力・標準エラー出力に書き出したログを自動的に収集し、Render ダッシュボードの「Logs」タブでリアルタイム表示・検索できる
- **保持期間**: Logs タブの日時範囲選択で「Last 7 Days」まで選択可能（無料プランでの実測）。ただし当該サービスは2026-08-23デプロイのため2026-08-26時点でまだ3日分しか実データが無く、7日境界での実際のローテーション（それより古いログが消えること自体）はまだ観測できていない
- デプロイ・再起動時にはインスタンスが入れ替わるため、直前のインスタンスのログは切り替え後に参照できなくなる可能性がある点に留意する（Render は「WebSocket接続にアイドルタイムアウトの固定値はないが、インスタンス入れ替え時に切断される」ことを公式ドキュメントで明記しており、ログについても同様の前提を置く）
- 構造化ログ（JSON形式、1.1節）を採用することで、Renderのログ検索機能でのフィールド単位の絞り込み（`userId`・`errorType`等）が可能になることを前提とした設計とする

### 4.1 外部ログ集約サービス(New Relic)への転送(2026-08-26、実機で設定・検証済み)

Renderの無料プランのログ保持期間が7日と短いため、RenderのLog Streams機能(ワークスペースの`Integrations > Observability`)を使い、New Relicへログを転送する設定を追加した。

**設定内容**

- 転送方式: syslog(TLS)、エンドポイントは`newrelic.syslog.nr-data.net:6514`(米国リージョン)
- 認証: New Relicのライセンスキーを、Renderの`Log Streams`設定画面の`Token`欄に入力(アプリの環境変数やソースコードには含めない。Render側が管理する設定値)
- 転送スコープ: **ワークスペース単位のデフォルト転送**のため、`chatspace`(Web Service)だけでなく`chatspace-db`(PostgreSQL)の接続ログも同じくNew Relicへ流れる。個別サービスの除外設定はRenderのPro プラン以上が必要(Hobby/Freeでは不可)。DBの接続ログは接続元ホスト/ポート・TLS情報程度でPIIを含まないため、この点は許容している
- 動作確認: New RelicのLogs画面で、構造化ログ(JSON)が`level`/`message`等のフィールドに正しくパースされて表示されることを確認した

**既知の限界(合格条件にはしない、正直に記録する)**

- **New Relicの無料プランでのログ保持期間も実測7日であり、Render単体の保持期間(7日)からの改善にはなっていない**。「無料プランでも最大30日保持できる」という情報も事前調査で見つかったが、実際に設定したアカウントの`Data management`画面ではLogsの保持日数は7日のままだった(延長UIも確認していない)
- したがって本転送設定の実質的な効果は「保持期間の延長」ではなく、「Render障害時・インスタンス入れ替え時に備えたセカンドコピー」「New Relic側の検索UI・アラート機能を使えるようにする」という点に限られる。長期(7日超)の監査ログが必要になった場合は、別途保持期間の長い外部サービスへの切り替えを検討する必要がある

## 5. 運用時の確認観点（フェーズ12「情報漏洩監査」対応）

`.plans/java-spring-boot-redesign.md` の実装フェーズ表におけるフェーズ12「仕上げ（… 情報漏洩監査）」に対応する観点を以下に整理する。これは §6のテスト設計書で保証する「実装時点での正しさ」とは別に、**運用開始後にログから事後的に検知・確認できるか**という観点である。

| 確認観点 | 具体的な確認方法 |
|---|---|
| DM/チャンネルアクセス判定で現在のワークスペースメンバーシップが再確認されているか | キック後に対象ユーザーのDM/チャンネルアクセスが403/404ログとして記録され続けていないか（＝キック後もアクセスが「成功」ログとして記録されていないか）を確認する |
| 通知の一覧・未読件数・既読化エンドポイント全てに同一スコープ条件が適用されているか | 同一ユーザー・同一時間帯で、一覧取得ログの件数と未読件数ログの件数に不整合がないかを確認する（3種のエンドポイントで異なる件数が返っている場合、スコープ条件の実装漏れの兆候） |
| スコープ絞り込みの複合条件がORでなくANDで結合されているか | 実装時のArchUnit/統合テスト（テスト設計書 AUTH-N06）で担保するが、運用ログ上は「キック済みユーザーが通知一覧を取得できている」形跡がないかを定期的にサンプル確認する |
| confused-deputy（URLスコープとリソースの実所属の一致確認） | `MessageScopeGuard` 拒否（404）ログの発生パターンを確認し、正当な操作が誤って404になっていないか（過剰ブロック）、逆に本来404であるべき操作が200/201になっていないかをテストログと突き合わせる |
| ソフトデリート対象クエリで `deletedAt IS NULL` 漏れがないか | 削除済みメッセージが検索結果・一覧に含まれていないかを定期的にサンプル確認する（ログからの検知は難しいため、主にテスト〈AUTH-N09〉と定期的な手動確認で担保する） |
| STOMP接続拒否・SUBSCRIBE/SEND拒否の頻発がないか | 2節の監査ログから、同一IPまたは同一ユーザーからの拒否イベントの頻度を確認し、権限探索・スキャンの兆候がないか確認する |
| キック操作のAFTER_COMMIT保証・ロールバック時の非切断 | キック成功ログと強制切断ログが常にペアで記録されていること、ロールバックログの場合は強制切断ログが存在しないことを確認する |

### 5.1 フェーズ12で実施した情報漏洩監査の結果

上表の観点について、**「運用開始後にログから事後的に検知・確認できるか」**という視点で実装を点検した結果を記録する。

**(a) 各観点に対応する監査イベントの有無**

| 確認観点 | 対応する監査イベント | 判定 |
|---|---|---|
| キック後にDM/チャンネルアクセスが拒否され続けているか | `AUTHORIZATION_DENIED`（`userId`・`path`・`errorType`）。キック自体は `MEMBER_KICKED` | ✅ 追跡可能 |
| 通知の一覧・未読件数・既読化に同一スコープ条件が適用されているか | 直接の専用ログは無い。アクセスログの `path` と `status` で3エンドポイントの呼び出しを突き合わせる | △ 間接的（実装の正しさは AUTH-N03〜N06 で担保） |
| スコープ条件が OR でなく AND で結合されているか | ログからの直接検知は不可 | △ テストで担保（AUTH-N06） |
| confused-deputy（URLスコープとリソース実所属の一致） | `AUTHORIZATION_DENIED` の `errorType=NotFoundException` の発生パターン | ✅ 追跡可能 |
| ソフトデリート漏れ（`deletedAt IS NULL`） | ログからの検知は困難 | △ テストで担保（AUTH-N09）。定期的な手動確認が必要 |
| STOMP接続拒否・SUBSCRIBE/SEND拒否の頻発 | `STOMP_HANDSHAKE_REJECTED`（`remoteAddress`・`origin`・`reason`）、`STOMP_DESTINATION_DENIED`（`userId`・`destination`） | ✅ 追跡可能 |
| キックのAFTER_COMMIT保証・ロールバック時の非切断 | `MEMBER_KICKED`（`closedSessionCount` 付き）と `MEMBER_KICK_ROLLED_BACK` を別イベントとして出し分け | ✅ 追跡可能 |

「△」の3項目は、**ログからの事後検知には本質的に向かない**（正常な応答と異常な応答がログ上は同じ形になる）。これらは実装時点の正しさを自動テストで担保する方式を継続し、運用側では定期的なサンプル確認で補う。この切り分け自体を監査の結論として記録する。

**(b) ログへの機密情報混入がないことの確認**

| 確認項目 | 結果 |
|---|---|
| アプリケーションコード中のログ出力箇所 | `AuditLogger`・`RequestLoggingFilter` 以外は `GlobalExceptionHandler` の想定外例外ログ1箇所のみ。例外スタックトレースのみでメッセージ本文は含まない |
| `System.out` / `printStackTrace` の残存 | なし |
| SQLログ（本文がSQLのパラメータとして出力される） | `show-sql: true` は **dev プロファイルのみ**。本番プロファイルでは無効のため、メッセージ本文がログに出ない |
| アクセスログのクエリ文字列 | `getRequestURI()` のみを記録し、検索クエリを含むクエリ文字列は記録しない |
| 監査ログの引数 | `AuditLoggerRedactionTest` が引数名をリフレクションで検査し、`password`・`token`・`body`・`query` 等を含む引数の追加を検出して失敗する |

**(c) 残課題**

- **7日境界での実際のログローテーションの確認**: Render・New Relicとも無料プランの保持期間は実測7日だが（§4・§4.1）、デプロイからまだ日数が浅く、「7日を過ぎたログが実際に消えること」自体はまだ観測できていない
- 拒否イベントの頻度に対する**アラート発報の閾値設定**は本書の対象外であり未実施。現時点では手動での確認を前提とする
