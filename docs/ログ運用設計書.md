# ChatSpace ログ運用設計書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki（Claude Code支援）
**対象:** Java/Spring Boot 再設計版（`apps/api`）

---

## 0. 位置づけ

ChatSpace はワークスペース／チャンネル単位で閲覧範囲が分かれるマルチテナント構成であり、CLAUDE.md が「認可の実装ミスが最大のリスク」「特にメッセージ検索と通知は、権限外のチャンネル/DMの内容を含めやすい」と明記している。本書はこのリスクを運用面から補完するため、認可拒否・認証失敗といったセキュリティ関連イベントを構造化ログとして記録し、フェーズ12の「情報漏洩監査」で確認すべき観点を整理するものである。

**対象範囲**: バックエンド（`apps/api`、Controller/Service/Repository/STOMPハンドラ）のログ。フロントエンド（ブラウザコンソール）は対象外。
**対象外**: 実際のアラート発報設定（閾値監視ツールの具体的な設定作業）。本書は設計であり、実装フェーズの進行に応じて随時更新する前提。

---

## 1. ログ方針

### 1.1 構造化ログの採用

すべてのログは構造化ログ（JSON形式）で出力することを推奨する。Spring Boot 標準の Logback + `logstash-logback-encoder` によるJSON出力、または SLF4J の `MDC`（Mapped Diagnostic Context）を用いたキー・バリュー付与のいずれかの方式を採用する（実装フェーズ〈フェーズ12〉着手時に確定する）。自由記述のテキストログではなく、`requestId`・`userId`・`errorType` 等を検索・集計可能なフィールドとして持たせることを最低要件とする。

### 1.2 ログレベル方針

| レベル | 用途 |
|---|---|
| `ERROR` | 未捕捉の例外（500系）。スタックトレースを含む |
| `WARN` | 想定内のエラー（4xx系: 401 未認証 / 403 Forbidden / 404 NotFound / 400 Validation）。特に**認可拒否（403/404の一部）・認証失敗（401、ログイン失敗）はセキュリティ関連イベントとして`WARN`以上で必ず記録する**（詳細は2節） |
| `INFO` | 正常系を含む全リクエストのアクセスログ、オーナー限定操作の実行結果、STOMP接続確立/切断、キック確定イベント |
| `DEBUG` | 開発環境のデフォルトレベル。詳細なデバッグ情報（SQLクエリ等） |

環境変数（例: `LOG_LEVEL`）で上書き可能とし、未設定時は本番 `INFO` ／開発 `DEBUG` とする。

### 1.3 認可拒否・認証失敗イベントのログ記録

以下のイベントは、通常のエラーハンドリング（4xxレスポンス）と独立して、**セキュリティ関連イベントとして識別可能な形で記録する**方針を取る（後述「2. 監査ログ対象」の実装方針）。

- 401（未認証アクセス）: `AuthenticationEntryPoint` 到達時
- 403（オーナー限定操作の拒否、`WorkspaceAuthorizationService.requireOwner()` 等の失敗）
- 404（confused-deputy対策による拒否、プライベートチャンネル/DM非可視性、`MessageScopeGuard.assertInScope()` の失敗、キック後のDMアクセス拒否）
- ログイン失敗（`PasswordService` によるハッシュ照合失敗。ユーザー不存在の場合もダミーハッシュ照合により同一の失敗ログとする）
- STOMP接続拒否（許可外Origin、JWT検証失敗、SUBSCRIBE/SEND default-denyによる拒否）

これらは単発では正常な運用の一部（誤操作・URL直叩き等）だが、**同一ユーザー/IPからの短時間の頻発は、権限探索やブルートフォース攻撃の兆候になり得る**ため、後述の監視項目（4節）で頻度ベースの異常検知観点を定義する。

### 1.4 ログに残さない情報（個人情報・機密情報の除外方針）

以下は**いかなるログレベルでも出力しない**。

| 送らない | 理由 |
|---|---|
| パスワード（平文・ハッシュ問わず） | 認証情報の漏洩防止 |
| JWT本体（`chatspace_token` Cookieの値） | トークン漏洩によるなりすまし防止 |
| メッセージ本文・添付ファイルの内容 | チャンネル/DMの内容がログ経由で権限外の閲覧者（ログ閲覧権限を持つ運用者を含む）に渡ることを避ける。特に通知本文プレビューは§3の「通知のスコープ漏洩防止」と同じ配慮が必要 |
| メールアドレス等の個人を特定しうる情報（ChatSpaceはメール認証を持たないため該当は限定的だが、表示名等のPIIに準ずる情報も同様に扱う） | 個人情報保護 |

ログに残してよい最小限の識別子は、**内部ユーザーID（UUID）・workspaceId・channelId・dmId・messageId** 等のリソース識別子に限定する。これらは本文を含まないため、ログ閲覧者に内容そのものを漏らさない。

### 1.5 出力項目（アクセスログ共通）

| フィールド | 内容 |
|---|---|
| `requestId` | リクエスト単位のUUID。同一リクエストのアクセスログ・エラーログ・監査ログを突き合わせるキー |
| `method` | HTTPメソッド（STOMPの場合はフレームタイプ: CONNECT/SUBSCRIBE/SEND等） |
| `path` | リクエストパスまたはSTOMP宛先（クエリ文字列は除く） |
| `status` | レスポンスのHTTPステータス（STOMPの場合は許可/拒否の別） |
| `duration_ms` | 処理時間（ミリ秒） |
| `userId` | 認証済みユーザーの内部ID（未認証時は`null`） |
| `errorType` | エラークラス名（`UnauthorizedException`/`ForbiddenException`/`NotFoundException`/`ValidationException` 等） |

## 2. 監査ログ対象

以下は「オーナー限定操作の実行」「キック操作」「通知配信失敗」「STOMP接続拒否」等のセキュリティ関連イベントであり、通常のアクセスログとは別に、監査目的での参照・検索がしやすい形（専用のログフィールド・ログカテゴリ、または将来的な専用監査テーブルの検討対象）で記録する。

| 監査対象 | 記録タイミング | 記録項目（本文・PIIは含めない） |
|---|---|---|
| オーナー限定操作の実行 | チャンネル作成/削除、招待、キックが**成功**した時点 | `actorUserId`（実行者）、`workspaceId`、`action`（種別）、対象リソースID（`channelId`/`targetUserId`等） |
| オーナー限定操作の拒否 | 一般メンバーが上記操作を試みて403になった時点 | `actorUserId`、`workspaceId`、`action`、`result: forbidden` |
| キック操作 | `WorkspaceMember`/`ChannelMember` 削除が**AFTER_COMMIT**で確定した時点（`.plans/java-spring-boot-redesign.md` §4のキック確定設計に対応） | `actorUserId`（オーナー）、`targetUserId`（対象）、`workspaceId`/`channelId`、切断したWebSocketセッション数 |
| キック処理のロールバック | トランザクションがコミットに至らず終わった場合 | `actorUserId`、`targetUserId`、`reason`（バリデーション失敗等）。**強制切断が実施されなかったことを確認できるよう、通常のキック成功ログと明確に区別する** |
| 通知配信失敗 | `RealtimeEventPublisher`経由の配信、または`/user/queue/events`へのプッシュが失敗した時点 | `targetUserId`、`notificationType`、失敗理由（本文は含めない） |
| STOMP接続拒否 | 許可外Origin、JWT検証失敗によるハンドシェイク拒否 | `remoteAddress`（可能な範囲で）、`origin`、`reason` |
| STOMP SUBSCRIBE/SEND拒否 | 非メンバーによるSUBSCRIBE拒否、`/topic/**`等への直接SEND拒否 | `userId`、宛先（`destination`）、`reason` |
| 認証失敗 | ログイン失敗（ユーザー不存在・パスワード不一致いずれも同一扱い） | `attemptedUserId`（ログイン試行に使われたユーザーID文字列。パスワードは含めない）、`remoteAddress` |
| 添付ファイルのライブ権限再チェック拒否 | アップロード済みファイルへのアクセスが403/404で拒否された時点 | `userId`、`attachmentId`、`reason` |
| 検索リクエスト | 通常は監査対象外だが、スコープ漏洩防止の検証観点としてクエリ文字列そのものはログに残さず、`userId`・ヒット件数のみ記録することを推奨（本文検索クエリはユーザーの入力内容そのものであり、PIIに準ずる扱いとする） | `userId`、ヒット件数、`durationMs` |

## 4. Render環境でのログ確認方法

デプロイ先として想定する Render（`.plans/java-spring-boot-redesign.md` の「デプロイ方針（Render想定）」章）では、Render公式のログ機能を利用する前提とする。

- Render の Web Service は標準出力・標準エラー出力に書き出したログを自動的に収集し、Render ダッシュボードの「Logs」タブでリアルタイム表示・検索できる（Render公式ドキュメントの一般的な仕様に基づく想定。実際のプラン・保持期間・検索機能の詳細は、Render の実インスタンスを用いた検証時〈フェーズ-2または12〉に確認し、本書に反映する）
- Render のログは一定期間（無料/Starterプランでは短期間、上位プランではより長期）保持された後にローテーションされるため、**長期監査が必要なイベント（キック操作、オーナー限定操作等）は、必要に応じて外部ログ集約サービスへの転送を検討する**（本書時点では未確定、フェーズ12で要否を再検討する既知の保留事項とする）
- デプロイ・再起動時にはインスタンスが入れ替わるため、直前のインスタンスのログは切り替え後に参照できなくなる可能性がある点に留意する（Render は「WebSocket接続にアイドルタイムアウトの固定値はないが、インスタンス入れ替え時に切断される」ことを公式ドキュメントで明記しており、ログについても同様の前提を置く）
- 構造化ログ（JSON形式、1.1節）を採用することで、Renderのログ検索機能でのフィールド単位の絞り込み（`userId`・`errorType`等）が可能になることを前提とした設計とする

## 5. 運用時の確認観点（フェーズ12「情報漏洩監査」対応）

`.plans/java-spring-boot-redesign.md` の実装フェーズ表におけるフェーズ12「仕上げ（… 情報漏洩監査）」に対応する観点を以下に整理する。これは §6のテスト設計書で保証する「実装時点での正しさ」とは別に、**運用開始後にログから事後的に検知・確認できるか**という観点である。

| 確認観点 | 具体的な確認方法 |
|---|---|
| DM/チャンネルアクセス判定で現在のワークスペースメンバーシップが再確認されているか | キック後に対象ユーザーのDM/チャンネルアクセスが403/404ログとして記録され続けていないか（＝キック後もアクセスが「成功」ログとして記録されていないか）を確認する |
| 通知の一覧・未読件数・既読化エンドポイント全てに同一スコープ条件が適用されているか | 同一ユーザー・同一時間帯で、一覧取得ログの件数と未読件数ログの件数に不整合がないかを確認する（3種のエンドポイントで異なる件数が返っている場合、スコープ条件の実装漏れの兆候） |
| スコープ絞り込みの複合条件がORでなくANDで結合されているか | 実装時のArchUnit/統合テスト（テスト設計書 AUTH-N06）で担保するが、運用ログ上は「キック済みユーザーが通知一覧を取得できている」形跡がないかを定期的にサンプル確認する |
| confused-deputy（URLスコープとリソースの実所属の一致確認） | `MessageScopeGuard` 拒否（404）ログの発生パターンを確認し、正当な操作が誤って404になっていないか（過剰ブロック）、逆に本来404であるべき操作が200/201になっていないかをテストログと突き合わせる |
| ソフトデリート対象クエリで `deletedAt IS NULL` 漏れがないか | 削除済みメッセージが検索結果・一覧に含まれていないかを定期的にサンプル確認する（ログからの検知は難しいため、主にテスト〈AUTH-N09〉と定期的な手動確認で担保する） |
| STOMP接続拒否・SUBSCRIBE/SEND拒否の頻発がないか | 2節の監査ログから、同一IPまたは同一ユーザーからの拒否イベントの頻度を確認し、権限探索・スキャンの兆候がないか確認する |
| キック操作のAFTER_COMMIT保証・ロールバック時の非切断 | キック成功ログと強制切断ログが常にペアで記録されていること、ロールバックログの場合は強制切断ログが存在しないことを確認する |

## 6. 今後の継続方針

- フェーズ0-11で機能追加のたびに、本書2節（監査ログ対象）・5節（確認観点）に該当項目があれば追記する

- 外部ログ集約サービスの導入を決定した場合、3節・4節を更新する
