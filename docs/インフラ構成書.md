## 1. インフラ概要

### 設計方針

- **フェーズ0〜12は単一インスタンス前提で完結させる**。STOMP は Spring 標準のシンプルブローカー(インメモリ)を使い、キック時の強制切断もローカルの `SessionRegistry` から直接 `WebSocketSession.close()` するだけで完結させる。RabbitMQ・Redis はこの範囲では使わない
- **デプロイ先は Render(1インスタンス構成)を想定する**。Render は「永続ディスクと複数インスタンスが排他」という制約を持つため、単一インスタンス構成の設計方針と自然に噛み合う(詳細は4節・8節)
- 添付ファイルはローカルディスク(Render Disk)への保存で完結させる。S3/MinIO 化は行わない(フェーズ0-12の範囲)
- 検索は PostgreSQL の `pg_trgm` 拡張 + `ILIKE`。Render が `pg_bigm` を公式サポートしないための選択(2節・7節参照)
- **水平スケール対応(RabbitMQ 外部ブローカーリレー・Redis 共有プレゼンス・キック通知配送の outbox 化・共有アップロードボリューム)はフェーズ13として独立させ、任意の学習発展フェーズと位置づける**。プロジェクトとしての完成・機能同等性チェックリストの達成にはフェーズ13は不要
- バックエンドのアーキテクチャは、ドメイン機能別のパッケージ分割(feature-vertical)と、各パッケージ内部での3層アーキテクチャ(プレゼンテーション層/ビジネスロジック層/データアクセス層)の責務分離を両立させる(2節のアーキテクチャ図参照)

    │  │      *AuthorizationService.java,             │
    │  │      MessageScopeGuard.java                  │

    │  │          ▼                                  │
    │  │  [データアクセス層] *Repository.java(Spring     │

    │  └───────────────────────────────────────────┘
    │
    │  ローカルディスク(Render Disk) ── 添付ファイル保存(chatspace.upload-dir)

※1 フロントエンド(`apps/web`)の配信方式(Spring Boot からの静的配信に統合するか、Render の別サービス〔Static Site 等〕として分離するか)は本ドキュメント作成時点で**未定**。フェーズ9(フロントエンド実装)またはデプロイ準備時に確定する。

ArchUnit により、上記3層アーキテクチャの依存方向(Controller→Repository層飛ばし禁止、Service層へのHTTP概念混入禁止、エンティティのController戻り値直接使用禁止)を自動テストとして強制する(`./gradlew build` に含まれる)。

### 2.2 水平スケール構成(フェーズ13・任意、Render上で実施する場合)

CLAUDE.md の既知制約(プレゼンス管理が単一プロセス前提)を本格的に解消したい場合、または学習目的で分散システム構成を経験したい場合にのみ実施する独立フェーズ。**フェーズ0-12の完了・機能同等性チェックリストの達成には不要。**

```
[ブラウザ(複数)]
    │
    ▼
[Render Web Service インスタンス#1] ←→ [Render Web Service インスタンス#2]
    │         │                              │        │
    │         └──────────────┬───────────────┘        │
    │                        ▼                         │
    │              [RabbitMQ(外部ブローカーリレー)]        │
    │              Render管理外(Private Service自前 or   │
    │              CloudAMQP等の外部サービス)              │
    │                                                    │
    ├── [Redis(Render Key Value)] 共有プレゼンス ──────────┤
    │
    ├── [オブジェクトストレージ(S3 / Cloudflare R2 等)] ─────┤
    │     添付ファイル(Render Diskは複数インスタンスと排他のため使用不可)
    │
    └──────────────────┬─────────────────────────────┘
                        ▼
              [Render PostgreSQL]
              + session_eviction_outbox テーブル(キック通知配送のoutboxパターン用)
```

水平スケール化に伴う主な変更点:

- STOMP ブローカーを Spring シンプルブローカーから **RabbitMQ 外部ブローカーリレー**(`enableStompBrokerRelay`)に切替
- プレゼンス管理をローカル `Map` から **Redis 共有プレゼンス**に切替
- キック時の強制切断を、単一インスタンス内の直接メソッド呼び出しから、**永続 outboxパターン(`session_eviction_outbox`テーブル + `SELECT ... FOR UPDATE SKIP LOCKED` による専用ディスパッチャ)+ Redis Pub/Sub `session-evict` チャネル**によるインスタンス横断の通知機構へ拡張。加えて、各インスタンスが定期(例: 30秒間隔)にローカルセッションのメンバーシップを再検証するバックグラウンドジョブを二次防御として持つ
- 添付ファイルを共有永続ボリューム化する必要があるが、**Render 上でフェーズ13を実施する場合はディスクと複数インスタンスが排他のためこの構成が取れず、オブジェクトストレージ(S3/R2等)化が必須になる**(ローカル docker-compose 上で名前付きボリュームを使って検証するだけであれば見直し不要)
- `/user/queue/events` の複数インスタンス配送機構(`userDestinationBroadcast`等の要否)は、この計画書時点では確定させず、**フェーズ13着手時に実際のSTOMPフレームを観測しながら再検証する**方針

## 4. サービス構成(本番、Render想定)

### 4.1 Render Web Service

| 項目 | 内容 |
|------|------|
| 用途 | Spring Boot アプリ(`apps/api`)のホスティング |
| インスタンス数 | **1(フェーズ0-12は水平スケールしない)** |
| 永続ディスク | Render Disk を1個アタッチし、`chatspace.upload-dir`(添付ファイル保存先)をマウント。**Render Diskは有料インスタンスでのみ利用可能なため、本番構成のWeb Serviceは無料インスタンスにはできない**(詳細・費用への影響は§7参照) |
| WebSocket | Render の Web Service はパブリックインターネットからの WebSocket 接続を受付可能(公式ドキュメントで確認済み)。**アイドルタイムアウトは固定値なし**だが、デプロイ・再起動時に強制切断される。クライアント側(`@stomp/stompjs`)の `heartbeatIncoming`/`heartbeatOutgoing` による定期 keepalive と、指数バックオフ付き再接続ロジックで対応する |
| ゼロダウンタイムデプロイ | **ディスクをアタッチするため無効**(旧インスタンス停止後に新インスタンスを起動する挙動になる) |

### 4.2 Render PostgreSQL

| 項目 | 内容 |
|------|------|
| 用途 | アプリケーションデータの永続化 |
| 拡張 | `pg_trgm` が PostgreSQL 13以降のサポート対象拡張として公式に確認済み(2026-08-15 時点のフェーズ-2調査)。`pg_bigm` はサポート対象拡張一覧に存在しない |
| 無料枠の制約 | **30日で失効**するため、継続運用するなら有料プランへの切替が必要 |
| マイグレーション | Flyway。アプリ起動時に自動適用(`spring.flyway.enabled=true`) |

### 4.3 Render Disk と水平スケールの排他制約

- Render の公式ドキュメントは「サービスにディスクがアタッチされている場合、複数インスタンスにスケールできない(`You can't scale a service to multiple instances if it has a disk attached`)」「永続ディスクは単一のサービスインスタンスからのみ、実行時にのみアクセス可能」と明記している。Render には EFS/NFS 相当の共有ファイルシステム製品も存在しない
- **この制約は本プロジェクトの単一インスタンス方針(フェーズ0-12)と整合する**: 1インスタンス + Render Disk で、添付ファイルのローカルディスク保存をそのまま実現できる。設計変更は不要
- **フェーズ13(水平スケール)を Render 上で実施する場合は上記前提が崩れる**: 複数インスタンス化するとディスクが使えなくなるため、添付ファイルはオブジェクトストレージ(S3 / Cloudflare R2 等)へ移す必要がある。これは通常時は不採用としている選択肢だが、**フェーズ13 を Render 上で実施する場合に限り見直す**(ローカル docker-compose 上で共有ボリュームを使って検証するだけであれば見直し不要)

## 5. 環境変数

| 変数名 | 設定先 | 説明 |
|--------|--------|------|
| `JWT_SECRET` | Render 環境変数(Secret管理) | JWT(HS256)の署名鍵。ローテーションなし |
| `DATABASE_URL` | Render 環境変数(PostgreSQL連携で自動設定) | **要変換(レビュー指摘により追加)**: Render が自動設定する `DATABASE_URL` は `postgresql://user:password@host:port/dbname` 形式だが、Spring の `DataSource`(`spring.datasource.url`)は `jdbc:postgresql://host:port/dbname` 形式の JDBC URL を要求し、ユーザー名・パスワードも別プロパティ(`spring.datasource.username`/`password`)で渡す必要がある。そのままでは互換性が無いため、起動時に変換する仕組み(例: `@PostConstruct`で`DATABASE_URL`をパースして`DataSourceProperties`に設定するBean、またはRender側で`spring.datasource.url`等の個別環境変数を別途手動設定する方式)のいずれかを採用することをフェーズ0で決定する |
| `WEB_ORIGIN` | Render 環境変数 | `StompEndpointRegistry.setAllowedOriginPatterns(...)` で使用する許可オリジン。本番ではワイルドカード `*` を使わない |
| `UPLOAD_DIR`(`chatspace.upload-dir`) | Render 環境変数 | 添付ファイルの保存先ディレクトリ。Render Disk のマウントパスを指す |
| `SPRING_PROFILES_ACTIVE` | Render 環境変数 | 本番プロファイル(`prod` 等)を指定。`dev,seed` プロファイルはローカル専用 |
| `MAX_ATTACHMENT_SIZE_BYTES` 相当 | `application.yml`(`spring.servlet.multipart.max-file-size`/`max-request-size`) | プロトタイプと同じ 25MB。環境変数化するかは実装時に判断(未定) |

> Cookie 属性(`HttpOnly; SameSite=Lax; Secure`〔本番のみ〕)はコード側の設定であり環境変数化はしない。`Secure` 属性の有効/無効はアクティブプロファイルで切り替える想定。

## 6. デプロイ手順(概要)

1. Render で PostgreSQL インスタンスを作成する(フェーズ-2で確認したバージョン・拡張〔`pg_trgm`〕が利用可能なことを事前確認)
2. Render で Web Service を作成し、GitHub リポジトリ(`apps/api`)と連携する
3. ビルドコマンド(`./gradlew bootJar` 等)・起動コマンド(`java -jar build/libs/*.jar`)を設定する(具体的なビルド方式はフェーズ0以降で確定)
4. Render Disk をアタッチし、`UPLOAD_DIR` のマウントパスを設定する
5. 環境変数(5節の一覧)を設定する。`JWT_SECRET` は Render のシークレット管理機能を使う
6. デプロイ実行。アプリ起動時に Flyway マイグレーションが自動適用され、`CREATE EXTENSION IF NOT EXISTS pg_trgm` を含むベースラインマイグレーションが反映される
7. フロントエンド(`apps/web`)の配信方式は未定(2.1節参照)のため、確定後に本節を更新する
8. デプロイ後、許可外 Origin からの `/ws` への CONNECT/SEND が拒否されること、WebSocket 接続が確立できることを実機で確認する(フェーズ-2 で確認済みの Render WebSocket サポート挙動の再確認)

## 7. コスト概算

| 項目 | 内容 |
|------|------|
| Render PostgreSQL | 無料枠は **30日で失効**。継続運用するなら有料プランが必要 |
| Render Web Service | **(レビュー指摘により修正)** Render の無料 Web Service インスタンスには永続ディスクをアタッチできない(Render公式: 永続ディスクは有料インスタンスのみの機能)。§4.1・§4.3 で添付ファイル保存に Render Disk のアタッチを前提としているため、**本番構成では最低でも有料プラン(Starter以上)の Web Service が必須**であり、無料インスタンスでは運用できない。**無料インスタンスのまま運用する場合は Render Disk をアタッチできないため、添付ファイルは永続化されない(インスタンス再起動・再デプロイのたびに消える)**。学習目的で無料枠のみを使いたい場合は、この制約を許容するか、フェーズ13を待たずにオブジェクトストレージ化するかを別途判断すること |
| スケール時の課金(フェーズ13実施時) | インスタンス数に比例(秒単位按分)。検証時のみ2台に上げて戻す運用が可能 |
| RabbitMQ(フェーズ13実施時) | Render にマネージド RabbitMQ は無い。Private Service として自前で立てるか、CloudAMQP 等の外部サービスを利用する必要がある |
| Redis 相当(フェーズ13実施時) | Render Key Value(無料枠 25MB・永続化なし)があり、プレゼンス用途であれば無料枠で足りる見込み |
| オブジェクトストレージ(フェーズ13をRender上で実施する場合) | S3 / Cloudflare R2 等の別サービス費用が発生(未定) |

> 上記の各種プラン・価格は変動しうるため、実際に契約する時点で Render の公式価格ページで再確認すること。具体的な月額費用は本ドキュメント作成時点では**未定**。

### 7.1 添付ファイルのオブジェクトストレージ化(フェーズ13、実施済み)

Render Disk が有料プラン必須であることに加え、無料インスタンス運用時はディスクをアタッチできず再デプロイのたびに
添付ファイルが消えるため、**添付ファイルの保存先を Cloudflare R2(S3互換オブジェクトストレージ)へ移した**。

- **実現方式**: `apps/api/src/main/java/com/chatspace/api/upload/AttachmentStorage.java` インターフェースを新設し、
  `LocalDiskAttachmentStorage`(既定、開発/テスト用)と `S3AttachmentStorage`(`chatspace.storage.type=s3`、本番用)を
  `@ConditionalOnProperty`で切り替える。`UploadService` は`AttachmentStorage`のみに依存し、保存先の実装詳細を知らない
- **認可への影響を避ける設計**: `UploadService.serve()`のライブ権限再チェック(`authorizeServe`)自体は無変更。
  ただし「存在確認」(`exists()`、本文を転送しない)と「本文取得」(`load()`)を分離し、**本文取得はライブ権限再チェックに
  成功した後にのみ行う**。認可拒否されるリクエストのたびにオブジェクトストレージへ本文転送させないため
  (認証済みだが無権限のユーザーによる連続リクエストでR2転送量・ヒープを消費させないための対策)
- **バケットは非公開のまま**。プライベートチャンネル・DMの添付は参加者以外に見えてはならず(AUTH-N07)、配信は
  必ず `GET /uploads/{storageKey}` を経由させてライブ権限再チェックを維持する。署名付きURL方式は不採用
  (前段のライブ権限再チェックを迂回できる経路を作らないため)
- **R2接続設定**: `S3StorageConfig`(`@ConditionalOnProperty`で`type=s3`のときのみ有効)がAWS SDK v2の`S3Client`を
  構築する。R2はS3互換APIだが path-style アドレッシング(`pathStyleAccessEnabled(true)`)と
  `chunkedEncodingEnabled(false)`(署名不一致対策、Cloudflare公式のAWS SDK for Java例に準拠)が必要
- **テストへの影響**: 既存の統合テスト(`UploadAuthorizationTest`)は`chatspace.storage.type`未設定→既定の
  `LocalDiskAttachmentStorage`が使われるため無改修のまま通る。`S3AttachmentStorage`は単体テスト
  (`S3AttachmentStorageTest`、Mockitoで`S3Client`をモック)で検証する
- **費用**: Render Disk が不要になる代わりにR2側の費用が発生する(無料枠の範囲内で収まる想定)

## 8. セキュリティ方針

### 8.1 認証

| 項目 | 方針 |
|------|------|
| JWT | HS256、`JWT_SECRET` 環境変数で署名、有効期限7日。実装は Nimbus JOSE+JWT(`com.nimbusds:nimbus-jose-jwt`)。Spring Security の OAuth2 Resource Server 自動構成は不採用(自前でトークンを発行する用途に対して不要な依存が増えるため) |
| パスワード | bcrypt(コストファクタ12)。ユーザー不在時も固定ダミーハッシュに対して比較処理を実行し、応答時間差からユーザー存在有無を推測できないようにする |
| Cookie | 名前 `chatspace_token`、`HttpOnly; SameSite=Lax; Secure`(本番のみ)、有効期限7日・`path=/` |
| ログアウト | Cookie の削除のみ。サーバー側でのトークン失効・リフレッシュトークンの仕組みは持たない(既知の設計選択) |
| REST 認証 | `JwtAuthenticationFilter` が Cookie 検証を行うが、失敗時に即401は返さず `SecurityContext` を空のまま後続へ委譲する。401判定自体は Spring Security の `AuthenticationEntryPoint` が行う(詳細は `docs/シーケンス図.md` 2節) |
| WebSocket 認証 | STOMP CONNECT ではなく **ハンドシェイク時**に Cookie の JWT を検証(`HandshakeInterceptor` + `determineUser()`)。実体は REST と同じ `JwtService` を使用 |

### 8.2 Origin / CSRF

| 項目 | 方針 |
|------|------|
| REST の CSRF | Cookie 認証 + `SameSite=Lax` を主たる防御とし、Spring Security の CSRF 保護は明示的に無効化する。前提として、フロントエンドとバックエンドが**同一 registrable domain(eTLD+1)** であることが必要(ローカル開発の `localhost` はこの前提を満たす) |
| 本番でフロント/APIが別ドメインになる場合 | `SameSite` の "site" 判定はポート・サブドメインを区別しないため上記前提が崩れる。その場合は `SameSite=None; Secure` + 別途 CSRF トークン方式へ切り替える判断が必要。**本番のドメイン構成が決まった時点で要再確認**(フェーズ12のチェック項目) |
| `/ws` の Origin 検証 | `StompEndpointRegistry.setAllowedOriginPatterns(...)` で `WEB_ORIGIN` 由来の許可オリジンのみ設定し、ワイルドカード `*` は本番では使わない。WebSocket ハンドシェイクは `fetch` と異なり Cookie が自動送信されるため、Origin 検証がこの経路唯一の CSRF 相当の防御となる |
| STOMP CONNECT の CSRF | Spring Security の WebSocket メッセージセキュリティの既定動作(CONNECTフレームへのCSRFトークン要求)は無効化し、Origin 許可リストを主たる防御とする。許可外 Origin からの CONNECT/SEND が拒否されることを統合テストで確認する(フェーズ4) |

#### 8.2.1 本番ドメイン確定時の判断手順(フェーズ12にて整理、実装は保留)

本番のドメイン構成が未定のため、フェーズ12では**判断基準の文書化に留め、コードは変更していない**。
「別ドメインになるかもしれない」という想定でCSRFトークン方式を先行実装すると、同一ドメイン構成に
落ち着いた場合に使われないコードと余分なテストが恒久的に残るため、必要になってから実装する方針とした。

公開時に以下の表で分岐を判断すること。

| 本番のドメイン構成 | 例 | 必要な作業 |
|---|---|---|
| フロントとAPIが**同一 registrable domain(eTLD+1)** | `chatspace.example.com` と `api.chatspace.example.com` | **作業なし**。現行の `SameSite=Lax` のままでよい。`WEB_ORIGIN` を本番ドメインに設定し、`COOKIE_SECURE=true` にするだけ |
| フロントとAPIが**別 registrable domain** | `chatspace.example.com` と `chatspace-api.net` | ① `AuthController` の Cookie を `SameSite=None; Secure` へ変更 ② CSRFトークン方式(double-submit cookie 等)を導入 ③ `SecurityConfig` の CORS 許可オリジンを見直し ④ CSRFトークン検証の統合テストを追加 |

> **誤設定が無防備な公開に繋がらない構造になっている**点を補足しておく。別ドメイン構成で `SameSite=Lax` の
> まま公開した場合、CookieがAPIへ送信されないため**そもそもログインできない**。「防御が外れたことに気付かない
> まま運用が始まる」形の事故は起きない。

### 8.3 STOMP SEND/SUBSCRIBE の default-deny

| ルール | 内容 |
|--------|------|
| SEND | `/app/**` 宛のみ許可し、認証済みユーザーに限定。`/topic/**`・`/queue/**`・`/user/**` へのクライアント発 SEND は常に拒否 |
| SUBSCRIBE | `/user/queue/events` は認証済みユーザーであれば常に許可(catch-allのdenyより前に評価)。チャンネル/DM/ワークスペーストピックは既存の認可チェック(メンバーシップ検証)を適用。それ以外は default-deny |
| CONNECT/DISCONNECT/UNSUBSCRIBE/HEARTBEAT | `permitAll()` として default-deny の対象から明示的に除外(`anyMessage().denyAll()` を素直に書くとSTOMP接続自体が確立しなくなるため) |
| Principal解決 | ハンドシェイク時に設定する Principal の `getName()` を、`convertAndSendToUser()` 呼び出し時の内部ユーザーIDと一致させる。不一致だと通知が例外もなく静かに届かなくなる |

### 8.4 認可

- `@PreAuthorize` 等の宣言的ロールチェックではなく、サービス層のヘルパークラス(`WorkspaceAuthorizationService`・`ChannelAuthorizationService`・`DmAuthorizationService`・`MessageScopeGuard`)でリソース単位の認可を行う
- **404-not-403方針**: 存在自体を隠すべきリソース(非参加のプライベートチャンネル/DM)は404、閲覧可能だが操作不可なものは403
- **DM権限**: 参加者チェックに加え、呼び出し時点で有効な `WorkspaceMember` であることを必須条件とする(ワークスペースキック後もDMの既知IDでアクセスが残り続けるギャップへの対策)
- **通知のスコープ再チェック**: 一覧取得・未読件数・個別既読・全件既読の全エンドポイントで、channelId/dmId/workspaceIdに対する現在のライブなメンバーシップをAND結合で再検証する(詳細は`docs/シーケンス図.md` 7節)
- **メンション**: `MentionResolver`および候補取得APIは、その時点のライブなチャンネルメンバーシップとのみ突合する

### 8.5 添付ファイル

- マジックバイト判定(PNG/JPEG/GIF/WEBP/MP4/WEBM の固定シグネチャ)によりクライアント指定の Content-Type を信用しない
- 保存ファイル名は `UUID.randomUUID()` + 検出MIMEから決めた拡張子
- 配信時は `storageKey` を正規表現検証後、パス正規化して保存ディレクトリ配下であることを再確認(パストラバーサル対策)
- 取得の都度、所属メッセージのチャンネル/DMに対するライブな権限チェックを再実行(アップロード時点のみのチェックにしない)
- アップロードサイズ上限は多層防御: `spring.servlet.multipart.max-file-size`/`max-request-size`(25MB、**必須**)+ サービス層での `MultipartFile#getSize()` 再確認(**必須**)

### 8.6 マークダウン

- HTML生成はクライアント側のみ(`marked` + `DOMPurify`、`img`タグ除外)で行い、バックエンドは入力値のバリデーション(長さ等)のみ担当する

### 10.1 Render環境でのログ確認方法

- アプリは標準出力にログを書き、Render の Web Service がそれを収集する。ダッシュボードの「Logs」タブで
  リアルタイム表示・検索ができる
- **本番では環境変数 `LOG_STRUCTURED_FORMAT=logstash` を設定する**こと。JSON形式で出力されるようになり、
  `requestId`・`userId`・`auditEvent`・`errorType` 等をフィールド単位で絞り込めるようになる。未設定の場合は
  人間可読な行形式のままで、フィールド検索ができない
- ログレベルは `LOG_LEVEL`(既定 `INFO`)・`LOG_LEVEL_APP`(`com.chatspace` 配下、既定 `INFO`)で調整する
- **保持期間の制約**: Render のログはプランに応じた期間でローテーションされ、デプロイ・再起動でインスタンスが
  入れ替わると直前のログを追えなくなる場合がある。キック操作・オーナー限定操作といった長期監査が必要な
  イベントについては、外部ログ集約サービスへの転送が必要かを運用開始後に判断する(現時点では未導入)

なお、単一インスタンス構成(フェーズ0-12)では「コミット直後にプロセスが落ちたらキック通知が飛ばないのでは」という懸念に対し、**プロセスが落ちれば同じメモリ上にある WebSocket セッション自体も同時に消える**ため、`@TransactionalEventListener(AFTER_COMMIT)` のみで整合性が完全に閉じる(詳細は`docs/シーケンス図.md` 6節)。この前提が崩れるのは複数インスタンス構成(フェーズ13)の場合であり、それが outbox パターンを要する理由である。
