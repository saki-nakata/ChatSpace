## 1. インフラ概要

### 設計方針

- **単一インスタンス前提で完結させる**。STOMP は Spring 標準のシンプルブローカー(インメモリ)を使い、キック時の強制切断もローカルの `SessionRegistry` から直接 `WebSocketSession.close()` するだけで完結させる。RabbitMQ・Redis は使わない。水平スケール対応は検討したが、Renderが1インスタンス運用でマネージドRabbitMQも無く本番で動かす先が無いため、実施しないことが確定している
- **デプロイ先は Render(1インスタンス構成、Web Service 1つ)。フロントエンド(`apps/web`)はビルド成果物を Spring Boot に同梱し、同一オリジンで配信する**(フェーズ14で確定。詳細は2.1節・4節)
- 添付ファイルは Cloudflare R2(S3互換オブジェクトストレージ)への保存で完結させる(フェーズ13で実施済み。詳細は7.1節)。Render Diskは使用しない
- 検索は PostgreSQL の `pg_trgm` 拡張 + `ILIKE`。Render が `pg_bigm` を公式サポートしないための選択(2節・7節参照)
- バックエンドのアーキテクチャは、ドメイン機能別のパッケージ分割(feature-vertical)と、各パッケージ内部での3層アーキテクチャ(プレゼンテーション層/ビジネスロジック層/データアクセス層)の責務分離を両立させる(2節のアーキテクチャ図参照)

## 2. アーキテクチャ図

### 2.1 本番構成(単一インスタンス、フロント同梱配信)

```
[ブラウザ]
    │  HTTPS
    ▼
[Render Web Service(Spring Boot + React静的配信、フェーズ14で確定)]
    │
    │  ┌───────────────────────────────────────────┐
    │  │  apps/api   │
    │  │                                             │
    │  │  [プレゼンテーション層] *Controller.java       │
    │  │          │ 呼び出しのみ・逆方向依存禁止           │
    │  │          ▼                                  │
    │  │  [ビジネスロジック層] *Service.java,           │
    │  │      *AuthorizationService.java,             │
    │  │      MessageScopeGuard.java                  │
    │  │          │ 呼び出しのみ・逆方向依存禁止           │
    │  │          ▼                                  │
    │  │  [データアクセス層] *Repository.java(Spring     │
    │  │      Data JPA), Entity                        │
    │  │                                             │
    │  │  [realtime/] StompDestinations,               │
    │  │      SessionRegistry, RealtimeEventPublisher, │
    │  │      WebSocketHandlerDecoratorFactory          │
    │  │      (STOMPシンプルブローカー、インメモリ)          │
    │  └───────────────────────────────────────────┘
    │
    │  Cloudflare R2(S3互換) ── 添付ファイル保存(フェーズ13、7.1節参照)
    │
    ▼  Spring Data JPA/Hibernate(Flywayでマイグレーション管理)
[Render PostgreSQL]
    - pg_trgm 拡張(message検索用GINインデックス)
```

`apps/web` のビルド成果物(`dist/`)はDockerマルチステージビルドで `apps/api` の静的リソースディレクトリへ同梱し、
同一オリジンで配信する(別サービスへの分離は不採用。理由は`*.onrender.com`がPublic Suffix Listに載っており、
サービスを分けると別サイト扱いになって`SameSite=Lax`のCookieが送られなくなるため)。SPAのクライアント側ルート
(`/login`・`/signup`・`/w/**`)は`SpaFallbackController`で`index.html`にフォワードする(実装計画書/phase14.md参照)。

ArchUnit により、上記3層アーキテクチャの依存方向(Controller→Repository層飛ばし禁止、Service層へのHTTP概念混入禁止、エンティティのController戻り値直接使用禁止)を自動テストとして強制する(`./gradlew build` に含まれる)。

## 4. サービス構成(本番、Render想定)

### 4.1 Render Web Service

| 項目 | 内容 |
|------|------|
| 用途 | Spring Boot アプリ(`apps/api`。フロントエンド`apps/web`のビルド成果物を同梱)のホスティング。Dockerfileでイメージをビルドする(リポジトリルート、実装計画書/phase14.md参照) |
| インスタンス数 | **1(水平スケール対応は実施しないことが確定)** |
| 永続ディスク | **使用しない**。添付ファイルはCloudflare R2(S3互換、フェーズ13・7.1節)に保存するため、Render Diskのアタッチは不要。**その結果、本番構成でも無料インスタンスで運用できる**(有料インスタンス必須だった旧方針から変更) |
| WebSocket | Render の Web Service はパブリックインターネットからの WebSocket 接続を受付可能(公式ドキュメントで確認済み)。**アイドルタイムアウトは固定値なし**だが、デプロイ・再起動時に強制切断される。クライアント側(`@stomp/stompjs`)の `heartbeatIncoming`/`heartbeatOutgoing` による定期 keepalive と、指数バックオフ付き再接続ロジックで対応する |
| ゼロダウンタイムデプロイ | ディスクをアタッチしないため有効(Renderの無料/Starterプランの制約に依存) |

### 4.2 Render PostgreSQL

| 項目 | 内容 |
|------|------|
| 用途 | アプリケーションデータの永続化 |
| 拡張 | `pg_trgm` が PostgreSQL 13以降のサポート対象拡張として公式に確認済み(2026-08-15 時点のフェーズ-2調査)。`pg_bigm` はサポート対象拡張一覧に存在しない |
| 無料枠の制約 | **30日で失効**するため、継続運用するなら有料プランへの切替が必要 |
| マイグレーション | Flyway。アプリ起動時に自動適用(`spring.flyway.enabled=true`) |

### 4.3 Render Diskを採用しなかった理由(経緯)

当初はRender Diskへの添付ファイル保存を検討していたが、以下の理由から不採用とし、Cloudflare R2(7.1節)へ切り替えた。

- Render公式ドキュメントによれば、Render Diskは有料インスタンスでのみ利用可能。無料インスタンスにアタッチできない
- 無料インスタンスのまま運用する場合、Render Diskが使えないため添付ファイルは永続化されず、再デプロイ・再起動のたびに消えてしまう
- 「サービスにディスクがアタッチされている場合、複数インスタンスにスケールできない」という制約もあるが、本プロジェクトは水平スケール対応を実施しないため、この制約自体は実害にならなかった。決め手になったのは上記の無料インスタンスとの非互換性

結果として、Render Diskを使わずCloudflare R2に統一したことで、有料インスタンスを前提とせず無料枠のままデプロイできるようになった(7節参照)。

| `WEB_ORIGIN` | Render 環境変数 | `StompEndpointRegistry.setAllowedOriginPatterns(...)`・REST側CORSで使用する許可オリジン。フロント同梱配信のため、実質的にRender Web Service自身のURL(例: `https://chatspace.onrender.com`)を設定する。本番ではワイルドカード`*`を使わない |
| `COOKIE_SECURE` | Render 環境変数 | `chatspace_token`Cookieの`Secure`属性。本番(HTTPS)では`true`にする。未設定時の既定は`false`(ローカル開発用) |

| `STORAGE_TYPE` | Render 環境変数 | `s3`を設定してCloudflare R2を使う(フェーズ13、7.1節)。未設定時の既定は`local` |
| `STORAGE_S3_BUCKET` / `STORAGE_S3_ENDPOINT` / `STORAGE_S3_REGION` / `STORAGE_S3_ACCESS_KEY_ID` / `STORAGE_S3_SECRET_ACCESS_KEY` | Render 環境変数(`STORAGE_TYPE=s3`のとき必須) | R2バケットの接続情報。R2はバケット限定の最小権限トークンを発行して使う |

## 6. デプロイ手順(概要、フェーズ14で確定)

前提: Cloudflare R2への移行(フェーズ13)が完了していること。R2移行前にデプロイ・CDを有効化すると、再デプロイのたびに添付ファイルが消える(実装計画書/phase13.md参照)。

1. R2バケットを作成し、バケット限定の最小権限APIトークンを発行する(非公開のまま。7.1節)
2. Render で PostgreSQL インスタンスを作成する(`pg_trgm`拡張が利用可能なことを事前確認)
3. Render で Web Service を作成し、GitHub リポジトリと連携する。ビルド方式は **Docker**(リポジトリルートの`Dockerfile`、実装計画書/phase14.md参照)を選択する。Render Diskはアタッチしない
4. 環境変数(5節の一覧)を設定する。`JWT_SECRET`はRenderのシークレット管理機能を使う。`DATABASE_URL_JDBC`等はRender PostgreSQLの個別接続情報から手動で組み立てる(5節参照)
5. Health Check Pathに`/health`を設定する
6. デプロイ実行。アプリ起動時に Flyway マイグレーションが自動適用され、`CREATE EXTENSION IF NOT EXISTS pg_trgm` を含むベースラインマイグレーションが反映される
7. デプロイ後、`https://<サービスURL>/`・`/login`にブラウザでアクセスしてSPAが表示されること、許可外Originからの`/ws`へのCONNECT/SENDが拒否されWebSocket接続が確立できることを実機で確認する
8. 上記の初回手動デプロイで所要時間・添付ファイルの保存/取得(R2経由)を確認できたら、GitHub Actions(`.github/workflows/release-ci.yml`)によるCD(`production`ブランチへのマージで自動デプロイ)を有効化する(実装計画書/phase14.md参照)

### 7.1 添付ファイルのオブジェクトストレージ化(フェーズ13、実施済み)

Render Disk が有料プラン必須であることに加え、無料インスタンス運用時はディスクをアタッチできず再デプロイのたびに
添付ファイルが消えるため、**添付ファイルの保存先を Cloudflare R2(S3互換オブジェクトストレージ)へ移した**。

- **実現方式**: `apps/api/src/main/java/com/chatspace/api/upload/AttachmentStorage.java` インターフェースを新設し、
  `LocalDiskAttachmentStorage`(既定、開発/テスト用)と `S3AttachmentStorage`(`chatspace.storage.type=s3`、本番用)を
  `@ConditionalOnProperty`で切り替える。`UploadService` は`AttachmentStorage`のみに依存し、保存先の実装詳細を知らない
- **認可への影響を避ける設計**: `UploadService.serve()`のライブ権限再チェック(`authorizeServe`)自体は無変更。
  ただし「存在確認」(`exists()`、本文を転送しない)と「本文取得」(`load()`)を分離し、**本文取得はライブ権限再チェックに
  成功した後にのみ行う**。認可拒否されるリクエストのたびにオブジェクトストレージへ本文転送させないため
  (認証済みだが無権限のユーザーによる連続リクエストでR2転送量・ヒープを消費させないための対策)
- **バケットは非公開のまま**。プライベートチャンネル・DMの添付は参加者以外に見えてはならず(AUTH-N07)、配信は
  必ず `GET /uploads/{storageKey}` を経由させてライブ権限再チェックを維持する。署名付きURL方式は不採用
  (前段のライブ権限再チェックを迂回できる経路を作らないため)
- **R2接続設定**: `S3StorageConfig`(`@ConditionalOnProperty`で`type=s3`のときのみ有効)がAWS SDK v2の`S3Client`を
  構築する。R2はS3互換APIだが path-style アドレッシング(`pathStyleAccessEnabled(true)`)と
  `chunkedEncodingEnabled(false)`(署名不一致対策、Cloudflare公式のAWS SDK for Java例に準拠)が必要
- **テストへの影響**: 既存の統合テスト(`UploadAuthorizationTest`)は`chatspace.storage.type`未設定→既定の
  `LocalDiskAttachmentStorage`が使われるため無改修のまま通る。`S3AttachmentStorage`は単体テスト
  (`S3AttachmentStorageTest`、Mockitoで`S3Client`をモック)で検証する
- **費用**: Render Disk が不要になる代わりにR2側の費用が発生する(無料枠の範囲内で収まる想定)

## 8. セキュリティ方針

### 8.1 認証

| 項目 | 方針 |
|------|------|
| JWT | HS256、`JWT_SECRET` 環境変数で署名、有効期限7日。実装は Nimbus JOSE+JWT(`com.nimbusds:nimbus-jose-jwt`)。Spring Security の OAuth2 Resource Server 自動構成は不採用(自前でトークンを発行する用途に対して不要な依存が増えるため) |
| パスワード | bcrypt(コストファクタ12)。ユーザー不在時も固定ダミーハッシュに対して比較処理を実行し、応答時間差からユーザー存在有無を推測できないようにする |
| Cookie | 名前 `chatspace_token`、`HttpOnly; SameSite=Lax; Secure`(本番のみ)、有効期限7日・`path=/` |
| ログアウト | Cookie の削除のみ。サーバー側でのトークン失効・リフレッシュトークンの仕組みは持たない(既知の設計選択) |
| REST 認証 | `JwtAuthenticationFilter` が Cookie 検証を行うが、失敗時に即401は返さず `SecurityContext` を空のまま後続へ委譲する。401判定自体は Spring Security の `AuthenticationEntryPoint` が行う(詳細は `docs/シーケンス図.md` 2節) |
| WebSocket 認証 | STOMP CONNECT ではなく **ハンドシェイク時**に Cookie の JWT を検証(`HandshakeInterceptor` + `determineUser()`)。実体は REST と同じ `JwtService` を使用 |

### 8.2 Origin / CSRF

| 項目 | 方針 |
|------|------|
| REST の CSRF | Cookie 認証 + `SameSite=Lax` を主たる防御とし、Spring Security の CSRF 保護は明示的に無効化する。前提として、フロントエンドとバックエンドが**同一 registrable domain(eTLD+1)** であることが必要(ローカル開発の `localhost` はこの前提を満たす) |
| 本番でフロント/APIが別ドメインになる場合 | `SameSite` の "site" 判定はポート・サブドメインを区別しないため上記前提が崩れる。その場合は `SameSite=None; Secure` + 別途 CSRF トークン方式へ切り替える判断が必要。**本番のドメイン構成が決まった時点で要再確認**(フェーズ12のチェック項目) |
| `/ws` の Origin 検証 | `StompEndpointRegistry.setAllowedOriginPatterns(...)` で `WEB_ORIGIN` 由来の許可オリジンのみ設定し、ワイルドカード `*` は本番では使わない。WebSocket ハンドシェイクは `fetch` と異なり Cookie が自動送信されるため、Origin 検証がこの経路唯一の CSRF 相当の防御となる |
| STOMP CONNECT の CSRF | Spring Security の WebSocket メッセージセキュリティの既定動作(CONNECTフレームへのCSRFトークン要求)は無効化し、Origin 許可リストを主たる防御とする。許可外 Origin からの CONNECT/SEND が拒否されることを統合テストで確認する(フェーズ4) |

#### 8.2.1 本番ドメイン構成の決定事項(フェーズ14で確定)

フェーズ12時点では本番のドメイン構成が未定のため判断基準の文書化に留めていたが、フェーズ14で
**フロントエンド(`apps/web`)をSpring Bootに同梱し同一オリジンで配信する**方針に確定した(2.1節参照)。
理由は`*.onrender.com`がPublic Suffix Listに載っており、サービスを分けると別サイト扱いになって
`SameSite=Lax`の`chatspace_token`が送られずログイン不能になるため。同一オリジンのため、以下の
「同一registrable domain」の行に該当し、**追加のコード変更は不要**(現行の`SameSite=Lax`のまま、
`WEB_ORIGIN`を本番URLに設定し`COOKIE_SECURE=true`にするだけ)。

| 本番のドメイン構成 | 必要な作業 |
|---|---|
| フロントとAPIが**同一 registrable domain(eTLD+1)**(★ 本プロジェクトの構成) | **作業なし**。現行の `SameSite=Lax` のままでよい。`WEB_ORIGIN` を本番ドメインに設定し、`COOKIE_SECURE=true` にするだけ |
| フロントとAPIが**別 registrable domain**(不採用) | ① `AuthController` の Cookie を `SameSite=None; Secure` へ変更 ② CSRFトークン方式(double-submit cookie 等)を導入 ③ `SecurityConfig` の CORS 許可オリジンを見直し ④ CSRFトークン検証の統合テストを追加 |

> **誤設定が無防備な公開に繋がらない構造になっている**点を補足しておく。別ドメイン構成で `SameSite=Lax` の
> まま公開した場合、CookieがAPIへ送信されないため**そもそもログインできない**。「防御が外れたことに気付かない
> まま運用が始まる」形の事故は起きない。

### 8.3 STOMP SEND/SUBSCRIBE の default-deny

| ルール | 内容 |
|--------|------|
| SEND | `/app/**` 宛のみ許可し、認証済みユーザーに限定。`/topic/**`・`/queue/**`・`/user/**` へのクライアント発 SEND は常に拒否 |
| SUBSCRIBE | `/user/queue/events` は認証済みユーザーであれば常に許可(catch-allのdenyより前に評価)。チャンネル/DM/ワークスペーストピックは既存の認可チェック(メンバーシップ検証)を適用。それ以外は default-deny |
| CONNECT/DISCONNECT/UNSUBSCRIBE/HEARTBEAT | `permitAll()` として default-deny の対象から明示的に除外(`anyMessage().denyAll()` を素直に書くとSTOMP接続自体が確立しなくなるため) |
| Principal解決 | ハンドシェイク時に設定する Principal の `getName()` を、`convertAndSendToUser()` 呼び出し時の内部ユーザーIDと一致させる。不一致だと通知が例外もなく静かに届かなくなる |

### 8.4 認可

- `@PreAuthorize` 等の宣言的ロールチェックではなく、サービス層のヘルパークラス(`WorkspaceAuthorizationService`・`ChannelAuthorizationService`・`DmAuthorizationService`・`MessageScopeGuard`)でリソース単位の認可を行う
- **404-not-403方針**: 存在自体を隠すべきリソース(非参加のプライベートチャンネル/DM)は404、閲覧可能だが操作不可なものは403
- **DM権限**: 参加者チェックに加え、呼び出し時点で有効な `WorkspaceMember` であることを必須条件とする(ワークスペースキック後もDMの既知IDでアクセスが残り続けるギャップへの対策)
- **通知のスコープ再チェック**: 一覧取得・未読件数・個別既読・全件既読の全エンドポイントで、channelId/dmId/workspaceIdに対する現在のライブなメンバーシップをAND結合で再検証する(詳細は`docs/シーケンス図.md` 7節)
- **メンション**: `MentionResolver`および候補取得APIは、その時点のライブなチャンネルメンバーシップとのみ突合する

### 8.5 添付ファイル

- マジックバイト判定(PNG/JPEG/GIF/WEBP/MP4/WEBM の固定シグネチャ)によりクライアント指定の Content-Type を信用しない
- 保存ファイル名は `UUID.randomUUID()` + 検出MIMEから決めた拡張子
- 配信時は `storageKey` を正規表現検証後、パス正規化して保存ディレクトリ配下であることを再確認(パストラバーサル対策)
- 取得の都度、所属メッセージのチャンネル/DMに対するライブな権限チェックを再実行(アップロード時点のみのチェックにしない)
- アップロードサイズ上限は多層防御: `spring.servlet.multipart.max-file-size`/`max-request-size`(25MB、**必須**)+ サービス層での `MultipartFile#getSize()` 再確認(**必須**)

### 8.6 マークダウン

- HTML生成はクライアント側のみ(`marked` + `DOMPurify`、`img`タグ除外)で行い、バックエンドは入力値のバリデーション(長さ等)のみ担当する

## 9. CI構成(GitHub Actions)

### 9.1 既存ワークフロー

`.github/workflows/claude-code-review.yml`(PR作成時・PRブランチへのプッシュ時に実行される Claude Code 自動レビュー)は引き続き稼働させる。ドラフトPRは対象外(Ready for reviewにした時点で実行)、フォークからのPRはシークレットが渡らないため実行されない。

### 9.2 新設するワークフロー

| ワークフロー | 内容 |
|------|------|
| バックエンドCI | **`./gradlew build`** を PR・main への push で実行。Gradle は `build`→`check`→`test` の依存関係を持ち、Spotless プラグイン適用時は `spotlessCheck` も `check` の依存に自動で入るため、`./gradlew build` 単体で **spotlessCheck・ArchUnit含む test・ビルド** の3つが実行される(Testcontainers込み)。実行時間が読みにくいため `timeout-minutes` を必須設定する |
| フロントエンドCI | `pnpm --filter @chatspace/web run typecheck`・`lint`・`build`(導入すれば `test`)を個別実行する。`pnpm run <script>` はスクリプト名を1つしか取らないため、まとめて実行する場合は `pnpm --filter @chatspace/web run "/^(typecheck\|lint\|build)$/"` の正規表現形式を使う。`--filter` は `package.json` の `name`(`@chatspace/web`)に一致させる |

両ワークフローとも「警告0件必須」という既存規約(CLAUDE.md)を新スタックでも踏襲する。

**新規ワークフロー自身も `quality-check` スキルが定義しているワークフロー確認観点(最小権限の`permissions`、`timeout-minutes`、`concurrency`、スクリプトインジェクション対策、アクションの参照方式)を満たすこと。** アクション参照を SHA 固定にするかタグ参照のままにするかは、新規ワークフロー作成時に既存ワークフロー(現状 `actions/checkout@v6`・`anthropics/claude-code-action@v1` ともタグ参照)とまとめて方針を統一する。

### 10.1 Render環境でのログ確認方法(2026-08-26、実機`chatspace`サービスで検証済み)

- アプリは標準出力にログを書き、Render の Web Service がそれを収集する。ダッシュボードの「Logs」タブで
  リアルタイム表示・検索ができる
- 環境変数 `LOG_STRUCTURED_FORMAT=logstash` は設定済み。実際のLogsタブの出力もJSON形式になっており、
  `requestId`・`userId`・`auditEvent`等での絞り込み検索も動作を確認した(詳細・出力サンプルは
  `docs/ログ運用設計書.md` §4参照)
- ログレベルは `LOG_LEVEL`(既定 `INFO`)・`LOG_LEVEL_APP`(`com.chatspace` 配下、既定 `INFO`)で調整する。
  本番環境ではいずれも未設定で、既定の `INFO` のまま運用している
- **保持期間の実測**: Logsタブの日時範囲選択で「Last 7 Days」まで選択可能(無料プラン)。デプロイからまだ
  日数が浅く7日境界での実際のローテーションは未確認
- **外部ログ集約(New Relic)**: RenderのLog Streams機能(ワークスペースの`Integrations > Observability`)で
  New Relicへの転送を設定済み(2026-08-26)。ただしNew Relic無料プラン側の保持期間も実測7日で、Render単体
  からの保持期間の改善にはなっていない。個別サービスの転送除外はRenderのProプラン以上が必要なため、
  `chatspace-db`(PostgreSQL)の接続ログもワークスペース単位でまとめて転送される。詳細・既知の限界は
  `docs/ログ運用設計書.md` §4.1参照

なお、単一インスタンス構成では「コミット直後にプロセスが落ちたらキック通知が飛ばないのでは」という懸念に対し、**プロセスが落ちれば同じメモリ上にある WebSocket セッション自体も同時に消える**ため、`@TransactionalEventListener(AFTER_COMMIT)` のみで整合性が完全に閉じる(詳細は`docs/シーケンス図.md` 6節)。この前提は複数インスタンス構成でなければ崩れないが、水平スケール対応は実施しないことが確定しているため、outboxパターン等の追加対応は不要。
