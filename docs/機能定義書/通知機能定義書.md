# 通知機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

## 1. 機能概要

メンション・DM・チャンネル招待・ワークスペース招待・スレッド返信の各イベント発生時に `Notification` レコードを生成し、`/user/queue/events`(STOMP)経由でリアルタイムに配信する機能。あわせて、未読件数の取得・個別既読化・全件既読化を提供する。

**最重要の設計制約**: 本機能は `.plans/java-spring-boot-redesign.md` §3 で「実在するギャップ」として明記されている**通知のスコープ漏洩防止**を修正対象として含む。プロトタイプの `notifications.ts` は通知一覧取得時に `userId`/`workspaceId` のみで絞り込んでおり、通知が指す `channelId`/`dmId` に対する現在のメンバーシップを再確認していない。このため、あるチャンネルをキックされた後も、そのチャンネルで過去に受け取った通知(メンション等)の本文を読み続けられてしまう。新スタックでは、通知に関する**全エンドポイント**に channel/dm/workspace の3条件を **AND** 結合したライブスコープ再チェックを適用することでこれを修正する(§6 参照)。

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、自分がメンションされたら通知を受け取りたい |
| US-02 | ユーザーとして、DM が届いたら通知を受け取りたい |
| US-03 | ユーザーとして、チャンネル/ワークスペースに招待されたら通知を受け取りたい |
| US-04 | ユーザーとして、自分の投稿へのスレッド返信(メンションが無くても)を通知として受け取りたい |
| US-05 | ユーザーとして、未読の通知件数をひと目で確認したい |
| US-06 | ユーザーとして、通知を個別に、またはまとめて既読にしたい |
| US-07 | ユーザーとして、チャンネルからキックされた後は、そのチャンネルに関する過去の通知の内容を読めなくなることを期待する(セキュリティ上の暗黙の期待) |

## 3. 機能詳細

### 3.1 通知の生成トリガー

| 種別(`NotificationType`) | トリガー | `channelId` | `dmId` | `workspaceId` |
|---|---|---|---|---|
| `MENTION` | チャンネルメッセージ内の有効な `@メンション`(`メンション機能定義書.md` 参照) | あり | null | あり |
| `DM` | DM メッセージ送信(送信者以外の相手へ) | null | あり | あり |
| `THREAD_REPLY` | 自分が投稿した(スレッド親)メッセージへの返信(メンションが無くても届く) | チャンネル時は あり / DM 時は null | DM 時は あり / チャンネル時は null | あり |
| `CHANNEL_INVITE` | チャンネルへの招待 | あり | null | あり |
| `WORKSPACE_INVITE` | ワークスペースへの招待 | null | null | あり(これのみを持つ) |

- 通知生成は `NotificationService`(`notification` パッケージ)に集約し、REST 経由のミューテーション(メッセージ投稿・招待)からも、将来的な STOMP `@MessageMapping` ハンドラからも同じ Service を呼べるようにする(§1「実装方針」の層分離方針に基づく)。
- 通知本文(`text`)にはメッセージ本文のプレビュー等、閲覧権限に紐づく情報を含み得るため、§6 のスコープ再チェックの対象になる。

### 3.2 リアルタイム配信

- 通知生成と同一トランザクション(コミット後)で、`/user/queue/events` へ `NOTIFICATION` イベントとして `convertAndSendToUser()` 経由で配信する。宛先解決の仕組み・Principal 名の一致保証は `リアルタイム通信機能定義書.md` を参照。
- クライアントが受信できなかった場合(オフライン等)でも、通知は DB に永続化されているため、次回の一覧取得・未読件数取得で参照できる。

### 3.3 未読管理

- `readAt IS NULL` の通知を未読として扱う。
- `GET /notifications/unread-count` は未読件数のみを返す軽量エンドポイントとして提供する。
- `POST /notifications/{notificationId}/read` は指定した通知1件を既読にする。
- `POST /notifications/read-all` は(オプションで `workspaceId` を指定して)未読通知を一括既読にする。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| GET | `/notifications?workspaceId={id}&unreadOnly={bool}&cursorCreatedAt={ts}&cursorId={id}` | 通知一覧取得(ライブスコープ再チェック適用、`(createdAt, id)`複合カーソルページング) | 必要 |
| GET | `/notifications/unread-count` | 未読件数取得(同上) | 必要 |
| POST | `/notifications/{notificationId}/read` | 個別既読化(同上) | 必要 |
| POST | `/notifications/read-all` | 全件既読化(同上) | 必要 |

**通知一覧レスポンス例**

```json
{
  "notifications": [
    {
      "id": "notif_1",
      "type": "MENTION",
      "channelId": "ch_1",
      "workspaceId": "ws_1",
      "text": "Alice さんがあなたをメンションしました",
      "readAt": null,
      "createdAt": "2026-08-15T01:00:00Z"
    }
  ]
}
```

詳細なスキーマは Swagger UI(`/swagger-ui.html`)を正とする。STOMP 経由の配信ペイロードは `リアルタイム通信機能定義書.md` の宛先表を参照。

## 5. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| 未認証ユーザーのアクセス | 401 |
| `workspaceId` クエリパラメータ(一覧・全件既読) | 任意。指定時は形式検証のみ(存在確認は §6 のスコープ再チェックに委ねる) |
| `notificationId`(個別既読) | 存在しない、または自分宛でない通知の場合は 404 相当(更新0件として扱う) |
| 他人の通知への既読化操作 | `userId` 条件で絞り込むため、他人の通知に影響を与えない(更新対象0件) |

## 6. セキュリティ仕様

### 6.1 通知のスコープ漏洩防止(最重要・実在するギャップの修正)

プロトタイプの `notifications.ts` は通知一覧取得時に `userId` と `workspaceId` のみで絞り込んでおり、通知本文(`text`、メッセージ本文のプレビューを含む)をそのまま返す。このため、あるチャンネルをキックされた後も、過去に受け取った通知(そのチャンネルでのメンション等)から本文を読み続けられてしまうギャップが**実在する**(CLAUDE.md が名指しする「通知」の漏洩リスクそのもの)。

新スタックでは、**通知一覧取得時に、各通知が指す `channelId`/`dmId`/`workspaceId` に対する現在のライブなメンバーシップを再検証し、非メンバーになったものは除外する**設計を採用する(添付ファイルのライブ再チェックと同じ設計原則)。この再チェックは一覧取得だけでなく、**`unread-count`(未読件数)・個別既読(`POST /notifications/{id}/read`)・全件既読(`POST /notifications/read-all`)の全エンドポイントに同一のスコープ条件を適用する**(一覧からは除外されるのに未読件数には残る、といった不整合を防ぐため)。

実装上は各通知ごとに `ChannelAuthorizationService`/`DmAuthorizationService` を1件ずつ呼ぶと N+1 クエリになるため、**`Notification` を `ChannelMember`/`DmThread`/`WorkspaceMember` と `EXISTS`/`JOIN` する1本の Repository クエリで一括絞り込みする**。3条件は必ず **`AND`** で結合すること(素直に「同様に」で `OR` 連結すると、チャンネル通知は `dm_id IS NULL` により DM 側の節が常に真になり、フィルタが完全に無効化される致命的なバグになる)。

```sql
WHERE (channel_id IS NULL OR EXISTS (
         SELECT 1 FROM channel_member cm
         WHERE cm.channel_id = notification.channel_id AND cm.user_id = :userId))
  AND (dm_id IS NULL OR EXISTS (
         SELECT 1 FROM dm_thread dt
         JOIN workspace_member wm ON wm.workspace_id = dt.workspace_id AND wm.user_id = :userId
         WHERE dt.id = notification.dm_id AND (dt.user_a_id = :userId OR dt.user_b_id = :userId)))
  AND (workspace_id IS NULL OR EXISTS (
         SELECT 1 FROM workspace_member wm
         WHERE wm.workspace_id = notification.workspace_id AND wm.user_id = :userId))
```

**DM 側の `EXISTS` は「DM参加者か」だけでは不十分な点に注意する**: `DmThread.userAId`/`userBId` はワークスペースからキックされても消えないため、DM 参加者チェックのみでは真のままになってしまう。上記の通り `workspace_member` との `JOIN` を必ず含めること。また `WORKSPACE_INVITE` 通知は `workspaceId` のみを持ち `channelId`/`dmId` は null であるため、`workspace_id` 条件も同じ `AND` 結合に含めないと、ワークスペースキック後も過去の招待通知が残留する(漏洩する情報はワークスペース名のみで実害は小さいが、一貫性のため同基準を適用する)。

この再チェックは**一覧取得・未読件数・個別既読・全件既読の4エンドポイント全てに同一のクエリ条件を適用する**ことが必須である。一覧取得だけに適用し他のエンドポイントを素通しにすると、「一覧には表示されないが未読件数にはカウントされ続ける」「一覧からは消えたのに既読API単体を直接叩けば既読化できてしまう(実害は小さいが一貫性を欠く)」といった不整合が生じる。

### 6.2 通知生成時のメンバーシップ検証との関係

- `MENTION` 通知の生成自体は `メンション機能定義書.md` §6 の「ライブなチャンネルメンバーシップとの突合」により、そもそも非メンバーに対して生成されない。
- 一方で本節の再チェックは「生成時点では正当だった通知が、後からメンバーシップを失ったことで閲覧不可になるべきケース」を扱う。両者は独立した防御層であり、片方を実装しても他方の代替にはならない。

### 6.3 他人の通知への操作防止

- 個別既読・全件既読は常に `userId` 条件(認証済みユーザー自身)で絞り込むため、他人の `notificationId` を指定しても他人の通知に影響を与えない。**(レビュー指摘により確定)** 存在しない、または他人の`notificationId`を指定した場合は**404**とする(本プロジェクト全体の404-not-403方針、および他の`messageId`等を受け取るエンドポイントと同じ扱いに揃える。「静かに成功扱い」という代替案は採用しない)。
- **不正な`cursorCreatedAt`/`cursorId`の扱い(レビュー指摘により確定)**: パース不能な値が渡された場合は400を返す。値として正しいがどのレコードにも一致しない(存在しないカーソル位置を指す)場合はエラーにせず、単純にそのカーソル値より古いレコードを対象に検索する(該当なしなら空配列 + `nextCursor: null` を返す)。

## 7. 制約・前提条件

- 通知の生成対象は §3.1 の5種別のみ(リアクションは通知トリガーに含めない、`リアクション機能定義書.md` §8 参照)。
- 通知は既読化しても削除はされない(既読/未読の状態のみを管理する)。
- **通知一覧のページネーション方式を確定する(レビュー指摘により未確定だった仕様を確定)**: プロトタイプの `take: 100`(ページネーション無し)は踏襲せず、要件定義書・DB設計書が既に定めている `(createdAt, id)` 複合カーソル方式に統一する。1回のレスポンス件数は**最大50件**(検索・メッセージ一覧の`RESULT_LIMIT`と揃える)とし、レスポンスに `nextCursor: { createdAt, id } | null` を含める。クライアントはこれを次回リクエストの `cursorCreatedAt`/`cursorId` に渡す。`unread-count` は件数のみを返す軽量エンドポイントのため、ページネーションの対象外とする。
- **通知パネル(画面設計書 S-13)のUI想定動作**: 新しい通知から古い通知の順に表示し、パネル下端に近づいたタイミングで次の50件を取得する(パネル内無限スクロール)。取得中に同一カーソルへの二重リクエストが発生しないようクライアント側でフェッチ中フラグを持つ。既読化操作(個別・全件)は一覧の並び順・表示位置を変更しない(既読になっても消えたり動いたりしない)。WebSocketで受信した新着通知は一覧の**先頭**に追加する(新しい順表示のため)。パネルを閉じても同一セッション内(タブを閉じるまで)は取得済み一覧とスクロール位置を保持し、再度開いた際に再取得しない。

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| ブラウザ通知(Web Push / Notification API) | UX 拡張としてフェーズ10で任意実装(本ドキュメントの必須要件には含めない) |
| メール通知 | スコープ外 |
| 通知の削除(既読とは別の完全削除) | スコープ外。既読管理のみ |
| 通知設定のカスタマイズ(種別ごとのミュート等) | スコープ外 |

## 9. テスト

| 種別 | 内容 | 対応フェーズ |
|---|---|---|
| 新規受け入れテスト | 通知のスコープ再チェック: あるチャンネルからキックされた後、キック前に受け取った通知(メンション等)の一覧・本文が取得できなくなること | フェーズ5 |
| 新規受け入れテスト | 上記と同じシナリオで `unread-count` が正しく減ること(一覧と未読件数の不整合が無いこと) | フェーズ5 |
| 新規受け入れテスト | キック後、除外された通知に対して個別既読 API を直接叩いても既読化・情報取得ができないこと | フェーズ5 |
| 新規受け入れテスト | ワークスペースキック後、過去の DM 通知が一覧・未読件数に含まれなくなること | フェーズ5 |
| 新規受け入れテスト | ワークスペースキック後、過去の `WORKSPACE_INVITE` 通知が一覧・未読件数から除外されること | フェーズ5 |
| 回帰テスト | スコープ再チェッククエリが `OR` ではなく `AND` で結合されていること(チャンネル通知が DM 側の `dm_id IS NULL` 分岐で誤って常に真にならないこと)を確認する単体テスト | フェーズ5 |
| 統合テスト | `MENTION`/`DM`/`THREAD_REPLY`/`CHANNEL_INVITE`/`WORKSPACE_INVITE` それぞれの生成トリガーで通知が正しく作成され、`/user/queue/events` に配信されること | フェーズ5 |
