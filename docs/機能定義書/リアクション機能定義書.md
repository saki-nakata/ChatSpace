# リアクション機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

## 1. 機能概要

チャンネル/DM メッセージに対して絵文字リアクションを行う機能。1ユーザーにつき「1メッセージ・1絵文字あたり1回」のみ登録でき、同一の API を再度呼び出すことでトグル(登録・解除)する。プロトタイプの `messages-service.ts` の `toggleReaction` をそのまま踏襲し、Java 版でも `MessageService`(`message` パッケージ)に同等の処理を実装する。

リアクションの追加・解除は、対象メッセージが所属するチャンネル/DM のトピック(`/topic/channels.{channelId}` または `/topic/dms.{dmId}`)へ、タグ付きユニオンの一種として `REACTION_UPDATED` イベントでリアルタイム配信される(メッセージ CRUD・タイピングと同一トピックに集約する設計。詳細は `リアルタイム通信機能定義書.md` §4 の宛先表を参照)。

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、メッセージに絵文字でリアクションして気持ちを手軽に伝えたい |
| US-02 | ユーザーとして、誤って付けたリアクションを取り消したい |
| US-03 | ユーザーとして、各メッセージにどの絵文字が何人分付いているか一覧で確認したい |
| US-04 | ユーザーとして、自分が既にリアクション済みかどうかをひと目で判別したい |
| US-05 | ユーザーとして、他のメンバーが自分のいるチャンネル/DM でリアクションを追加・解除したら、画面を再読み込みせずリアルタイムに反映してほしい |

---

## 3. 機能詳細

### 3.1 リアクション操作(トグル)

- `POST /workspaces/{workspaceId}/channels/{channelId}/messages/{messageId}/reactions` および `POST /workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}/reactions` を呼び出すことでトグル動作する。
  - 対象メッセージ・ユーザー・絵文字の組み合わせで既存の `Reaction` が無ければ登録、あれば解除する。
  - DB の一意制約 `(messageId, userId, emoji)` により、同時多重リクエストが来ても重複行は作られない(JPA でも `@UniqueConstraint` を維持する)。
- 処理の入口で必ず `MessageScopeGuard.assertInScope(message, scope)` を呼び、URL 上の `channelId`/`dmId` と対象メッセージの実際の所属が一致することを確認してからトグル処理へ進む(§6 参照)。
- ソフトデリート済み(`deletedAt IS NOT NULL`)のメッセージに対するリアクションは 404 として扱う(削除済みメッセージへの新規操作を許可しない)。

### 3.2 レスポンス・表示仕様

- レスポンスはメッセージ全体の DTO で返し、`reactions` フィールドは絵文字ごとに集約したサマリの配列とする。

| フィールド | 内容 |
|---|---|
| `emoji` | 絵文字文字列 |
| `count` | その絵文字を付けたユーザー数 |
| `reactedByMe` | 応答を受け取ったユーザー自身が付けているか |
| `userIds` | その絵文字を付けたユーザーID一覧(チャンネル/DM メンバーへの「誰がリアクションしたか」表示に使用) |

- `userIds` はチャンネル/DM のメンバーであれば閲覧できる情報として扱う(Slack 同様、リアクション済みユーザーの一覧はメンバー間では非公開情報ではないという設計をプロトタイプから踏襲)。ただし当然、そのチャンネル/DM のメンバーでない者には §6 の認可によりメッセージ自体が見えないため `userIds` も漏れない。

### 3.3 リアルタイム配信

- リアクションの登録・解除いずれも、更新後のメッセージ DTO を `REACTION_UPDATED` イベントとして対象トピック(`/topic/channels.{channelId}` または `/topic/dms.{dmId}`)へブロードキャストする。
- クライアントは既に当該トピックを `SUBSCRIBE` 済みである前提(チャンネル/DM 画面を開いた時点で購読する)。購読自体がメンバーシップ検証を経ているため(`リアルタイム通信機能定義書.md` 参照)、非メンバーにイベントが届くことはない。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| POST | `/workspaces/{workspaceId}/channels/{channelId}/messages/{messageId}/reactions` | チャンネルメッセージへのリアクション toggle | 必要 |
| POST | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}/reactions` | DM メッセージへのリアクション toggle | 必要 |

**リクエストボディ例**

```json
{ "emoji": "👍" }
```

**レスポンス例(メッセージ DTO の抜粋)**

```json
{
  "id": "msg_123",
  "reactions": [
    { "emoji": "👍", "count": 2, "reactedByMe": true, "userIds": ["user_a", "user_b"] }
  ]
}
```

STOMP 経由の配信ペイロード形式は `リアルタイム通信機能定義書.md` の宛先表・イベント仕様を参照。詳細な REST スキーマは springdoc-openapi が生成する Swagger UI(`/swagger-ui.html`)を正とする。

## 5. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| 未認証ユーザーの操作 | 401 を返す |
| `emoji` の長さ | 1〜8 文字(プロトタイプの Zod スキーマ `toggleReactionSchema` を Bean Validation `@NotBlank @Size(min=1, max=8)` で1:1再現) |
| 存在しない `messageId` | 404 |
| ソフトデリート済みメッセージへの操作 | 404(通常メッセージが存在しない場合と区別しない) |
| `channelId`/`dmId` と対象メッセージの所属不一致 | 404(`MessageScopeGuard` による confused-deputy 対策、§6 参照) |
| 重複トグル(連打・多重リクエスト) | DB 一意制約により重複行が作られない。2回目の呼び出しは解除として扱われる(仕様通りの動作) |
| 自分のメッセージへのリアクション | 制限なし(自分の投稿にもリアクション可能) |

## 6. セキュリティ仕様

- **メッセージスコープの confused-deputy 対策(既存テストで保護されている5点の一つ)**: `messageId` を受け取る全エンドポイント(本機能含む)は、処理の先頭で `MessageScopeGuard.assertInScope(message, scope)` を呼ぶ。これは URL の `channelId`/`dmId` と、`messageId` が実際に所属するチャンネル/DM が一致するかを検証するもので、例えば「自分が参加しているチャンネル A の URL に、実際には別チャンネル B(非参加)に属する `messageId` を差し込んでリアクションを付けようとする」攻撃を防ぐ。プロトタイプの `test/authorization.test.ts` で「クロスチャンネルのメッセージID漏洩防止」として検証されている不変条件であり、新スタックでも同名のテストとして1:1移植する(`.plans/java-spring-boot-redesign.md` §10)。
- **チャンネル/DM メンバーシップの事前確認**: リアクション操作自体が `ChannelAuthorizationService.requireChannelMember`/`DmAuthorizationService.requireDmAccess` を経由するため、非メンバーはそもそも 404 でリアクション操作に到達できない。DM の場合はワークスペースからキックされたユーザーが `dmId` を知っているだけでは操作できないよう、`DmAuthorizationService.requireDmAccess()` が DM 参加者チェックに加えて現在有効な `WorkspaceMember` であることも必須条件とする(§3「認証・認可レイヤー」で述べる実在するギャップの修正、詳細は `DM機能定義書.md`/`メッセージング機能定義書.md` を参照)。
- **リアルタイム配信面の防御**: `REACTION_UPDATED` イベントはサーバーの `RealtimeEventPublisher`(`SimpMessagingTemplate` 経由)のみが `/topic/channels.{channelId}`・`/topic/dms.{dmId}` へ発行でき、クライアントが直接これらの宛先へ `SEND` することは SEND default-deny 設定により拒否される(偽装イベントの配信不可、詳細は `リアルタイム通信機能定義書.md` §SEND default-deny を参照)。また `SUBSCRIBE` 時点でも非メンバーは購読できないため、イベント自体が非メンバーに届くことはない。

---

## 7. 制約・前提条件

- 1ユーザーが同一メッセージ・同一絵文字にリアクションできるのは1回のみ(DB の複合一意制約 `(messageId, userId, emoji)` で保証)。
- 1メッセージに付けられる絵文字の種類数に上限は設けない。
- リアクションはログイン済みユーザーのみ操作可能。
- リアクションの取り消しに時間制限は設けない(投稿から時間が経ってもいつでも解除可能)。

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| カスタム絵文字(ワークスペース独自の絵文字)の追加 | スコープ外。標準的な Unicode 絵文字のみ対象 |
| リアクション専用の通知(メンション・DM・招待・スレッド返信のみ通知対象) | プロトタイプ通りリアクションは通知トリガーに含めない(`通知機能定義書.md` 参照) |
| リアクションの集計・ランキング等の分析機能 | スコープ外 |

## 9. テスト

| 種別 | 内容 | 対応フェーズ |
|---|---|---|
| 単体テスト | `toggleReaction` の登録/解除の分岐、重複トグル時の一意制約違反ハンドリング | フェーズ3 |
| 認可テスト | クロスチャンネルの `messageId` を使ったリアクション試行が 404 になること(`MessageScopeGuard`) | フェーズ3 |
| 認可テスト | 非メンバーがチャンネル/DM のメッセージへリアクションを試みて 404 になること | フェーズ3 |
| 認可テスト | ワークスペースキック後、既知の DM `messageId` へのリアクションが 404 になること | フェーズ3 |
| 統合テスト | リアクション登録/解除が対象トピックへ `REACTION_UPDATED` として配信され、非購読者(非メンバー)には届かないこと | フェーズ4 |
| 統合テスト | クライアントが `/topic/channels.{id}` へ直接 `SEND` して偽装 `REACTION_UPDATED` を配信しようとしても拒否されること | フェーズ4 |

詳細な受け入れテストの一覧・実行方法は `docs/テスト設計書.md` を参照。
