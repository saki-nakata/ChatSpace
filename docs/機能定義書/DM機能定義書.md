# DM機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15

> 本ドキュメントは `.plans/java-spring-boot-redesign.md`(以下「計画書」)§3「認証・認可レイヤー」を正式文書化したものである。移植元は `apps/api/src/routes/dm.ts`・`apps/api/src/lib/authz.ts`。
>
> **本機能はプロジェクト全体の中でも最優先で検証すべき認可上の注意点を含む。** 計画書レビューにより、プロトタイプの実装コードに**実在する**セキュリティギャップ(ワークスペースからキックされたユーザーが、既知の `dmId` さえあれば DM の読み書き・添付取得を継続できてしまう)が発見されている。§6「セキュリティ仕様」を必ず参照すること。

---

## 1. 機能概要

ダイレクトメッセージ(DM)は、同一ワークスペースに所属する2ユーザー間の1対1チャットである。

- DM スレッド一覧取得、ユーザーID(ハンドル)を指定したDMスレッドの取得/新規作成
- 既読管理(自分の既読位置のみ更新)
- 認可は `DmAuthorizationService`(プロトタイプの `authz.ts` の `requireDMAccess` を移植・**修正**)が担う
- メッセージ本体のCRUD・スレッド返信・リアクションはチャンネルと共通の `MessageService` を使う(詳細は `メッセージング機能定義書.md`)。本ドキュメントは DM スレッド自体の管理と、DM 特有の認可要件(ワークスペースメンバーシップの再確認)に焦点を当てる

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ワークスペースメンバーとして、同じワークスペースの他のメンバーとDMを始めたい |
| US-02 | ユーザーとして、自分の全DMスレッドを一覧で見て未読数を確認したい |
| US-03 | ユーザーとして、DMを読んだら既読位置を更新したい |
| US-04 | ワークスペースメンバーとして、自分自身とはDMできないようにしてほしい |
| US-05 | **ワークスペースからキックされたユーザーとして、以後そのワークスペース内の誰ともDMの読み書きができなくなってほしい(既に知っている `dmId` を使っても不可)** |
| US-06 | ワークスペースメンバーとして、キックされた相手から過去のDM内容を読み続けられることのないようにしてほしい(相互に保護される) |

## 3. 機能詳細

### 3.1 DM スレッド一覧

- ワークスペースメンバーであることが前提(非メンバーは404)
- 自分が `userAId` または `userBId` であるスレッドを、作成日時降順で返す
- 各スレッドに相手ユーザー情報、未読数(`deletedAt IS NULL` かつ相手投稿かつ自分の既読位置より新しいメッセージ数)、最新メッセージのプレビューを含める

### 3.2 DM スレッドの取得/新規作成

- 入力:相手のユーザーID(ハンドル)
- 処理:
  1. ワークスペースメンバーシップチェック(呼び出し元)
  2. 相手ハンドルをユーザーテーブルで解決(存在しなければ404)
  3. 自分自身を指定した場合は400(「自分自身とはDMできません。」)
  4. **相手が現在のワークスペースメンバーであることを確認**(非メンバーなら404)
  5. `userAId < userBId` となるよう正規化してから `(workspaceId, userAId, userBId)` の一意制約で upsert(既存があれば取得、無ければ新規作成)
  6. 新規作成時は相手側クライアントにもリアルタイムでスレッド作成を通知し、相手のセッションを DM トピックの購読対象に加える

### 3.3 既読更新

- `DmAuthorizationService.requireDmAccess()` による認可チェック(§6)を通過した場合のみ、呼び出し元が `userAId`/`userBId` のどちらかに応じて `lastReadAtA`/`lastReadAtB` を更新する

### 3.4 DM メッセージ機能への参照

DM 内のメッセージ一覧・投稿・編集・削除・スレッド返信・リアクションは、チャンネルメッセージと同じ `MessageService`/`MessageScopeGuard` を使う。エンドポイント・バリデーション・confused-deputy対策の詳細は `メッセージング機能定義書.md` を参照。**これらの全エンドポイントの入口で、本ドキュメント§6の `DmAuthorizationService.requireDmAccess()` によるチェックが必ず先に実行される。**

## 4. 使用 API

DM スレッド自体の管理:

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| GET | `/workspaces/{workspaceId}/dms` | 自分のDMスレッド一覧 | 必要(ワークスペースメンバー) |
| POST | `/workspaces/{workspaceId}/dms` | 指定ユーザーとのDMスレッド取得/新規作成 | 必要(ワークスペースメンバー、相手も現在のワークスペースメンバーであること) |
| POST | `/workspaces/{workspaceId}/dms/{dmId}/read` | 既読位置更新 | 必要(DM参加者 かつ 現在のワークスペースメンバー) |

DM メッセージ(詳細は `メッセージング機能定義書.md`。認可要件は本ドキュメント§6が適用される):

| Method | エンドポイント | 説明 |
|--------|--------------|------|
| GET | `/workspaces/{workspaceId}/dms/{dmId}/messages` | メッセージ一覧 |
| POST | `/workspaces/{workspaceId}/dms/{dmId}/messages` | メッセージ投稿 |
| GET | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}/context` | 前後メッセージ取得(検索ジャンプ用) |
| GET | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}/replies` | スレッド返信一覧 |
| PATCH | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}` | メッセージ編集(投稿者本人のみ) |
| DELETE | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}` | メッセージ削除(論理削除、投稿者本人のみ) |
| POST | `/workspaces/{workspaceId}/dms/{dmId}/messages/{messageId}/reactions` | リアクション切り替え |

## 6. セキュリティ仕様

### 6.1 発見された実在するギャップ(必読)

プロトタイプの `apps/api/src/lib/authz.ts:55-65` の `requireDMAccess` は以下しか見ていない:

- `dm` が存在するか
- 呼び出し元が `dm.userAId` または `dm.userBId` と一致するか(DM参加者チェック)
- (`workspaceId` を渡した場合)`dm.workspaceId` と一致するか

**`requireWorkspaceMember` を呼んでいない。** 呼び出し側(`dm-messages.ts` の7エンドポイント全て)もこれを補っておらず、`uploads.ts:108` に至っては `workspaceId` すら渡していない。

`DMThread.userAId`/`userBId` はワークスペースからキックされても**消えない**(ワークスペースキックが削除するのは `WorkspaceMember`・`ChannelMember` のみで、`DMThread` はカスケード対象に含まれない)。したがって:

> **ワークスペースからキックされたユーザーは、既知の `dmId` さえあれば DM の読み書き・添付ファイル取得を継続できてしまう。**

これは CLAUDE.md が名指しする「認可の実装ミスが最大のリスク」「特にメッセージ検索と通知は権限外の内容を含めやすい」の範疇にある、DMについての実在するギャップである。

### 6.2 新スタックでの設計(必須修正)

`DmAuthorizationService.requireDmAccess(dmId, userId, workspaceIdOrNull)` は、以下の**両方**を満たさない限り成功させない:

1. DM参加者チェック(従来通り:`userId` が `dm.userAId` または `dm.userBId` と一致し、`workspaceId` を渡した場合は `dm.workspaceId` とも一致する)
2. **呼び出し時点で有効な `WorkspaceMember`(`dm.workspaceId`, `userId`)が存在すること**

いずれか一方でも欠ける場合は、既存の「非参加者には存在を隠す」方針(404-not-403)に合わせて **同一の404**(「DMが見つかりません。」)を返す。ワークスペースメンバーシップ切れであることを403で明示的に区別しない(区別すると「このDMは存在するが権限が無い」という情報を非メンバーに与えてしまうため)。

この再検証は DM スレッド管理系のエンドポイント(§4上表)だけでなく、`メッセージング機能定義書.md` が定義する **DM メッセージ関連の全エンドポイント**(一覧・投稿・編集・削除・スレッド返信・リアクション・添付ファイル取得)が入口で必ず通過する経路として実装する。

### 6.3 影響範囲(関連ドキュメントでの扱い)

ワークスペースキックが波及する範囲は複数の機能にまたがるため、対応する各ドキュメントに同じ設計原則(ライブなワークスペースメンバーシップの再確認)を適用する:

| 影響範囲 | 対応するドキュメント | 概要 |
|---|---|---|
| DMメッセージ取得・投稿・編集・削除・リアクション | `メッセージング機能定義書.md` | `DmAuthorizationService.requireDmAccess()` を経由するため自動的に保護される |
| DMトピックへのSTOMP再購読 | `リアルタイム通信機能定義書.md` | SUBSCRIBE時認可チェックが同じ `DmAuthorizationService` を使う |
| DM添付ファイルの取得 | (添付ファイル機能。本タスクの対象外だが計画書§3に記載) | `UploadService.serve()` のライブ権限再チェックで、DMに紐づく添付は `DmAuthorizationService.requireDmAccess()` を経由させる(`uploads.ts:108` が `workspaceId` を渡していなかった不備も併せて是正する) |
| DM通知の一覧・未読件数・既読化 | `通知機能定義書.md` | 通知一覧のスコープ再チェッククエリで、DM側の `EXISTS` 条件に **`workspace_member` との `JOIN` を必ず含める**(DM参加者チェックのみでは不十分。計画書§3のSQL例を参照) |

### 6.4 セキュリティ仕様一覧

| 項目 | 仕様 |
|------|------|
| DM参加者チェック | `userId` が `dm.userAId` または `dm.userBId` に一致すること |
| **ワークスペースメンバーシップの再確認(必須)** | 呼び出し時点で有効な `WorkspaceMember` が存在すること。DM参加者チェックと**AND**で結合し、どちらか一方の失敗でも404(§6.2) |
| confused-deputy対策 | `workspaceId` を渡した呼び出しでは `dm.workspaceId` との一致も検証する(URLの `workspaceId` と実際のDMの所属ワークスペースの不一致は404) |
| 404-not-403方針 | 非参加者・キック済みメンバーいずれに対しても、DMの存在自体を隠す404を返す。403は使わない |
| 自己DM禁止 | 自分自身を相手に指定したDM作成は400 |
| メッセージレベルの認可 | `MessageScopeGuard` によるconfused-deputy対策(URLの `dmId` と実際のメッセージの所属DMの一致確認)は `メッセージング機能定義書.md` を参照 |

## 7. 制約・前提条件

- DMスレッドはワークスペース単位で正規化される(`(workspaceId, userAId, userBId)` の一意制約)。同じ2人でも異なるワークスペースでは別スレッドになる
- DMスレッド自体の削除機能は無い(退出・アーカイブの概念を持たない)
- 一方が再度ワークスペースに招待されて再入場した場合、既存の `DMThread` レコード(削除されていない)がそのまま復活し、過去の履歴を再び参照できる(この挙動は意図的:キック中のみアクセスを止め、履歴自体は保持する設計)

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| グループDM(3人以上) | スコープ外。1対1のみ |
| DMスレッドの削除・アーカイブ | スコープ外 |
| DMのブロック機能 | スコープ外 |
