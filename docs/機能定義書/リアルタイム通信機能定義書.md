# リアルタイム通信機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

> **本ドキュメントの位置づけ**: 他の機能定義書は REST API の詳細スキーマを springdoc-openapi が生成する Swagger UI(`/swagger-ui.html`)に一本化しているが、STOMP/WebSocket のメッセージ仕様は Swagger の対象外であるため、本ドキュメントを**正式な STOMP メッセージ仕様書**として、他の機能定義書より詳細に記載する。

## 1. 機能概要

STOMP over WebSocket(`spring-boot-starter-websocket`)によるリアルタイム通信基盤。メッセージ CRUD・リアクション・タイピング表示・プレゼンス(オンライン/オフライン)・個人宛通知・キック時の強制切断を担う。プロトタイプの Socket.IO 実装(`socket.ts`, `notify.ts`, `presence.ts`)を土台に、STOMP のトピック/宛先ベースの設計へ置き換える。

**単一インスタンス前提**とし、ブローカーは Spring 標準のシンプルブローカー(インメモリ、`enableSimpleBroker`)を使う。RabbitMQ 外部ブローカーリレーへの切替・Redis 共有プレゼンスは、水平スケール対応そのものを検討の結果実施しないことが確定したため行わない。この方針に至った経緯(水平スケールを最初から作り込んだ結果、outbox・ブローカー認証・共有ボリューム等が芋づる式に増えた反省)は `.plans/java-spring-boot-redesign.md`「スコープに関する方針」を参照。

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、他のメンバーが投稿したメッセージを画面を再読み込みせずリアルタイムに見たい |
| US-02 | ユーザーとして、他のメンバーが入力中であることをタイピングインジケーターで知りたい |
| US-03 | ユーザーとして、ワークスペースメンバーのオンライン/オフライン状態を確認したい |
| US-04 | ユーザーとして、自分だけに届く通知やキック通知をリアルタイムに受け取りたい |
| US-05 | ワークスペースオーナーとして、キックしたユーザーが即座に接続を切断され、それ以降の会話を購読できなくなることを期待する |
| US-06 | 開発者として、悪意あるクライアントが認可されていない宛先へ購読・送信しても拒否されることを期待する(セキュリティ上の暗黙の期待) |

## 3. エンドポイント・接続方式

- **エンドポイント**: `/ws`(SockJS フォールバックなし、生 WebSocket のみ)
- **ブローカー**: Spring 標準のシンプルブローカー(インメモリ、単一インスタンス内で完結)
- **クライアント実装**: `@stomp/stompjs`。Cookie は WebSocket ハンドシェイクで自動送信されるため、`Authorization` ヘッダは不要
- **ハートビート・再接続**: クライアント側の `heartbeatIncoming`/`heartbeatOutgoing`/`reconnectDelay` は、Render の WebSocket 運用実態(固定のアイドルタイムアウトは無いが、デプロイ・再起動時に強制切断される。公式ドキュメントに ping/pong による定期 keepalive と指数バックオフ再接続が一般的なベストプラクティスとして案内されている)を踏まえて設定する。具体的な秒数は実装計画書(フェーズ4)で確定する

## 4. STOMP 宛先(Destination)一覧

| 用途 | 宛先 | 方向 |
|---|---|---|
| チャンネル内イベント(メッセージ CRUD・リアクション・タイピングをタグ付きユニオンで1トピックに集約) | `/topic/channels.{channelId}` | サーバー→クライアント(SUBSCRIBE) |
| DM 内イベント | `/topic/dms.{dmId}` | サーバー→クライアント(SUBSCRIBE) |
| ワークスペースイベント(チャンネル作成/削除等) | `/topic/workspaces.{workspaceId}` | サーバー→クライアント(SUBSCRIBE) |
| プレゼンス | `/topic/workspaces.{workspaceId}.presence` | サーバー→クライアント(SUBSCRIBE) |
| 個人宛通知・強制排除通知 | `/user/queue/events`(実体は `/user/{userId}/queue/events`、`convertAndSendToUser()` で解決) | サーバー→クライアント(SUBSCRIBE) |
| タイピング送信 | `/app/channels.{channelId}.typing` | クライアント→サーバー(SEND、`@MessageMapping` ハンドラが受信) |

宛先名の定数は Java 側 `StompDestinations.java` を正とし、フロントエンド `apps/web/src/realtime/destinations.ts` に手動同期する。ドリフト防止のため、Java 側の宛先名リストをビルド時に JSON リソースとして出力し、フロントエンドの契約テスト(Vitest)が突き合わせる(`.plans/java-spring-boot-redesign.md` §7)。

### 4.1 チャンネル/DM トピックのイベントペイロード(タグ付きユニオン)

`/topic/channels.{channelId}` と `/topic/dms.{dmId}` は、以下のイベント種別を `type` フィールドで判別するタグ付きユニオンとして1トピックに集約する(プロトタイプの Socket.IO イベント名 `message:created` 等に相当する概念を、STOMP では1トピック内のペイロード種別として表現する)。

| `type` | 内容 | 送信元 |
|---|---|---|
| `MESSAGE_CREATED` | 新規メッセージ投稿 | `MessageService` |
| `MESSAGE_UPDATED` | メッセージ編集 | `MessageService` |
| `MESSAGE_DELETED` | メッセージ削除(ソフトデリート) | `MessageService` |
| `REACTION_UPDATED` | リアクション登録/解除 | `MessageService`(`リアクション機能定義書.md` 参照) |
| `TYPING_UPDATE` | 入力中インジケーター | `TypingController` |

### 4.2 ワークスペーストピックのイベントペイロード

| `type` | 内容 |
|---|---|
| `CHANNEL_CREATED` | チャンネル作成 |
| `CHANNEL_DELETED` | チャンネル削除 |
| `DM_THREAD_CREATED` | 新規 DM スレッド作成 |
| `CHANNEL_MEMBER_KICKED` | チャンネルからのキック |
| `WORKSPACE_MEMBER_KICKED` | ワークスペースからのキック |

### 4.3 `/user/queue/events` のペイロード

| `type` | 内容 |
|---|---|
| `NOTIFICATION` | メンション・DM・招待・スレッド返信通知(`通知機能定義書.md` 参照) |
| `MEMBER_REMOVED` | 自分がキックされたことのベストエフォート通知(強制切断前に送信、§8 参照) |

## 5. 認証(ハンドシェイク時 JWT 検証)

- STOMP の CONNECT フレームではなく、**WebSocket ハンドシェイク時に Cookie の JWT を検証**する(`HandshakeInterceptor` + `DefaultHandshakeHandler.determineUser()`)。httpOnly Cookie を維持でき、REST と同じ検証経路(`JwtService`)を共有できるため。
- `WebSocketAuthInterceptor`(`ChannelInterceptor`)が CONNECT フレームで Principal の有無を再確認する。
- 認証の実体は REST・WebSocket で完全に共通であり、検証タイミング(HTTP リクエスト時 vs ハンドシェイク時)が異なるだけである(`.plans/java-spring-boot-redesign.md` §3)。

## 6. Cookie / Origin / CSRF 方針

- `chatspace_token` Cookie は `HttpOnly; SameSite=Lax; Secure`(本番のみ、ローカル開発の http では無効化)を REST と共通で維持する。
- `/ws` エンドポイントは `StompEndpointRegistry.setAllowedOriginPatterns(...)` で `WEB_ORIGIN` 環境変数由来の許可オリジンのみを設定し、ワイルドカード `*` は本番では使わない。**WebSocket ハンドシェイクは `fetch` と異なり Cookie が自動送信されるため、Origin 検証がこの経路唯一の CSRF 相当の防御になる**(Cross-Site WebSocket Hijacking 対策)。
- REST 側の CSRF は `SameSite=Lax` Cookie を主たる防御とし、Spring Security の CSRF 保護は明示的に無効化する(前提: フロントエンドとバックエンドが同一 registrable domain であること。本番でドメインが分かれる場合は `SameSite=None; Secure` + 別途 CSRF トークン方式への切り替えが必要になるため、本番ドメイン構成確定後にフェーズ12で再確認する)。
- **STOMP CONNECT の CSRF**: Spring Security の WebSocket メッセージセキュリティを組み込む場合、既定で CONNECT フレームに CSRF トークンを要求する(`AbstractSecurityWebSocketMessageBrokerConfigurer` の既定動作)。本設計では REST 同様、Origin 許可リストを主たる防御として CONNECT の CSRF トークン要求は無効化する方針を取るため、防御が Origin 検証の1点に集約される。この判断を弱めないため、**許可外 Origin からの CONNECT/SEND が拒否されることを確認する統合テスト**をフェーズ4のテスト項目に追加する(§11 参照)。

## 7. SUBSCRIBE 時点の認可

`SUBSCRIBE` フレームをインターセプトし、購読先(チャンネル/DM/ワークスペース)への現在のメンバーシップを検証する(非メンバーは拒否)。これが平時の認可実施点である。

### 7.1 `/user/queue/events` の SUBSCRIBE 許可(必須修正事項)

下記 §8 の SEND/SUBSCRIBE default-deny を素直に「チャンネル/DM/ワークスペース以外は拒否」と実装すると、個人宛通知の宛先である `/user/queue/events` への SUBSCRIBE も拒否されてしまい、通知機能そのものが動作しなくなる。そのため、SUBSCRIBE の認可ルールは以下の順序で明示する。

1. `/user/queue/events` への SUBSCRIBE は、**認証済みユーザーであれば常に許可**する(catch-all の deny より前に評価されるルールとして定義する)。
2. Spring の `UserDestinationMessageHandler` は `Principal#getName()` を使って宛先を `/user/{principalName}/queue/events` に解決するため、**ハンドシェイク時に設定する Principal の `getName()` が、`convertAndSendToUser()` 呼び出し時に渡す内部ユーザーIDと一致していることを保証する**(不一致だとサーバーからの通知プッシュが本人に届かない)。
3. チャンネル/DM/ワークスペーストピックへの SUBSCRIBE は本節冒頭の既存の認可チェックを適用する。
4. 上記のいずれにも一致しない SUBSCRIBE 宛先は拒否(default-deny)。

**受け入れテスト**:
1. 認証済みユーザーが自分の `/user/queue/events` を購読でき、サーバーから送った通知を受信できること。
2. 未認証状態での購読が拒否されること。
3. Principal 名と `convertAndSendToUser()` の宛先ユーザーIDの不一致が起きていないこと(通知が本人に届くことの確認で間接的に検証。**ここがズレると例外も出ずに通知だけが静かに消えるため、原因究明に最も時間を取られやすいバグである点に注意**)。
4. **他人の `/user/{他人のuserId}/queue/events` を明示的に指定して購読を試みても、`UserDestinationResolver` が認証済み Principal を使って宛先を書き換えるため自分のキューにしか解決されないこと**(=他人宛の通知を盗み見できないこと)。

## 8. SEND 宛先の default-deny

SUBSCRIBE 側の認可だけでは、悪意あるクライアントが直接 `SEND /topic/channels.{id}` のようなブローカー向け宛先にメッセージを送りつけ、サーバーが発行したかのような偽イベント(例: 偽の `MESSAGE_CREATED`)を他ユーザーへ配信させる余地が残る。Spring Security の WebSocket メッセージ認可設定(`AuthorizationManager` ベースの構成)で、以下を明示的なホワイトリスト方式(default-deny)で設定する。

- `SEND` は `/app/**` 宛のみ許可し、かつ認証済みユーザーに限定する(`/app/channels.{channelId}.typing` など、アプリ側の `@MessageMapping` ハンドラが受け口となるものだけ)。
- クライアントからの `SEND` を `/topic/**`・`/queue/**`・`/user/**` へ送ることは常に拒否する(これらはサーバーが `RealtimeEventPublisher`/`SimpMessagingTemplate` 経由でのみ発行する、クライアント発信不可の宛先)。
- `/app/**` 宛の SEND であっても、届いたペイロードに対して §9 のバリデーションとリソース認可(タイピングイベントなら対象チャンネル/DM のメンバーシップ確認)を必ず実施する。
- 上記のいずれにも一致しない `SEND`・`SUBSCRIBE` 宛先はすべて拒否する(明示的に許可したものだけを通す構成とし、暗黙の許可を残さない)。
- **`SimpMessageType.CONNECT`/`DISCONNECT`/`UNSUBSCRIBE`/`HEARTBEAT` は `permitAll()` として default-deny の対象から明示的に除外する**(`CONNECT` は §5 のハンドシェイク時 JWT 検証・§6 の Origin 検証で既に守られている)。Spring Security の WebSocket メッセージ認可で `anyMessage().denyAll()` を素直に書くと、これらメッセージタイプまで拒否されて STOMP 接続自体が確立しなくなる典型的な誤りがあるため、**default-deny の対象は `SEND` と `SUBSCRIBE` の宛先のみに限定する**。

**受け入れテスト**: クライアントが直接 `/topic/channels.{id}` へ SEND を試み拒否されること、偽装した `MESSAGE_CREATED` イベントが他ユーザーへ配信されないこと、通常の CONNECT/SUBSCRIBE/送受信フローが上記の制限下でも正常に動作することを確認する統合テストをフェーズ4に追加する。

## 10. キック時の強制切断(単一インスタンス設計)

### 10.1 不採用にした設計とその理由

- **案A(不採用)**: `MEMBER_REMOVED` を送ってクライアントが自主的に `unsubscribe()` する方式。悪意あるクライアントが無視すれば購読済みの非メンバーにメッセージが届き続けてしまうため不採用。
- **案B(不採用)**: `SessionConnectEvent` で `WebSocketSession` を保持する方式。STOMP の `SessionConnectEvent` は STOMP セッション情報のみを運び、生の `WebSocketSession` を渡さないため実装として成立しない。

### 10.2 採用した設計

- `WebSocketHandlerDecoratorFactory` を実装し、`WebSocketMessageBrokerConfigurer#configureWebSocketTransport` の `WebSocketTransportRegistration.addDecoratorFactory(...)` に登録する(登録先はここであり、`ServletServerContainerFactoryBean` ではない――そちらはバッファサイズやアイドルタイムアウトの設定用であってデコレータの登録先ではない)。このデコレータの `afterConnectionEstablished(WebSocketSession session)` / `afterConnectionClosed(WebSocketSession session, CloseStatus status)` は生の `WebSocketSession` を受け取れる(Spring の低レベル WebSocket API の正式なフック)。
- `afterConnectionEstablished` 時点で `session.getPrincipal()`(ハンドシェイク時に設定した認証済みユーザー)から `userId` を取得し、`SessionRegistry` Bean が持つローカルの `Map<String sessionId, WebSocketSession>` と `Map<UUID userId, Set<String sessionId>>` に登録、`afterConnectionClosed` で解除する。

### 10.3 キック確定は「DBコミット完了後」であることを実装で保証する(必須修正)

通常の `@Transactional` サービスメソッド内で `SessionRegistry` を直接呼ぶと、その呼び出しは実際にはトランザクションのコミット**前**に実行されてしまう。これだと (a) トランザクションが後でロールバックしても既に切断されてしまう、(b) 切断直後に即座に再接続したクライアントが、コミット前の(まだ有効なままの)メンバーシップを参照して再購読できてしまう、という2つの競合が起こり得る。

これを避けるため、キック確定処理は **`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`** で受けるイベントリスナーとして実装する。

- `WorkspaceService`/`ChannelService` はメンバーシップ削除のトランザクション内で `MemberKickedEvent` を `ApplicationEventPublisher` 経由で発行するだけに留める。
- 実際に `SessionRegistry` を参照して `session.close(CloseStatus.POLICY_VIOLATION)` を呼ぶ処理は、**トランザクションのコミットが実際に成功した後にのみ**実行される `@TransactionalEventListener` 側で行う(購読単位ではなく接続単位で切断――STOMP は1接続に複数購読を多重化するため)。
- 単一インスタンスなのでネットワーク越しの通知機構(Redis Pub/Sub 等)は不要。

**なぜ単一インスタンスでは `AFTER_COMMIT` だけで十分と言えるか**: 「コミット直後にプロセスが落ちたらイベントが飛ばないのでは」という疑問が当然出るが、**単一インスタンス構成ではプロセスが落ちれば同じメモリ上にある WebSocket セッション自体も同時に消える**(セッションは `SessionRegistry` を持つのと同じプロセスのメモリ上にしか存在しない)。したがって「コミットは成立したのに切断されない」という状態は単一インスタンスでは原理的に発生せず、`AFTER_COMMIT` イベントリスナーだけで完全に閉じる。この前提は複数インスタンス構成でなければ崩れないが、水平スケール対応は実施しないことが確定しているため、outboxパターン等の追加対応は不要。

### 10.4 切断後のクライアント挙動

- 切断前に(ベストエフォートで)`MEMBER_REMOVED` を `/user/queue/events` へ送り、行儀の良いクライアントには理由付きの通知を届ける。
- クライアントは STOMP の自動再接続で再接続するが、新しいハンドシェイクで JWT が再検証され、対象チャンネル/ワークスペースへの `SUBSCRIBE` は §7 の認可チェックにより拒否される(キック後は DB 上のメンバーシップが既に削除されているため)。

### 10.5 受け入れテスト(必須修正)

1. キック処理がロールバックした場合(例: 後続のバリデーションで例外が発生)は強制切断が発生しないこと。
2. キック成功後に即座に再接続を試みても、コミット後の(削除済みの)メンバーシップを参照するため再購読できないこと。
3. 「キック前に購読済み → キック → 新規メッセージを受信しないこと」を確認すること。

## 11. プレゼンス管理

- **単一インスタンス構成**: プロトタイプの `presence.ts` と同じ設計を踏襲し、`PresenceService` がローカルの `Map<UUID userId, Integer connectionCount>` で接続数を追跡する(同一ユーザーの複数タブ/デバイス接続を考慮)。
  - 最初の接続でオンラインに遷移し、全接続が切れた時点でオフラインに遷移する。
  - オンライン/オフライン遷移が発生したユーザーの全ワークスペースメンバーシップに対し、`/topic/workspaces.{workspaceId}.presence` へ `PRESENCE_UPDATED` イベントをブロードキャストする。
- **水平スケール対応(Redis共有プレゼンスへの切替)は検討した結果、実施しないことが確定している**(Renderが1インスタンス運用でマネージドRabbitMQも無く、本番で動かす先が無いため)。プレゼンス管理は単一プロセスのメモリ上での実装のまま継続する。

---

## 12. タイピングインジケーター

- クライアントは入力中に `/app/channels.{channelId}.typing`(または DM 相当の宛先)へ `SEND` する。
- サーバーの `TypingController`(`@MessageMapping` ハンドラ)は、送信者が対象チャンネル/DM のメンバーであることを検証したうえで、`/topic/channels.{channelId}`(または `/topic/dms.{dmId}`)へ `TYPING_UPDATE` イベントとしてブロードキャストする(送信者自身には配信しない)。
- タイピングイベントは永続化しない(揮発性のリアルタイムイベントのみ)。

## 13. 使用 STOMP フレーム一覧(まとめ)

| フレーム | 用途 | 認可 |
|---|---|---|
| CONNECT | 接続確立 | ハンドシェイク時 JWT 検証(§5)、`permitAll()`(§8) |
| DISCONNECT | 切断 | `permitAll()`(§8) |
| SUBSCRIBE | トピック/キュー購読 | §7(`/user/queue/events` は認証済みなら常時許可、それ以外はメンバーシップ検証、default-deny) |
| UNSUBSCRIBE | 購読解除 | `permitAll()`(§8) |
| SEND | `/app/**` へのクライアント発信 | §8(`/app/**` のみ許可、`/topic/**`/`/queue/**`/`/user/**` への直接 SEND は拒否) |
| HEARTBEAT | キープアライブ | `permitAll()`(§8) |

## 14. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| ハンドシェイク時の Cookie/JWT | 欠如・不正・期限切れの場合はハンドシェイクを拒否(REST の「空の SecurityContext で後続へ委譲」とは異なり、WebSocket ハンドシェイクは認証必須の入口であるため即時拒否する) |
| SUBSCRIBE 宛先 | §7・§8 のホワイトリストに従う。非メンバーのチャンネル/DM/ワークスペーストピックへの購読は拒否 |
| SEND 宛先 | `/app/**` 以外は拒否(§8) |
| タイピングペイロード | `channelId`/`dmId` の形式検証、サイズ上限(§9) |
| Origin | `WEB_ORIGIN` 由来の許可リストに一致しない場合は拒否(§6) |

## 15. セキュリティ仕様

- **Origin 検証が CSRF 相当防御の要**: WebSocket ハンドシェイクは Cookie が自動送信されるため、`setAllowedOriginPatterns` によるオリジン制限が Cross-Site WebSocket Hijacking を防ぐ唯一の防御層になる(§6)。本番でワイルドカード `*` を設定しないことを必須とする。
- **SUBSCRIBE 認可の抜け穴に対する明示的な例外規定**: `/user/queue/events` を default-deny の対象に含めてしまうと通知機能自体が壊れるため、認証済みユーザーへの許可を明示的な最優先ルールとして先に評価する設計とする(§7.1)。
- **SEND default-deny によるイベント偽装対策**: クライアントが `/topic/**`・`/queue/**`・`/user/**` へ直接 `SEND` できないようにすることで、偽の `MESSAGE_CREATED`/`REACTION_UPDATED`/`NOTIFICATION` 等のイベントを他ユーザーに配信させる攻撃を防ぐ(§8)。
- **キック確定のトランザクション整合性**: `@TransactionalEventListener(AFTER_COMMIT)` により、ロールバック時の誤切断・コミット前の再接続競合を防ぐ(§10.3)。
- **Principal 名の一致保証**: `/user/queue/events` の宛先解決は Principal の `getName()` に依存するため、ハンドシェイク時に設定する Principal と `convertAndSendToUser()` に渡すユーザーIDの型・値を完全に一致させる。この不一致は例外を出さずに通知が消える「サイレント障害」になるため、実装時とテスト時の両方で明示的に確認する(§7.1)。

---

## 16. 制約・前提条件

- STOMPブローカーとしてSpring標準のシンプルブローカー(インメモリ)を使用し、単一インスタンス構成を前提とする。
- RabbitMQ 外部ブローカーリレー・Redis 共有プレゼンス・キック通知配送の outbox 化は、水平スケール対応そのものを実施しないことが確定しているため導入しない。
- Render へのデプロイは単一インスタンス構成(`インフラ構成書.md` のデプロイ方針を参照)。
- Render は WebSocket 接続に固定のアイドルタイムアウト値を設けていないが、デプロイ・再起動時に強制切断される点はクライアント側の再接続ロジックで吸収する。

---

## 17. 対象外仕様

| 機能 | 理由 |
|------|------|
| ボイスチャンネル・音声/映像通信 | 要件定義書で明示的に対象外 |
| RabbitMQ 外部ブローカーリレー、Redis 共有プレゼンス、キック通知の outbox 化、共有アップロードボリューム | 水平スケール対応そのものを実施しないことが確定(`インフラ構成書.md` 参照) |
| メッセージ配信の Exactly-once 保証 | シンプルブローカー(インメモリ)構成のため、配信保証はベストエフォート。永続化された REST 経由の状態(DB)が最終的な正となる設計とし、リアルタイムイベントの取りこぼしはクライアントの再読み込み/再同期で補う |
