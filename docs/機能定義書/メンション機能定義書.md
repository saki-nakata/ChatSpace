# メンション機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

## 1. 機能概要

チャンネルメッセージ本文中の `@ユーザーID`(例: `@alice`)記法を抽出し、該当ユーザーに `MENTION` 通知を送る機能。あわせて、メッセージ入力中に `@` を入力した際の候補一覧を返す**メンション自動補完 API** も本機能の対象とする。

**最重要の設計制約**: メンション解決(通知対象の決定)は、メッセージ投稿**その時点の**ライブなチャンネルメンバーシップとのみ突合する。過去にチャンネルへ参加していた・現在パブリックチャンネルの一覧に名前が見えている、といった理由だけでは通知対象にしない。これはメンション経由でチャンネルの非メンバーへ「このチャンネルにこのユーザーIDの人がいる/いた」という存在情報を漏洩させないための対策であり、`.plans/java-spring-boot-redesign.md` §3 が明記する最優先の認可制約の一つである。自動補完 API も同じ制約を負う(§6 参照)。

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、メッセージ本文で `@ユーザーID` と書くことで特定のメンバーに通知を送りたい |
| US-02 | ユーザーとして、`@` を入力した際にそのチャンネルに実在するメンバーの候補が出てきてほしい |
| US-03 | ユーザーとして、自分がメンションされたらリアルタイムに気付きたい |
| US-04 | ユーザーとして、自分がメンションされたメッセージの本文がどれか一覧で確認したい |
| US-05 | チャンネルの非メンバーとして、自分がそのチャンネルの会話やメンバー構成について一切知らされないことを期待する(セキュリティ上の暗黙の期待) |

---

## 3. 機能詳細

### 3.1 メンション抽出

- メッセージ本文から正規表現 `@([a-zA-Z0-9_.-]{3,20})` (プロトタイプの `MENTION_REGEX` を1:1移植)でメンション候補のユーザーID(ハンドル)を抽出する。`USER_ID_REGEX` と同じ文字種・長さ制約であるため、ユーザーIDとして成立し得る文字列のみを候補とする。
- 抽出は `Message` エンティティへの永続化後、同一トランザクション(または直後の処理)で `MentionResolver`(`message` パッケージ)が実行する。

### 3.2 メンション解決(ライブなチャンネルメンバーシップとの突合)

- `MentionResolver` は抽出したユーザーID候補を、**投稿先チャンネルの現在の `ChannelMember` 一覧**(`ChannelMemberRepository` への都度クエリ)とのみ突合する。事前にキャッシュされたメンバー一覧やクライアントから送られた候補リストは信用しない。
- 一致しなかった候補(そのチャンネルの非メンバー、または存在しないユーザーID)は静かに無視する(エラーにはしない。Slack 同様、本文中の「メンションのように見える文字列」がすべて有効なメンションとは限らないため)。
- 投稿者自身への自己メンションは通知対象から除外する。
- 解決できたメンションは `Mention` エンティティ(`messageId`, `mentionedUserId`)として保存し、`MENTION` 種別の `Notification` を生成する(`通知機能定義書.md` 参照)。
- DM メッセージは本機能の対象外とする(DM は常に参加者2名のみで、メンションによる第三者への漏洩リスクが構造上存在しないため。プロトタイプでも `processMentionsForChannelMessage` はチャンネルメッセージのみに適用される)。

### 3.3 メンション自動補完(候補一覧取得 API)

- クライアントがメッセージ入力欄で `@` を入力すると、対象チャンネルのメンバー一覧から前方一致等で絞り込んだ候補を取得する API を呼び出す(新規機能。プロトタイプにはこの専用 API は無く、既存の「チャンネルメンバー一覧取得」を流用する形になるが、Java 版では明示的なメンション候補 API として切り出す)。
- 候補の絞り込み元は**対象チャンネルの `ChannelMember` のみ**とする。ワークスペース全体のメンバー一覧や、他チャンネルのメンバーを候補に含めてはならない(§6 参照)。
- 呼び出し元ユーザー自身がそのチャンネルのメンバーであることも当然の前提として検証する(非メンバーは候補取得自体ができない)。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| POST | `/workspaces/{workspaceId}/channels/{channelId}/messages` | メッセージ投稿(本文中の `@` を解析し、メンション解決・通知生成をサーバー側で自動実行) | 必要 |
| GET | `/workspaces/{workspaceId}/channels/{channelId}/mentions/candidates?q={prefix}` | メンション自動補完候補の取得(対象チャンネルのメンバーのみ) | 必要 |

**候補取得レスポンス例**

```json
{
  "candidates": [
    { "userId": "alice", "displayName": "Alice" },
    { "userId": "alice2", "displayName": "Alice2" }
  ]
}
```

投稿 API 自体のレスポンス(`MessageDTO`)は `mentionedUserIds` フィールドとして解決済みのメンション対象ユーザーID一覧を含む。詳細なスキーマは Swagger UI(`/swagger-ui.html`)を正とする。

## 5. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| メンション対象ユーザーIDの文字種・長さ | `USER_ID_REGEX`(英数字・`_`・`.`・`-`、3〜20文字)に合致しない文字列はそもそも抽出対象にならない |
| 存在しない/非メンバーのユーザーIDへのメンション | エラーにはせず、通知・`Mention` レコードを生成しない(静かに無視) |
| 自己メンション | 通知対象から除外(自分への通知は生成しない) |
| 候補取得 API の `q` パラメータ | 空文字・未指定時は絞り込みなしで先頭 N 件を返す(件数上限を設ける想定。上限値は実装計画書で確定) |
| 未認証ユーザーの候補取得 | 401 |

## 6. セキュリティ仕様

**メンション経由のメンバー漏洩防止(最重要・新規の受け入れテストとして追加する対象)**: プロトタイプの `notify.ts` (`processMentionsForChannelMessage`)にはこの制約に沿った実装(投稿先チャンネルの `ChannelMember` とのみ突合)が既に存在するが、`test/authorization.test.ts` では検証されていない(`.plans/java-spring-boot-redesign.md` の注記参照)。したがって新スタックへの移植にあたっては「既存の保証を引き継ぐ」のではなく、**新規の受け入れテストとして明示的に追加する**。具体的に守るべき不変条件は以下の通り。

1. **通知の生成範囲**: `@handle` がチャンネルの非メンバーのユーザーIDと一致していても、そのユーザーには通知も `Mention` レコードも生成されない。これにより「このユーザーIDの人物が存在する」という情報や「そのチャンネルで自分の名前が話題に上っている」という情報が非メンバーへ伝わらない。
2. **自動補完 API の絞り込み範囲**: `GET /workspaces/{workspaceId}/channels/{channelId}/mentions/candidates` は対象チャンネルの `ChannelMember` のみを候補として返す。ワークスペースメンバー全体やハンドル検索(`GET /users/lookup` 相当)を流用して「ワークスペース内の任意のユーザーID」を返してはならない。**候補一覧そのものが「このチャンネルの実際のメンバー構成」の情報源になってしまう**(候補に出てくる=メンバーである、という推測を許す)ため、絞り込みを誤ると本文投稿時のメンション解決以上に直接的な情報漏洩経路になる。
3. **ライブ性**: メンション解決・候補取得のいずれも、投稿/リクエストの都度その時点の `ChannelMember` テーブルを参照する。メッセージ投稿後にメンバーがキックされても過去のメンション自体が取り消されることはないが(通知はメッセージ投稿時点の状態で確定してよい)、新規のメンション解決・候補取得は常に最新のメンバーシップに基づく。
4. **プライベートチャンネルとの関係**: プライベートチャンネルでのメンションも同じ `MentionResolver` を通るため、非メンバーへの通知漏洩は原理的に発生しない(そもそも非メンバーはメンションの元になったメッセージ自体を閲覧できない)。

---

## 7. 制約・前提条件

- メンションはチャンネルメッセージのみを対象とし、DM メッセージは対象外(構造上メンバー漏洩リスクが無いため)。
- 1メッセージ内で同じユーザーIDを複数回メンションしても、通知・`Mention` レコードは1件に正規化する(プロトタイプの `Set` による重複排除を踏襲)。
- メンション記法はプレーンな `@ユーザーID` のみをサポートし、`@here`/`@channel` のような一括メンションはサポートしない。

---

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| `@here`/`@channel`/`@everyone` のような一括メンション | スコープ外(今回の要件定義書に含まれない) |
| メンション履歴の集計・分析 | スコープ外 |
| DM メッセージでのメンション | 構造上不要(常に相手が確定しているため) |

## 9. テスト

| 種別 | 内容 | 対応フェーズ |
|---|---|---|
| 新規受け入れテスト | 非メンバーのユーザーIDを含むメッセージを投稿しても、当該ユーザーに通知・`Mention` レコードが作成されないこと | フェーズ5 |
| 新規受け入れテスト | メンション自動補完 API が、対象チャンネルの非メンバーのユーザーIDを候補として返さないこと | フェーズ5 |
| 新規受け入れテスト | 非メンバーが `mentions/candidates` API を呼び出すと 404 になること(§6 参照) | フェーズ5 |
| 単体テスト | `MentionResolver` の重複排除・自己メンション除外ロジック | フェーズ5 |
| 統合テスト | 有効なメンションを含むメッセージ投稿後、対象ユーザーの `/user/queue/events` に `MENTION` 通知が届くこと | フェーズ5 |

詳細は `docs/テスト設計書.md` を参照。
