# 認証機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15

> 本ドキュメントは `.plans/java-spring-boot-redesign.md`(以下「計画書」)§3「認証・認可レイヤー」を正式文書化したものである。移植元はプロトタイプ(Node.js/Hono)の `apps/api/src/routes/auth.ts`・`apps/api/src/auth/{jwt,password,middleware}.ts`。

---

## 1. 機能概要

ユーザーID(ログインハンドル)とパスワードによるステートレス認証。Auth.js のような外部認証ライブラリは使わず、Spring Boot 上で自前実装する。

- **メール認証は不要**。ユーザーID・パスワード・表示名のみで即時アカウント作成する
- 認証状態は **HS256 署名の JWT** を **HttpOnly Cookie**(`chatspace_token`)に保存して表現する。サーバー側にセッションストア・DBセッションテーブルは持たない(ステートレス)
- JWT の発行・検証は **Nimbus JOSE+JWT**(`com.nimbusds:nimbus-jose-jwt`)を直接使う `JwtService` が担う。Spring Security の OAuth2 Resource Server 自動構成(外部IdP発行トークンの検証を前提とする機構)は、本アプリが自前でトークンを発行するため採用しない
- パスワードは **bcrypt(コストファクタ12)** でハッシュ化し `PasswordService` に集約する
- REST・WebSocket(STOMPハンドシェイク)の両方が同じ Cookie・同じ `JwtService` を使って認証する(検証タイミングが異なるだけ)。WebSocket 側の詳細は `リアルタイム通信機能定義書.md` を参照

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | 新規ユーザーとして、ユーザーID・パスワード・表示名を入力してアカウントを作成したい |
| US-02 | 登録済みユーザーとして、ユーザーID・パスワードでログインしたい |
| US-03 | ログイン中のユーザーとして、ログアウトしてセッションを終了したい |
| US-04 | ログイン中のユーザーとして、自分の現在の認証状態・プロフィール概要を確認したい |
| US-05 | 未認証ユーザーとして、保護対象の API に Cookie 無し/不正な Cookie でアクセスした場合、公開API は影響を受けず、保護対象API のみ 401 になってほしい |

## 3. 機能詳細

### 3.1 ユーザー登録(signup)

- 入力項目:ユーザーID(ログインハンドル)・パスワード・表示名
- 処理フロー:
  1. リクエストボディを Bean Validation で検証(§5)
  2. `userId` の重複チェック(既存ユーザーがいれば 409)
  3. `PasswordService` で bcrypt(コスト12)ハッシュ化して `User` を作成
  4. 内部ユーザーID(`User.id`)を `sub` claim とする JWT を発行し、`chatspace_token` Cookie にセットする
  5. 作成したユーザー情報(パスワードハッシュを除く)を 201 で返す
- 異常系:
  - `userId` 重複 → **409**「このユーザーIDは既に使用されています。」(レビュー指摘により400から訂正。既存リソースとの衝突を表す409で、チャンネル名重複[チャンネル機能定義書]・シーケンス図の記述と統一する)
  - バリデーションエラー → 400

### 3.2 ログイン(login)

- 入力項目:ユーザーID・パスワード
- 処理フロー:
  1. `userId` でユーザーを検索
  2. bcrypt でパスワード照合(§6「タイミング攻撃対策」参照)
  3. 照合成功時に JWT を発行し Cookie にセット
  4. ユーザー情報を 200 で返す
- 異常系:
  - ユーザー不存在、またはパスワード不一致 → いずれも同一メッセージの 400「ユーザーIDまたはパスワードが正しくありません。」(ユーザーID列挙を防ぐため、不存在と不一致を区別しない)

### 3.3 ログアウト(logout)

- `chatspace_token` Cookie を削除するのみ(`path=/` を指定して削除し、確実に消えるようにする)
- 認証済みであることを要求しない(未認証状態で呼んでも 204 を返す。プロトタイプの挙動を踏襲)
- サーバー側のトークン失効・リフレッシュトークンの仕組みは持たない。発行済み JWT はログアウト後も有効期限(7日)内は理論上有効なままだが、これはプロトタイプからの既知の設計選択を引き継ぐものであり新規のギャップではない(§7)

### 3.4 現在のユーザー情報取得(me)

- `GET /auth/me` は認証必須。`SecurityContext` のユーザーIDでユーザーを検索し返す
- 対象ユーザーが(理論上)存在しない場合は 404 相当のサーバーエラーとして扱う(通常運用では発生しない)

### 3.5 リクエスト認証の役割分担(公開エンドポイントとの整合)

`JwtAuthenticationFilter`(`OncePerRequestFilter`)は **Cookie の有無・正当性だけで即 401 を返さない**。正しい役割分担は次の通り:

1. Cookie が無い、または JWT が不正・期限切れの場合、フィルターは 401 を返さず `SecurityContext` を空のまま後続のフィルタチェーンへ処理を委譲する
2. `/auth/signup`・`/auth/login`・`/health` 等の公開エンドポイントは Spring Security の認可設定で `permitAll()` としているため、`SecurityContext` が空でもそのままハンドラに到達できる
3. `/workspaces/**` 等の保護対象エンドポイントは、`SecurityContext` が空のままアクセスされた場合、Spring Security の `AuthenticationEntryPoint` が 401 を返す(認証チェック自体は Spring Security の認可フィルタが行い、`JwtAuthenticationFilter` は「Cookie があれば検証してコンテキストにセットするだけ」の役割に限定する)
4. 公開エンドポイントに**不正な**(改ざん・期限切れの)Cookie が付いていた場合も、`JwtAuthenticationFilter` は検証失敗を無視して `SecurityContext` を空のまま先へ進める(公開エンドポイントの可用性を損なわない)

この設計により「トークン欠如時は即401」という誤り(公開エンドポイントを含む全リクエストが401になってしまう)を避ける。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| POST | `/auth/signup` | ユーザー登録(即時ログイン状態になる) | 不要 |
| POST | `/auth/login` | ログイン | 不要 |
| POST | `/auth/logout` | ログアウト(Cookie削除のみ) | 不要 |
| GET | `/auth/me` | 現在のユーザー情報取得 | 必要 |

## 5. バリデーション仕様

Bean Validation(`@Valid` + `@NotBlank`/`@Size`/`@Pattern`)で、プロトタイプの Zod スキーマ(`packages/shared/src/schemas.ts`)の制約を1:1で再現する。OpenAPI(springdoc)はこのアノテーションから制約情報も抽出する。

| 項目 | 制約 | 備考 |
|------|------|------|
| ユーザーID(`userId`) | 必須・`^[a-zA-Z0-9_.-]{3,20}$` | 英数字・`_`・`.`・`-` のみ、3〜20文字。ログインハンドル・`@メンション`にも使用 |
| パスワード | 必須・8文字以上・**UTF-8バイト列で72バイト以下** | **(レビュー指摘により修正)** bcryptの入力長制限は「72文字」ではなく「72バイト」であり、日本語等のマルチバイト文字は1文字で2〜4バイトを消費するため、「72文字以下」という文字数ベースの上限では実質的に72バイトを超える入力を許してしまい、超過分が無音で切り捨てられて異なるパスワードが同一ハッシュになり得る。`@Size`ではなくカスタムバリデータで`password.getBytes(StandardCharsets.UTF_8).length <= 72`を検証する |
| 表示名(`displayName`) | 必須・1〜50文字 | |
| ログイン時ユーザーID/パスワード | 必須(空文字不可) | 形式チェックはしない(存在有無を漏らさないため、登録時と同じ正規表現チェックは行わない) |

## 6. セキュリティ仕様

| 項目 | 仕様 |
|------|------|
| パスワードハッシュ | bcrypt、コストファクタ **12**。`PasswordService` に集約 |
| タイミング攻撃対策 | ログイン時、ユーザーが存在しない場合でも**固定のダミーハッシュ**に対して bcrypt 照合を必ず実行する。存在有無による応答時間差を無くし、ユーザーID列挙を防ぐ(プロトタイプの `DUMMY_PASSWORD_HASH` パターンを踏襲) |
| JWT 署名 | **HS256**。鍵は環境変数 `JWT_SECRET` から読み込む。実装は **Nimbus JOSE+JWT** を直接使用(OAuth2 Resource Server 自動構成は不採用) |
| JWT 有効期限 | **7日間** |
| JWT claim | `sub` = 内部ユーザーID(`User.id`)。ログインハンドルではなく内部IDを使う(ハンドル変更機能を将来追加してもトークンが無効化されないようにするため) |
| Cookie 属性 | 名前 `chatspace_token`。`HttpOnly; SameSite=Lax; Secure`(本番のみ、ローカル開発の http では無効化)、`path=/`、有効期限7日 |
| 公開エンドポイントの扱い | `JwtAuthenticationFilter` は Cookie 欠如・不正時に即401を返さず `SecurityContext` を空のまま委譲する(詳細は §3.5)。認可判定自体は Spring Security の認可フィルタ・`AuthenticationEntryPoint` が行う |
| Spring Security 全体構成 | `SessionCreationPolicy.STATELESS`。CSRF保護は無効化(Cookie認証 + `SameSite=Lax` を主防御とする方針。根拠・前提条件の詳細は `docs/インフラ構成書.md`)。`/auth/**`・`/health` は `permitAll()`、それ以外は認証必須 |
| ログアウト | Cookie削除のみ。サーバー側のトークン失効機構は持たない(既知の設計選択、§7) |
| WebSocket 認証との関係 | STOMP ハンドシェイク時も同じ Cookie・同じ `JwtService` で検証する。認証の実体は REST と完全共通(詳細は `リアルタイム通信機能定義書.md`) |

## 7. 制約・前提条件

- ~~認証のレート制限(ブルートフォース対策)はプロトタイプ同様**未実装**~~ → **フェーズ12で実装済み**。`AuthRateLimiter`(`com.chatspace.api.ratelimit`)が「試行対象のユーザーID + クライアントIP」単位で連続失敗を数え、既定で15分ウィンドウ内に5回失敗すると15分間 `429 Too Many Requests`(`Retry-After` ヘッダ付き)を返す。ブロック中は正しいパスワードでもパスワード照合自体を行わない。ログイン成功でカウンタはリセットされる
  - キーにユーザーIDとIPの両方を含める理由: IP単独だと同一NAT配下の無関係な利用者を巻き込み、ユーザーID単独だと攻撃者が任意のアカウントを恒久的にロックアウトできてしまう(DoS)ため
  - 上限値・ウィンドウ・ブロック時間は環境変数(`AUTH_RATE_LIMIT_*`)で調整可能
  - **単一インスタンス前提のインメモリ実装**のため、水平スケール時は実効上限がインスタンス数倍になる。共有ストアへの移行はフェーズ13の検討事項
- JWT の即時失効・リフレッシュトークンの仕組みは持たない。ログアウト後も発行済みトークンは有効期限(7日)まで理論上有効(プロトタイプからの既知の設計選択の継続、新規のギャップではない)
- `SameSite=Lax` による CSRF 相当防御は、フロントエンドとバックエンドが**同一 registrable domain(eTLD+1)** であることが前提。本番でフロントとAPIが別ドメインになる場合はこの前提が崩れるため、`SameSite=None; Secure` + 別途 CSRFトークン方式へ切り替える判断が必要(本番のドメイン構成確定後にフェーズ12で再確認する)
- ローカル開発(`localhost:5173` / `localhost:8080` 想定)は host が同一のため `SameSite=Lax` の前提を満たす

## 9. テスト

`test/authorization.test.ts` からのポート対象ではないが、計画書§10のフェーズ表に基づき以下を実施する(フェーズ1)。

| # | テストケース | 確認内容 |
|---|------------|---------|
| 1 | JWT 発行・検証の単体テスト | `JwtService` が正しい `sub` claim・7日有効期限で署名し、改ざん・期限切れトークンを拒否すること |
| 2 | signup → 自動ログイン | 登録後にCookieがセットされ `/auth/me` が本人情報を返すこと |
| 3 | login 成功/失敗 | 正しい認証情報でCookieが発行されること、誤ったユーザーID・パスワードで同一メッセージの400が返ること |
| 4 | タイミング攻撃対策 | ユーザー不存在時もダミーハッシュに対する bcrypt 照合が実行されること(実装の単体テストとして、不存在時に bcrypt 呼び出しがスキップされないことを検証) |
| 5 | logout | Cookie が削除されること、未認証状態で呼んでも204が返ること |
| 6 | 公開エンドポイントの整合性 | Cookie無し/不正Cookieで `/auth/signup`・`/auth/login`・`/health` が401にならないこと、`/workspaces` 等の保護対象は401になること |
| 7 | Cookie属性 | `HttpOnly`・`SameSite=Lax`・(本番相当プロファイルで)`Secure` が付与されること |
