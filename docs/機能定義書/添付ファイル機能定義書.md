# 添付ファイル機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

## 1. 機能概要

チャンネル/DM メッセージに画像・動画ファイルを添付する機能。アップロード時にファイルの実データ(先頭バイト・マジックナンバー)から MIME タイプを判定し、クライアントが送ってくる `Content-Type` は一切信用しない。配信(取得)エンドポイントは、要求される都度「そのファイルが紐づくメッセージのチャンネル/DM に、要求者が現在も参加しているか」を再検証する**ライブ権限再チェック**を行う。

プロトタイプの `file-signature.ts`(マジックバイト判定)・`uploads.ts`(アップロード/配信)のロジックをそのまま Java に移植する(外部ライブラリなし)。

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、チャンネル/DM に画像・動画を添付して投稿したい |
| US-02 | ユーザーとして、他のメンバーが投稿した添付ファイルを表示・再生したい |
| US-03 | ユーザーとして、許可されていない形式のファイルを誤ってアップロードしても弾かれてほしい |
| US-04 | ユーザーとして、極端に大きいファイルのアップロードでサーバーに負荷をかけたくない(上限を超えたら早期に拒否されてほしい) |
| US-05 | ユーザーとして、自分が既にキックされたチャンネル/DM の添付ファイルには、URL を知っていてもアクセスできないと確信したい |

## 3. 機能詳細

### 3.1 アップロード

- `POST /uploads` に `multipart/form-data` で `file` フィールドを送信する。
- サーバーはファイル実データの先頭バイトからマジックナンバー判定を行い(PNG/JPEG/GIF/WEBP/MP4/WEBM の固定シグネチャ、`file-signature.ts` を1:1移植した `MimeSniffer` クラスで判定)、許可された MIME タイプ(`ALLOWED_ATTACHMENT_MIME_TYPES`)と一致しない場合は 400 を返す。
- 保存ファイル名(`storageKey`)は `UUID.randomUUID()` + **検出 MIME から決めた固定拡張子**で生成する。クライアントが送ってきた元のファイル名や拡張子は保存パスの決定に一切使わない(パストラバーサル対策)。元のファイル名は `fileName` として表示用に別途保持する。
- 保存先は`AttachmentStorage`抽象化(`chatspace.storage.type`)を経由する。既定はローカルディスク(`chatspace.upload-dir`、`LocalDiskAttachmentStorage`)。Renderは無料枠に永続ディスクが無く再デプロイのたびにファイルが失われるため、本番は Cloudflare R2(S3互換、`S3AttachmentStorage`)を使う(フェーズ13で実施済み、詳細は `インフラ構成書.md` §7.1)。

### 3.2 配信(取得)

- `GET /uploads/{storageKey}` で取得する。`storageKey` は正規表現(`^[A-Za-z0-9_-]+\.[a-z0-9]+$` 相当)で形式を検証したうえで、`AttachmentStorage.exists()`(本文を転送しない軽量な存在確認。ローカルディスク実装はパス正規化後に保存ディレクトリ配下であることを再確認、オブジェクトストレージ実装は`HeadObject`)で存在を確認してから、ライブ権限再チェックへ進む。
- `Attachment` が特定のメッセージに紐づいている場合(`messageId IS NOT NULL`)、そのメッセージの `channelId`/`dmId` に対して**要求の都度**メンバーシップを再検証する(§6 参照)。ライブ権限再チェックに成功した場合のみ`AttachmentStorage.load()`で本文を取得する(認可拒否されるリクエストのたびにオブジェクトストレージへ本文転送させないための順序、`インフラ構成書.md` §7.1)。
- `Attachment` がまだどのメッセージにも紐づいていない場合(`messageId IS NULL`、アバター画像またはメッセージ送信前のプレビュー中のファイル):
  - いずれかのユーザーの現在のアバター画像として使われていれば、認証済みユーザー全員に閲覧を許可する(アバターは `UserDTO` 経由で誰でも見える情報のため、画像本体も同等に扱う)。
  - それ以外(投稿前のプレビュー段階)は、アップロード本人のみ閲覧可能とする。
- レスポンスの `Content-Type` は**サーバーが検出した MIME タイプ**を使用する(アップロード時にクライアントが申告した値やファイル名の拡張子は使わない)。`X-Content-Type-Options: nosniff` を付与し、ブラウザによる MIME スニッフィングを無効化する。

### 3.3 アップロードサイズ上限の多層防御

Bean Validation はリクエスト DTO のフィールド検証であり、**multipart 解析より前段の巨大リクエストそのものを防ぐことはできない**。以下の実装を必須の多層防御として行う。

1. **(必須)** `application.yml` の `spring.servlet.multipart.max-file-size` を、プロトタイプと同じ **25MB**(`MAX_ATTACHMENT_SIZE_BYTES`)に設定する。**`max-request-size` は同じ25MBちょうどではなく、余裕を持たせた値(例: 26MB)に設定する**(レビュー指摘により修正: `max-request-size` はリクエスト全体のサイズであり、multipartの境界文字列やヘッダー等のオーバーヘッド分だけファイル本体より必ず大きくなる。両方を同じ25MBに設定すると、ファイル自体はちょうど25MB以下でもリクエスト全体が25MBを超えて拒否される誤検知が起こり得る)。multipart 解析エンジンのレベルで上限超過リクエストを早期に拒否し、巨大リクエストがディスクにスプールされてから弾かれる事態を避ける。
2. **(必須)** サービス層でも `MultipartFile#getSize()` により実際のサイズを再確認する(設定ミスや将来の設定変更に対する多層防御)。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| POST | `/uploads` | ファイルアップロード(`multipart/form-data`、`file` フィールド) | 必要 |
| GET | `/uploads/{storageKey}` | ファイル配信(取得の都度ライブ権限再チェック) | 必要 |

**アップロードレスポンス例**

```json
{
  "attachment": {
    "id": "att_123",
    "url": "/uploads/8f1c...-a1.png",
    "fileName": "screenshot.png",
    "mimeType": "image/png",
    "sizeBytes": 204800,
    "kind": "IMAGE"
  }
}
```

詳細なスキーマは Swagger UI(`/swagger-ui.html`)を正とする。

## 5. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| ファイルサイズ | 25MB 以下(`spring.servlet.multipart.max-file-size`/`max-request-size` による事前拒否 + サービス層での `getSize()` 再確認、二重チェック) |
| ファイル形式(MIME) | サーバー側でマジックバイトから検出した MIME が `ALLOWED_ATTACHMENT_MIME_TYPES`(画像: png/jpeg/gif/webp、動画: mp4/webm)に含まれること。クライアント申告の `Content-Type` は検証に使わない |
| `storageKey` の形式(配信時) | 固定パターン(`^[A-Za-z0-9_-]+\.[a-z0-9]+$`)に一致しない場合は 404(存在を秘匿) |
| `file` フィールド未指定 | 400 |
| 未認証ユーザーのアップロード/取得 | 401 |

## 6. セキュリティ仕様

- **マジックバイト検証(クライアント申告 MIME の不信任)**: ブラウザが送ってくる `Content-Type`(`File.type`)は偽装可能なため、拡張子・保存先の決定やレスポンスの `Content-Type` の決定にはそのまま使わず、必ずサーバー側が実データの先頭バイトから判定した MIME のみを正として扱う(`file-signature.ts` → `MimeSniffer` への移植)。
- **パストラバーサル対策**: (1) アップロード時、保存ファイル名はクライアント指定の名前・拡張子を一切使わず `UUID` + 検出 MIME 由来の固定拡張子で生成する。(2) 配信時、`storageKey` を正規表現で検証したうえで、パス正規化後に保存ディレクトリ配下であることを再確認してから読み出す(二重防御)。
- **ライブ権限再チェック(最重要・新規の受け入れテストとして追加する対象)**: `.plans/java-spring-boot-redesign.md` §3 が明記する通り、`UploadService.serve()` は取得の都度、所属メッセージのチャンネル/DM に対してライブな権限チェックを再実行する(アップロード時点のみのチェックにしない)。プロトタイプの実装コード自体にはこのロジックが存在するが、`test/authorization.test.ts` では検証されていない(既存テストが守る5点に含まれない)ため、新スタックでは**新規の受け入れテストとして明示的に追加する**。具体的な確認事項:
  - アップロード後にチャンネル/DM からキック(または退出)されたユーザーが、以後その添付ファイルを `GET /uploads/{storageKey}` で取得できなくなること。
  - **ワークスペースキック後の DM 添付ファイル取得不可**: DM の添付ファイル配信は `DmAuthorizationService.requireDmAccess()` を経由するため、DM 参加者チェックに加えて現在有効な `WorkspaceMember` であることも必須条件となる。ワークスペースからキックされたユーザーは、既知の `dmId`/`storageKey` を知っていても DM 添付ファイルを取得できない(`.plans/java-spring-boot-redesign.md` §3 の「DM 権限にワークスペースメンバーシップの再確認を追加」で修正する実在ギャップの一部)。プロトタイプの `uploads.ts:108` は `requireDMAccess` 呼び出し時に `workspaceId` すら渡しておらず、この再確認が漏れていた実装だった点を踏まえ、新スタックでは `DmAuthorizationService.requireDmAccess(dmId, userId, workspaceId)` を必ず `workspaceId` 付きで呼ぶ。
- **アバター画像の扱い**: `messageId IS NULL` かつ「いずれかのユーザーの現在のアバターとして使われている」ファイルは、認証済みユーザー全員に公開してよい(アバターは `UserDTO` 経由で誰でも見える情報のため)。それ以外の `messageId IS NULL` ファイル(投稿前のプレビュー)はアップロード本人のみ閲覧可とする。
- **MIME スニッフィング対策**: レスポンスに `X-Content-Type-Options: nosniff` を付与し、ブラウザが実際のファイル内容から `Content-Type` を独自に推測して意図しない挙動(例: HTML として解釈し XSS を誘発)を起こさないようにする。
- **ウイルススキャンは対象外**: マジックバイト検証のみを実施し、ウイルス・マルウェアスキャンは行わない(プロトタイプから継続する既知の制約、§7 参照)。

## 7. 制約・前提条件

- 保存先はローカルディスク実装(開発/テスト用、既定)と Cloudflare R2(S3互換オブジェクトストレージ、本番用)を`chatspace.storage.type`で切り替え可能(フェーズ13で実施済み、`AttachmentStorage`抽象化、詳細は `インフラ構成書.md` §7.1)。
- ファイルサイズ上限は 25MB(`MAX_ATTACHMENT_SIZE_BYTES`)。
- 許可される MIME タイプは画像(png/jpeg/gif/webp)と動画(mp4/webm)のみ。
- 添付ファイルのウイルス・マルウェアスキャンは実施しない(マジックバイト検証のみ、プロトタイプから継続)。

## 8. 対象外仕様

| 機能 | 理由 | 優先度・備考 |
|------|------|------|
| ウイルス・マルウェアスキャン | スコープ外。マジックバイト検証のみ継続 | 今回のスコープ外(継続的な既知のギャップ) |
| メッセージに紐付かないまま一定期間放置された未使用アップロード(`messageId IS NULL`)の定期クリーンアップ | 実装コストに対して当初は優先度低と判断した | **現在も未実装**。ただし公開デモ化により脅威モデルが変わっており、認証さえ通れば無制限にストレージを消費できる経路として残っている(下記§8.1参照) |
| アップロード回数制限・ユーザー別のストレージ容量上限 | 当初は非公開前提だったため未検討 | **未実装**。認証系(ログイン・新規登録)にはIP単位のレート制限があるが、アップロードには無い(下記§8.1参照) |
| 画像のサムネイル生成・動画のトランスコード | スコープ外 | - |
| ファイルの複数添付上限の高度な制御(枚数制限等) | スコープ外 | 実装計画書で必要に応じて確定 |

> **対象外から外れた項目**: 「DB への `Attachment` レコード保存失敗時にストレージ側のオブジェクトを削除する後始末処理」は当初この表に未実装として記載していたが、2026-08-16のレビュー指摘を受けて **実装済み**(`UploadService#registerRollbackCleanup`。トランザクションがコミット以外で完了した場合にオブジェクトを削除する)。

### 8.1 公開デモ運用に伴う既知のリスク

公開URL(`https://chatspace-ydxk.onrender.com`)で誰でも新規登録できる構成にしたことで、以下が現実的なリスクとして残っている。

| リスク | 現状 |
|------|------|
| 自動化されたアカウント大量生成 | **対応済み**。新規登録にクライアントIP単位のレート制限を追加(認証機能定義書§7) |
| 認証後の反復アップロードによるストレージ濫用 | **未対応**。アップロード回数・ユーザー別容量とも上限が無い |
| 未使用アップロード(`messageId IS NULL`)の蓄積 | **未対応**。定期クリーンアップが無い |
| アップロード時のヒープ負荷 | **未対応**。`UploadController` はファイル全体を `byte[]` に読み込むため、25MBの並列アップロードでヒープ使用量が増える |
| ウイルス・マルウェア | **対象外**(上表のとおり継続)。READMEで「本物の個人情報を登録しないこと」と告知している |

## 9. テスト

| 種別 | 内容 | 対応フェーズ |
|---|---|---|
| 単体テスト | `MimeSniffer` のマジックバイト判定(PNG/JPEG/GIF/WEBP/MP4/WEBM、非対応形式の拒否) | フェーズ7 |
| バリデーションテスト | 25MB を超えるリクエストが multipart 解析レベルで拒否されること(`max-file-size`/`max-request-size`) | フェーズ7 |
| 新規受け入れテスト | 添付ファイルのライブ権限再チェック: アップロード後にチャンネルからキックされたユーザーが取得できなくなること | フェーズ7 |
| 新規受け入れテスト | ワークスペースキック後、DM 添付ファイルを取得できないこと | フェーズ7 |
| セキュリティテスト | `storageKey` にパストラバーサル文字列(`../` 等)を含むリクエストが 404 で拒否されること | フェーズ7 |
| セキュリティテスト | 拡張子を偽装したファイル(例: `.png` 拡張子だが中身が実行ファイル)がマジックバイト検証で拒否されること | フェーズ7 |

詳細は `docs/テスト設計書.md` を参照。
