# メッセージング機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15

> 本ドキュメントは `.plans/java-spring-boot-redesign.md`(以下「計画書」)§2・§3・§7を正式文書化したものである。移植元は `apps/api/src/lib/messages-service.ts`・`apps/api/src/routes/{channel-messages,dm-messages}.ts`。

---

## 1. 機能概要

チャンネル・DM共通のメッセージ機能。投稿・編集(論理削除ではなく本文更新)・削除(論理削除)・スレッド返信・絵文字リアクションを扱う。Markdown記法の**レンダリング**はクライアント側の責務であり、バックエンドは入力値の検証のみを行う。

- チャンネルメッセージとDMメッセージは同一の `MessageService`/`MessageScopeGuard` を共有する(プロトタイプの `messages-service.ts` を1:1移植)
- 呼び出し元の「URLスコープ(channelId/dmId)へのメンバーシップ」チェックは、それぞれ `ChannelAuthorizationService`/`DmAuthorizationService`(チャンネル機能定義書・DM機能定義書を参照)が担う。本ドキュメントは、その後段で行う **「指定された `messageId` が実際にそのスコープに属するか」の検証(`MessageScopeGuard`、confused-deputy対策)** と、メッセージ自体のCRUD・スレッド・リアクション仕様に焦点を当てる

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | チャンネル/DMメンバーとして、メッセージを投稿したい |
| US-02 | 投稿者として、自分のメッセージを編集・削除したい(他人のメッセージは編集・削除できない) |
| US-03 | チャンネル/DMメンバーとして、メッセージにスレッド返信したい |
| US-04 | チャンネル/DMメンバーとして、メッセージに絵文字リアクションを付けたり外したりしたい |
| US-05 | チャンネル/DMメンバーとして、Markdown記法(太字・リスト・コードブロック等)で見やすく投稿したい |
| US-06 | 検索結果から特定のメッセージへジャンプし、前後の文脈を見たい |
| US-07 | 攻撃者として、自分が参加している別のチャンネル/DMのURLに、権限外のメッセージIDを組み合わせて渡しても、内容を読み取れないようにしてほしい |

## 3. 機能詳細

### 3.1 メッセージ投稿

- 入力:本文(1〜4000文字)、任意の返信先 `parentId`、任意の添付ファイルID配列(最大10件)
- 処理:
  1. `parentId` 指定時、返信先メッセージが実在し**同一スコープ(channelId/dmId)に属すること**を検証(不一致は400「返信先のメッセージが不正です。」— 存在自体は呼び出し元がスコープメンバーである前提のもとでの整合性エラーなので400とする。存在しない場合は404)。**さらに、返信先メッセージ自身の `parentId` が `NULL`(トップレベルメッセージ)であることを検証する**(レビュー指摘により追加: UIはSlack同様1階層のスレッドのみを前提としており、返信への返信[2階層目]を許すとUIから到達不能なメッセージが生成されてしまう。返信先が既に返信[`parentId`が非NULL]である場合は400「スレッド内の返信にはさらに返信できません。」を返す)
  2. 添付ファイルID指定時、各添付ファイルが実在し、**アップロード者が投稿者本人であること**、**未使用(いずれのメッセージにも未添付)であること**を検証(いずれかの条件を満たさない場合は403または400)
  3. メッセージを作成
  4. チャンネル投稿の場合:メンション処理(`メンション機能定義書.md`)、返信の場合はスレッド返信通知を送信
  5. DM投稿の場合:相手ユーザーへDM受信通知を送信
  6. 作成したメッセージをリアルタイムに配信(`/topic/channels.{channelId}` または `/topic/dms.{dmId}`)

### 3.2 メッセージ編集

- 投稿者本人のみ実行可(それ以外は403)
- 論理削除済み(`deletedAt` が非null)のメッセージは404として扱う(既に削除済みのものへの編集は「存在しない」と同じ扱い)
- `editedAt` を更新し、リアルタイムに配信

### 3.3 メッセージ削除(論理削除・tombstone方式)

- 投稿者本人のみ実行可(それ以外は403)
- 既に削除済みの場合(削除・編集・リアクション等の**書き込み系操作**の対象として)は404
- `deletedAt` に現在時刻をセットするのみ(物理削除しない)
- **表示方針(レビュー指摘により統一、tombstone方式)**: 削除済みメッセージは行ごと非表示にするのではなく、行を残したまま本文を伏せて返す(いわゆるtombstone)。**一覧取得(`listMessages`)・スレッド返信取得(`listThreadReplies`)・コンテキスト取得(`getMessageContext`)はいずれも `deletedAt` の有無で行を除外しない**。DTOへの変換時に、`deletedAt` が非nullなら `body` を空文字またはプレースホルダに置き換えて返し、クライアント側(画面設計書 S-06)が「このメッセージは削除されました」という表示に変換する。この方式を採る理由は2点: (1) 一覧を再読み込みした際も削除表示が維持される、(2) スレッドの**親メッセージ**が削除された場合に行ごと除外すると、残っている返信群が取得できなくなる(親を軸にwindowを組む`getMessageContext`が破綻する)ため、親メッセージも tombstone として残す必要がある
- **`deletedAt IS NULL` による除外が必要なのは検索(`検索機能定義書.md`)のみ**であり、一覧・スレッド・コンテキスト取得には適用しない。DB設計書の「全クエリで`deletedAt IS NULL`を明示する」という記述は検索クエリを指すものとして限定する(§6参照)
- リアルタイムに削除イベント(`MESSAGE_DELETED`、本文を含まない)を配信

### 3.4 スレッド返信

**ページネーション方針を確定(レビュー指摘により修正)**: 当初「投稿日時昇順で全件返す」としていたが、これは §6「ページネーション方針」の複合カーソル方針と矛盾していた(全件返すなら本来カーソルは不要なはず)。以下の通り統一する。

- `listThreadReplies` は指定した親メッセージIDの直接の返信を、投稿日時昇順(古い順)で**初期20件**返す。`(createdAt, id)` の複合カーソルでページングし、レスポンスに `nextCursor`(さらに新しい返信がある場合)を含める
- UI(スレッドパネル、画面設計書 S-07)は「さらに20件の返信を読み込む」ボタンで追加取得する。ボタンの文言は、親メッセージの返信数(`replyCount`)から残件数を正確に算出できる場合のみ「さらにN件」とし、算出できない場合は単に「さらに返信を読み込む」とする
- WebSocket経由で新着返信を受信した場合は、取得済み返信一覧の**末尾に追加**する(先頭挿入ではない。返信は古い順表示のため)
- 初期20件・追加読み込みという方式を採る理由は「Slackと同じだから」ではなく(公式UI仕様として確認しづらいため)、**スレッドパネルという横幅の狭いUIでは、全件を一度に描画するより段階的に読み込む方が操作しやすい**という理由に基づく
- 親メッセージの一覧取得(`listMessages`)は常に `parentId IS NULL`(トップレベル)のみを対象とし、返信はスレッド展開時に別APIで取得する
- 返信先メッセージ自体のスコープ検証は §3.1 手順1、`messageId` を受け取る他の全エンドポイントの検証は §6「MessageScopeGuard」を参照

### 3.5 絵文字リアクション

- `(messageId, userId, emoji)` の一意制約でトグル動作:既存なら削除、無ければ作成
- 削除済みメッセージへのリアクションは404

### 3.6 メッセージ一覧・検索ジャンプ用コンテキスト取得(「around」取得としての正式化)

- `listMessages`:トップレベルメッセージを投稿日時降順で取得し、クライアントには古い順に並べ替えて返す。ページングは `(createdAt, id)` の複合カーソルで行う(§6「ページネーション方針」)。**削除済み(`deletedAt`非null)メッセージも除外せず取得し、tombstoneとして返す**(§3.3参照)。チャンネル/DM画面は上方向無限スクロール+仮想化リストで表示し、WebSocketで受信した新着メッセージは末尾に追加する(新着到達時のスクロール制御・「新着N件」ボタンの詳細UXは画面設計書 S-05/S-06 を参照。バックエンドAPIとしての変更点は無い)
- **`getMessageContext`(around取得、レビュー指摘により双方向継続取得に対応するようレスポンスを拡張)**: 検索結果・通知などから特定のメッセージにジャンプする際に使う。新規に「around API」を追加するのではなく、**既存の `context` APIをそのまま双方向カーソル取得として正式化する**(当初「前後それぞれ最大25件」の固定ウィンドウのみだったが、ジャンプ後にさらに古い方向・新しい方向へスクロールする契約が不足していたための拡張)。レスポンス形式:

```json
{
  "messages": ["... 対象メッセージを含む前後最大25件ずつ ..."],
  "targetMessageId": "msg_123",
  "olderCursor": { "createdAt": "2026-08-10T09:00:00Z", "id": "msg_050" },
  "newerCursor": { "createdAt": "2026-08-10T09:30:00Z", "id": "msg_100" },
  "hasOlder": true,
  "hasNewer": true
}
```

  - `olderCursor`/`newerCursor` は、ジャンプ後にさらに古い方向・新しい方向へスクロールする際、通常の `listMessages` エンドポイントへ `cursorCreatedAt`/`cursorId` として渡して継続取得するために使う(around専用の別実装は用意しない。同じカーソル方式を使い回す)
  - `hasOlder`/`hasNewer` が `false` の場合、UIはそれ以上の読み込みボタン・自動読み込みトリガーを表示しない
  - 対象がスレッド返信の場合は親メッセージを軸にウィンドウを組み、`replyMessageId` を返してクライアント側でスレッドパネルを開かせる(スレッドパネル側の継続読み込みは §3.4 の20件単位ページングに従う)。こちらも削除済みメッセージをtombstoneとして含める(特に親メッセージが削除済みでも返信ウィンドウは正常に組む)

### 3.7 Markdown記法対応

- **レンダリング(Markdown→HTML変換・サニタイズ)はクライアント側のみで行う**:`marked` でHTML化した後、`DOMPurify` でサニタイズし、`img` タグは除外する
- **バックエンドはMarkdown文法の解釈・HTML生成を一切行わない**。行うのは本文の長さ等、入力値としてのバリデーション(Bean Validation)のみ
- この設計により、サーバーが保存する `body` は常に未加工のMarkdownテキストであり、XSS対策の責務は完全にクライアント側の `marked`+`DOMPurify` の組み合わせに委ねられる。将来クライアント側の実装がこのサニタイズ経路を通さずに `body` を直接HTMLとして描画するような変更が入ると、保存済みの過去メッセージも含めて再びXSSリスクが生じる点に留意する(実装・レビュー時にDOMPurifyを経由しない `dangerouslySetInnerHTML` 相当の使用が無いかを確認すること。CLAUDE.mdの既存の全体方針とも一致する)

## 6. セキュリティ仕様

### 6.1 MessageScopeGuard(confused-deputy対策、最重要)

`requireChannelMember`/`requireDmAccess` は「呼び出し元がURLの `channelId`/`dmId` のメンバーか」だけを検証し、パスに含まれる `messageId` がその scope に実際に属しているかは別途保証しなければならない。これを怠ると、**自分が参加している任意のチャンネル/DMのURLに、権限外のチャンネル/DMの `messageId` を組み合わせて渡すことで、本文やスレッド返信を読めてしまう**(confused-deputy攻撃)。

- `MessageScopeGuard.assertInScope(message, scope)` は、取得した `message.channelId`/`message.dmId` が呼び出し元のURLスコープ(`scope.channelId`/`scope.dmId`)と完全一致することを検証し、不一致であれば **404**(「メッセージが見つかりません。」)を返す
- **`messageId` を受け取る全エンドポイントの先頭で呼ぶ**:`context`取得、`replies`取得、編集、削除、リアクション切り替え、返信投稿時の `parentId` 検証、いずれも対象
- 実装上は、`MessageScopeGuard` を `MessageService` のミューテーション処理と同じクラス/パッケージに置く(プロトタイプの `messages-service.ts` が `assertMessageInScope` を同ファイルに置いていた設計を踏襲し、認可チェックの取りこぼしを防ぐ)

### 6.2 権限モデル

| 操作 | 必要な権限 |
|------|-----------|
| メッセージ一覧・詳細取得・スレッド閲覧 | スコープ(チャンネル/DM)のメンバーであること |
| メッセージ投稿 | スコープのメンバーであること |
| メッセージ編集・削除 | スコープのメンバーであること **かつ** 投稿者本人であること(他人の投稿は403) |
| リアクション切り替え | スコープのメンバーであること(投稿者本人である必要はない) |

### 6.3 ソフトデリートの扱い(tombstone方式、レビュー指摘により修正)

- `Message.deletedAt` は nullable カラムのまま(Hibernate `@SQLDelete` フィルタは使わず、明示クエリで除外する設計、計画書§2)
- **`deletedAt IS NULL` による除外が必要なのは検索(検索機能定義書)のみ**。一覧取得(`listMessages`)・スレッド返信取得(`listThreadReplies`)・コンテキスト取得(`getMessageContext`)は削除済み行を除外せず、tombstone(本文を伏せた行)として返す(理由は§3.3参照)。当初「メッセージを列挙する全てのクエリで除外する」としていたが、これだと画面設計書が要求する「このメッセージは削除されました」という再読み込み後も維持される表示や、親メッセージ削除時のスレッド返信到達性と矛盾するため、対象を検索クエリに限定するよう訂正した
- 削除済みメッセージへの**書き込み系操作**(編集・リアクション・再削除)は404として扱う(既に削除されたものへの操作を許さない)。読み取り系操作(一覧・コンテキスト・スレッド取得)は上記の通りtombstoneとして200で返す

### 6.4 添付ファイルの投稿時所有権検証

- メッセージ作成時、指定された `attachmentIds` の各ファイルについて「アップロード者が投稿者本人であること」「まだどのメッセージにも紐付いていないこと」を検証する(他人がアップロードした添付ファイルを勝手に自分のメッセージへ付け替えることを防ぐ)
- アップロード後の**閲覧時**のライブ権限再チェック(チャンネル/DMからキックされた後の取得不可)は `添付ファイル機能定義書.md` の対象であり、本ドキュメントの対象外(参照のみ)

### 6.5 Markdown/XSS対策の責務分界

- サニタイズは完全にクライアント側(`marked`+`DOMPurify`、`img`タグ除外)の責務。バックエンドはHTML生成を行わないため、サーバー側の出力エスケープに起因するXSSは原理的に発生しない一方、クライアント実装の不備(DOMPurifyを経由しないレンダリング経路の追加)がそのままXSS脆弱性に直結する非対称なトレードオフであることを認識しておく

### 6.6 ページネーション方針

- メッセージ一覧・スレッド返信一覧は `createdAt` の単純降順ではなく、**`(createdAt, id)` の複合カーソル**でページングする(`createdAt` だけでは同一ミリ秒に複数行が存在した場合に取りこぼす可能性があるため)
- Repository のカーソルクエリは `WHERE (created_at, id) < (:cursorCreatedAt, :cursorId) ORDER BY created_at DESC, id DESC` の形で統一する(検索機能・通知機能も同じ方針)

## 7. 制約・前提条件

- メッセージの物理削除機能は無い(常に論理削除)。管理者による完全消去機能も今回のスコープには含めない
- スレッド返信の階層は1階層に制限する。**プロトタイプにはこの禁止バリデーションが無かったが、新スタックでは§3.1の通りAPIレベルで技術的に禁止する**(レビュー指摘により追加。UIが1階層のスレッド表示のみを前提としており、バリデーションが無いとUIから到達不能な2階層目の返信が作成できてしまうため、プロトタイプからの意図的な差分として本設計から新規に導入する)
- リアクションの絵文字はサーバー側で許可リストを持たない(任意の1〜8文字を許容)

| 機能 | 理由 |
|------|------|
| メッセージのピン留め | スコープ外 |

| 1 | クロスチャンネルのメッセージID漏洩防止(confused-deputy) | 自分が参加する別チャンネルのURLに、権限外チャンネルの `messageId` を渡すと404になること(`context`/`replies`/編集/削除/リアクションの全エンドポイントで検証) |
| 2 | ワークスペースキック後のDMメッセージ取得404 | `DM機能定義書.md` §9 参照。HTTPエンドポイント経由の統合テストとして本フェーズで実施 |

新規に追加する受け入れテスト:

| # | テストケース | 確認内容 |
|---|------------|---------|
| 3 | 他人のメッセージ編集・削除の403 | 投稿者本人以外が編集・削除を試みると403になること |
| 4 | 削除済みメッセージへの操作の404 | 論理削除済みメッセージへの編集・リアクションが404になること |
| 5 | ソフトデリートのtombstone表示 | 削除済みメッセージが一覧・スレッド返信・コンテキスト取得の結果からは除外されず、本文が伏せられたtombstoneとして返ること。かつ検索結果からは除外されること(§3.3・§6.3参照) |
| 6 | 添付ファイルの所有権検証 | 他人がアップロードした添付ファイル、または既に他メッセージへ添付済みのファイルIDを指定すると投稿が拒否されること |
| 7 | 複合カーソルページネーション | 同一ミリ秒に複数メッセージが存在するケースで、`(createdAt, id)` カーソルにより取りこぼしなくページングできること |
| 8 | 2階層目スレッド返信の拒否 | 既に返信であるメッセージ(`parentId`が非NULL)を`parentId`に指定して投稿しようとすると400になること |
