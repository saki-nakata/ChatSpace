# 検索機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15
**作成者:** Nakata Saki

---

## 1. 機能概要

自分が所属しているチャンネル・DM の範囲内でメッセージ本文を部分一致検索する機能。プロトタイプは SQLite の `contains`(大文字小文字区別あり、全文検索エンジン未導入)による簡易実装だったが、新スタックでは PostgreSQL の **`pg_trgm` 拡張 + `ILIKE`** による部分一致検索(大文字小文字区別なし)に置き換える(`.plans/java-spring-boot-redesign.md` §5)。

**最重要の設計制約**: 検索範囲は常に「呼び出しユーザーが現在参加している(=ライブなメンバーシップを持つ)チャンネル・DM」に限定する。非所属のチャンネル/DM を明示的に指定して検索した場合も、403/404 のようなエラーで存在を示唆せず、**単に「結果なし」を返す**ことで、権限外リソースの存在自体を漏洩させない設計とする(プロトタイプの `search.ts` の方針を踏襲)。

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、過去に自分が読める範囲で交わされた会話をキーワードで検索したい |
| US-02 | ユーザーとして、特定のチャンネルに絞って検索したい |
| US-03 | ユーザーとして、検索結果に自分が読めないチャンネル/DM の内容が絶対に含まれないと確信したい |
| US-04 | ユーザーとして、削除済みのメッセージが検索結果に出てこないことを期待する |
| US-05 | ユーザーとして、`%` や `_` のような記号を含む文字列で検索しても、意図通りの文字どおり一致で検索したい |

## 3. 機能詳細

### 3.1 検索範囲の決定

- リクエスト時点で、呼び出しユーザーが所属する `ChannelMember` の `channelId` 一覧と、参加中の `DMThread` の `id` 一覧を都度取得し、検索対象をこの範囲に限定する(キャッシュや過去のスナップショットは使わない=ライブなメンバーシップ)。
- `channelId` を明示指定した場合は、まず呼び出しユーザーがそのチャンネルのメンバーであるかを確認する。**非メンバーであれば 403/404 を返さず、`messages: []` という「結果なし」のレスポンスを返す**(プロトタイプと同じ設計。所属チャンネルかどうかの真偽をレスポンスの違いから推測できないようにする)。

### 3.2 検索クエリ(`pg_trgm` + `ILIKE`)

- Flyway マイグレーションで `CREATE EXTENSION IF NOT EXISTS pg_trgm` を有効化し、`Message.body` に `CREATE INDEX message_body_trgm_idx ON message USING GIN (body gin_trgm_ops)` を追加する。
- `SearchService` は以下の形のネイティブクエリを実行する(`.plans/java-spring-boot-redesign.md` §5 のクエリ例):

```sql
SELECT * FROM message
WHERE deleted_at IS NULL
  AND (channel_id = ANY(:myChannelIds) OR dm_id = ANY(:myDmIds))
  AND body ILIKE '%' || REPLACE(REPLACE(REPLACE(:q, '\', '\\'), '%', '\%'), '_', '\_') || '%' ESCAPE '\'
  AND (created_at, id) < (:cursorCreatedAt, :cursorId)
ORDER BY created_at DESC, id DESC
LIMIT 50
```

- **`deleted_at IS NULL` を必ず明示する**: ソフトデリート済みメッセージは検索対象から除外する(削除されたメッセージの本文が検索結果経由で読めてしまうと削除操作の意味が失われるため)。**この除外は検索クエリに限った方針であり、一覧・スレッド・コンテキスト取得では逆に削除済み行をtombstoneとして含める**(レビュー指摘により明確化。メッセージング機能定義書§3.3・§6.3参照。検索とそれ以外の一覧系エンドポイントで扱いが異なる点に注意)。
- **ページネーション方式(レビュー指摘により、モーダルUIに即した方式を確定)**: `(created_at, id)` の複合カーソルで降順ページングする方式自体は他エンドポイントと共通(`created_at` 単体では同一ミリ秒に複数行が存在した場合に取りこぼす可能性があるため、`id` を tie-breaker として含める)。1回のレスポンスは最大50件、`nextCursor: { createdAt, id } | null` を返す(プロトタイプの `RESULT_LIMIT` を踏襲)。
- **検索結果パネル(S-12、モーダル)のUI方針**: 検索結果は専用ページではなくモーダル内に表示されるため、**完全な無限スクロールのみには頼らず、「さらに検索結果を表示」ボタンを基本とし、ボタン押下後にスクロールでも追加取得できる併用方式**とする(モーダル末尾への到達やキーボード操作での操作性を優先する。無限スクロールのみだと、モーダル内でどこまでスクロールすれば終端か分かりにくい)。
- **件数表示**: 追加の `COUNT(*)` クエリは発行しない。`nextCursor` の有無から件数表示を組み立てる: 現在読み込んだ件数が50件で `nextCursor != null` なら「50件以上」、100件読み込み時点で `nextCursor != null` なら「100件以上」、`nextCursor == null` になった時点(例: 150件で打ち止め)で初めて「150件」という確定件数を表示する。

### 3.3 ワイルドカードのエスケープ

- `ILIKE` は検索語中の `%` と `_` をワイルドカードとして解釈する。ユーザー入力の「文字どおりの部分一致」を要件とする以上、検索語中の `%`・`_`・エスケープ文字自身(`\`)を事前にエスケープしてから `ESCAPE '\'` 句を付ける(上記クエリの `REPLACE` の三重チェーンがこれに当たる: まず `\` 自身を `\\` に、次に `%` を `\%` に、`_` を `\_` にエスケープする。適用順序を誤ると二重エスケープになるため、実装時にこの順序を厳守する)。
- これを怠ると、`%` や `_` を含む検索語で意図しないパターンマッチ(例: `_` が任意の1文字にマッチしてしまう)が発生する。

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| GET | `/workspaces/{workspaceId}/search?q={query}&channelId={channelId}&cursor={cursor}` | メッセージ検索(所属チャンネル/DM 範囲、`channelId` 省略時は全所属範囲を対象) | 必要 |

**レスポンス例**

```json
{
  "messages": [
    { "id": "msg_1", "channelId": "ch_1", "body": "明日の会議は10時からです", "createdAt": "2026-08-15T01:00:00Z" }
  ],
  "nextCursor": { "createdAt": "2026-08-15T01:00:00Z", "id": "msg_1" }
}
```

詳細なスキーマは Swagger UI(`/swagger-ui.html`)を正とする。

## 5. バリデーション仕様

| 項目 | 仕様 |
|------|------|
| `q`(検索語) | 1〜200文字(プロトタイプの `searchQuerySchema` を Bean Validation で1:1再現)。空文字は 400 |
| `channelId` | 任意。指定時は UUID 形式を検証。非メンバーの場合はエラーを返さず結果を空にする(§3.1) |
| ページングカーソル | `(createdAt, id)` の形式が不正な場合は 400、または先頭ページとして扱う(実装計画書で確定) |
| 未認証ユーザーの検索 | 401 |
| ワークスペース非メンバーの検索 | 404(ワークスペース自体への `requireWorkspaceMember` チェックを先に実施) |

## 6. セキュリティ仕様

- **検索スコープの漏洩防止**: 検索対象は常にリクエスト時点でライブに解決した「自分が参加しているチャンネル/DM」の集合に限定する。事前計算・キャッシュされたメンバーシップは使わない。これは通知・添付ファイルと並び、CLAUDE.md が名指しで「特にメッセージ検索と通知は、権限外のチャンネル/DMの内容を含めやすい」と警告している箇所であり、最優先で検証する。
- **存在の秘匿(403/404 と区別しない設計)**: 非所属のチャンネルを `channelId` に指定して検索しても、エラーコードは返さず「結果なし」を返す。これにより、レスポンスの違い(200 の空配列 vs 403/404)から「そのチャンネルが存在するかどうか」を推測できないようにする。プライベートチャンネルの `requireChannelMember` が 404(存在の秘匿)を返す設計と一貫性を持たせている。
- **ソフトデリート済みメッセージの除外**: `deleted_at IS NULL` を全検索クエリで明示する。削除されたメッセージの本文が検索結果経由で読めてしまうと、削除操作自体の意味が失われる。
- **ワイルドカードインジェクション対策**: §3.3 のエスケープ処理により、ユーザー入力の `%`/`_` が意図しないパターンマッチを引き起こすことを防ぐ(検索結果の正しさに関わる問題であり、直接的な認可バイパスではないが、期待しない検索結果の広がりを防ぐという意味でセキュリティ仕様に含める)。
- **DM 検索とワークスペードキックの関係**: DM の検索対象範囲(`myDmIds`)は「DM 参加者であり、かつ現在も対象ワークスペースの `WorkspaceMember` であること」を条件に解決する。ワークスペースからキックされたユーザーが、既知の DM が過去に存在したことだけを根拠に検索対象へ含めてしまわないようにする(`.plans/java-spring-boot-redesign.md` §3 の DM 権限ギャップ修正と同じ原則を検索にも適用する)。

## 7. 制約・前提条件

- 検索対象はメッセージ本文のみ(添付ファイルのファイル名やユーザープロフィールは対象外)。
- 1回の検索結果は最大50件、`(createdAt, id)` カーソルでページングする。
- **既知の制約(パフォーマンス特性)**: `pg_trgm` は検索対象文字列から抽出可能なトライグラムが無い、またはごく少ない場合、GIN インデックスを効率的に絞り込めず、PostgreSQL のプランナの判断により **seq scan(全表シーケンシャルスキャン)または index full scan にフォールバックし得る**。「3文字未満のクエリは必ず全表スキャンになる」と一律に断定はできず、テーブルサイズやプランナの統計情報にも依存するが、日本語の2文字クエリ(例:「会議」)では長いクエリと異なる性能特性になり得る。**結果自体の正しさ(`ILIKE` によるマッチ)は保たれる**ため、機能要件としては問題ないが、レイテンシが伸びる可能性がある既知のギャップとして受け入れる。Render が `pg_bigm`(2文字から効く拡張)を公式サポートしていないため、この制約は今回のスコープでは解消しない(`.plans/java-spring-boot-redesign.md` の「スコープに関する方針」参照)。
- 形態素解析による自然な単語区切り検索は今回のスコープ外(スペース区切りでない日本語の複合語検索は部分一致に依存する)。

---

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| 形態素解析ベースの全文検索(例: `pg_bigm`, Elasticsearch 等) | スコープ外。Render のマネージド拡張制約と学習目的のバランスから `pg_trgm` + `ILIKE` を採用 |
| ファイル名・ユーザープロフィールの検索 | スコープ外。メッセージ本文のみが検索対象 |
| 検索結果のハイライト表示(マッチ箇所の強調) | フロントエンドの UX 拡張として任意(フェーズ10)、本ドキュメントの必須要件には含めない |
| 検索履歴の保存・サジェスト | スコープ外 |
