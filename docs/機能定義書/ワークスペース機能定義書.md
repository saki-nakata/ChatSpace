# ワークスペース機能定義書

**バージョン:** 1.0
**作成日:** 2026-08-15

> 本ドキュメントは `.plans/java-spring-boot-redesign.md`(以下「計画書」)§3「認証・認可レイヤー」を正式文書化したものである。移植元は `apps/api/src/routes/workspaces.ts`・`apps/api/src/lib/authz.ts`。

---

## 1. 機能概要

ワークスペースはチャンネル・DM・メンバーシップの最上位のマルチテナント境界。作成したユーザーが自動的に **オーナー**(`WorkspaceRole.OWNER`)になり、それ以外の参加者は **メンバー**(`WorkspaceRole.MEMBER`)になる。

- ワークスペースの新規作成・自分の所属ワークスペース一覧取得
- メンバー一覧・オンラインプレゼンス確認
- オーナー限定操作:メンバー招待、メンバーのキック(強制退出)
- メンバー自身による自主退出(オーナーは退出不可)
- 認可は `WorkspaceAuthorizationService`(プロトタイプの `authz.ts` の `requireWorkspaceMember`/`requireWorkspaceOwner` を移植)が担う

---

## 2. ユーザーストーリー

| ID | ストーリー |
|----|-----------|
| US-01 | ユーザーとして、新しいワークスペースを作成しオーナーになりたい |
| US-02 | ユーザーとして、自分が参加している全ワークスペースの一覧を見たい |
| US-03 | ワークスペースメンバーとして、他のメンバーの一覧とオンライン状況を確認したい |
| US-04 | オーナーとして、ユーザーIDを指定してメンバーを招待したい |
| US-05 | オーナーとして、問題のあるメンバーをワークスペースから強制退出させたい |
| US-06 | メンバーとして、自分の意思でワークスペースから退出したい(ただしオーナーは退出できない) |
| US-07 | 非メンバーとして、参加していないワークスペースの情報(存在・メンバー・チャンネル等)にはアクセスできないようにしたい |

---

## 3. 機能詳細

### 3.1 ワークスペース作成

- 入力:ワークスペース名(1〜80文字)
- 作成者は自動的にオーナー(`role = OWNER`)としてメンバーに追加される
- 同一名のワークスペースを禁止する一意制約は設けない(プロトタイプと同じ)

### 3.2 ワークスペース一覧

- 認証ユーザーが `WorkspaceMember` を持つワークスペースのみを、参加日時(`joinedAt`)昇順で返す
- 各要素に自分のロール(`myRole`: `OWNER`/`MEMBER`)を含める

### 3.3 メンバー一覧

- ワークスペースメンバーのみアクセス可(非メンバーは404、§6)
- 参加日時昇順で全メンバー(ユーザー情報・ロール・参加日時)を返す

### 3.4 プレゼンス(オンラインメンバー確認)

- ワークスペースメンバーのみアクセス可
- 現在オンラインの `userId` 一覧を返す(参加直後のスナップショット用)。以降の変化はリアルタイム経路(`/topic/workspaces.{workspaceId}.presence`)で受け取る。プレゼンス管理自体の詳細は `リアルタイム通信機能定義書.md` を参照

### 3.5 メンバー招待(オーナー限定)

- 入力:招待するユーザーID(ハンドル)
- 処理:
  1. オーナー権限チェック(§6)
  2. 指定ハンドルのユーザーを検索(存在しなければ404)
  3. 既にメンバーなら409 Conflict
  4. `WorkspaceMember`(role=MEMBER)を作成
  5. 招待されたユーザーへ通知(`WORKSPACE_INVITE` 種別、詳細は `通知機能定義書.md`)を送信

### 3.6 メンバーのキック(オーナー限定)

- 入力:対象ユーザーの内部ID
- 処理:
  1. オーナー権限チェック
  2. オーナー自身を対象にした場合は400(オーナーはキックできない)
  3. 対象がメンバーでなければ404
  4. **同一トランザクション内で** 対象ユーザーの当該ワークスペース内 `ChannelMember` を全削除してから `WorkspaceMember` を削除する(チャンネル参加も道連れで失効させる)
  5. トランザクションコミット後(`AFTER_COMMIT`)に強制切断・リアルタイム通知を行う。詳細な配送設計(セッションレジストリ、`WebSocketHandlerDecoratorFactory`)は `リアルタイム通信機能定義書.md` を参照
- **DMへの影響に関する重要な注意**: ワークスペースキックは `DMThread` レコード自体を削除しない(DMスレッドは `userAId`/`userBId` を保持し続ける)。そのため DM への読み書き・添付ファイル取得・通知の可視性を確実に失わせるには、DM側の認可サービスが **キック後もライブなワークスペースメンバーシップを再確認する** 設計が必須になる。詳細・実装方針は `DM機能定義書.md` の「セキュリティ仕様」を参照(計画書で発見された実在するギャップ)

### 3.7 自主退出

- 認証ユーザー自身がワークスペースから退出する
- 対象ユーザーが `OWNER` ロールの場合は400(オーナーはオーナー権限の移譲・ワークスペース削除の仕組みが無いため退出できない)
- それ以外はキックと同じ「チャンネルメンバーシップも道連れで削除」処理(§3.6手順4〜5)を、自分自身に対して実行する

## 4. 使用 API

| Method | エンドポイント | 説明 | 認証 |
|--------|--------------|------|------|
| POST | `/workspaces` | ワークスペース作成(作成者がオーナーになる) | 必要 |
| GET | `/workspaces` | 自分の所属ワークスペース一覧 | 必要 |
| GET | `/workspaces/{workspaceId}/members` | メンバー一覧 | 必要(ワークスペースメンバー) |
| GET | `/workspaces/{workspaceId}/presence` | オンラインメンバーのユーザーID一覧 | 必要(ワークスペースメンバー) |
| POST | `/workspaces/{workspaceId}/invite` | メンバー招待 | 必要(オーナー限定) |
| POST | `/workspaces/{workspaceId}/kick` | メンバーのキック | 必要(オーナー限定) |
| POST | `/workspaces/{workspaceId}/leave` | 自主退出(オーナーは不可) | 必要(ワークスペースメンバー) |

## 6. セキュリティ仕様

| 項目 | 仕様 |
|------|------|
| メンバーシップ判定 | `WorkspaceAuthorizationService.requireMember(workspaceId, userId)` — `WorkspaceMember` レコードが無い場合は **404**(ワークスペースの存在自体を非メンバーに知らせない) |
| オーナー限定操作 | `WorkspaceAuthorizationService.requireOwner(workspaceId, userId)` — メンバーではあるがオーナーでない場合は **403**。非メンバーの場合はメンバーチェックが先に走るため404になる(オーナー限定操作の失敗理由から「メンバーかどうか」が漏れない) |
| **404-not-403 方針** | 「存在自体を隠すべきリソース(非参加のワークスペース)」は404、「閲覧可能だが操作不可(メンバーだがオーナーでない)」は403、という区別を厳密に守る |
| オーナーのキック免除 | オーナー自身をキック対象に指定した場合は400(オーナーは自分自身を含めキック不可) |
| オーナーの退出制限 | オーナーは `/leave` を呼んでも400。オーナー権限の移譲機構が無いため、ワークスペースを離れる手段は無い(既知の設計、§7) |
| キック時のカスケード | キック・自主退出のいずれも、当該ワークスペース内の全チャンネルメンバーシップを同一トランザクションで削除する。これにより「ワークスペースからは抜けたがチャンネルには居残る」という不整合を防ぐ |
| **DMアクセスへの波及(重要)** | ワークスペースメンバーシップの削除だけでは `DMThread` の参加者情報は変化しないため、DM側の認可(`DmAuthorizationService`)が独自にライブなワークスペースメンバーシップを再確認しない限り、キック後もDMの読み書き・添付ファイル取得・通知が漏洩し続ける。これは計画書レビューで発見された **実在するギャップ**(プロトタイプの `authz.ts:55-65` の `requireDMAccess` が `requireWorkspaceMember` を呼んでいないことに起因)であり、新スタックでは `DmAuthorizationService.requireDmAccess()` に必須の再検証として組み込む。詳細は `DM機能定義書.md` |
| キック確定と強制切断のタイミング | `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` でイベントを受けてから強制切断する(トランザクションのコミット前に切断すると、後続の例外でロールバックした場合に矛盾が生じるため)。詳細は `リアルタイム通信機能定義書.md` |

## 7. 制約・前提条件

- オーナー権限の移譲機能は無い。オーナーがワークスペースを離れる唯一の方法は、ワークスペースそのものを削除する運用(削除API自体は本計画のスコープに明記が無く、今回のドキュメント一式でも扱わない)
- ワークスペース名の重複は許可される(一意制約なし)
- プレゼンス管理は単一プロセスのメモリ上で完結する。水平スケール対応(Redis共有プレゼンスへの切替)は検討の結果実施しないことが確定している

---

## 8. 対象外仕様

| 機能 | 理由 |
|------|------|
| オーナー権限の移譲 | スコープ外(プロトタイプにも無い) |
| ワークスペースの削除 | 本ドキュメント・現計画のスコープでは詳細化しない |
| ワークスペース名の重複禁止 | 要件上不要 |
| 複数オーナー制 | スコープ外。オーナーは作成者1名のみ |

## 9. テスト

`test/authorization.test.ts` からポートするもの(フェーズ2、既存テストで検証済みの5点のうち該当分):

| # | テストケース | 確認内容 |
|---|------------|---------|
| 1 | オーナー限定操作の403 | 一般メンバーが招待・キックAPIを呼ぶと403になること |
| 2 | 非メンバーの404 | ワークスペースメンバーでないユーザーがメンバー一覧・プレゼンス等にアクセスすると404になること(存在の有無が漏れないこと) |

新規に追加する受け入れテスト:

| # | テストケース | 確認内容 |
|---|------------|---------|
| 3 | オーナー自身のキック不可 | オーナーを対象にキックAPIを呼ぶと400になること |
| 4 | オーナーの退出不可 | オーナーが `/leave` を呼ぶと400になること |
| 5 | キック時のチャンネル道連れ削除 | キック後、対象ユーザーの当該ワークスペース内 `ChannelMember` が全て削除されていること |
| 6 | キックのロールバック時は強制切断されないこと | キック処理が例外でロールバックした場合、強制切断が発生しないこと(`AFTER_COMMIT` の検証。詳細は `リアルタイム通信機能定義書.md`) |
| 7 | キック後の即時再購読拒否 | キック成功後に即座に再接続しても、削除済みメンバーシップのため対象ワークスペース/チャンネルへ再購読できないこと |
